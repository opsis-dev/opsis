# Packaging and licences

How a release build and its installers are made, what they ship, how update files are signed and listed, where the app reads its resources, the app icon, and the licence rules for dependencies, vendored code and the bundled FFmpeg. Paths are relative to the repository root. The engine and FFmpeg at run time are in [engine.md](engine.md), the app's side of updates in [updates.md](updates.md); see also [AGENTS.md](../AGENTS.md).

## Rules

### Building

- **`bun run make` runs `bun run stage`, builds the release binary against `setup`'s static Qt, then `opsis-packager` builds the installers into `~/.cache/opsis-dev/build` (`buildAndPackage`).** It builds the deb on Linux, the macOS app and dmg on macOS, the NSIS installer on Windows; `--formats` names others from `deb`, `rpm`, `appimage`, `pacman`, `nsis`, `app` and `dmg`, and the remaining arguments go to `cargo build`.
- **Each installer is made by its format's own documented tool, which `opsis-packager` runs**: `dpkg-deb` (zstd), `rpmbuild` (zstd payload, package format 4 through `_rpmformat`, so the package is the same whichever rpm builds it: one that defaults to format 6 writes a package `bsdtar` can't read), `makepkg`, `appimagetool` with the AppImage runtime, `makensis`, and on macOS `iconutil`, `codesign`, `ditto`, `tar` and `hdiutil`. A tool that isn't on the PATH fails the build by name.
  - A format builds only on its own system (`Format::builds_on`); naming another fails with `WrongPlatform`. Naming both `app` and `dmg` builds the app once, since they share it.
  - Linux's tools come from the system's packages (`rpm`, `makepkg` with `pacman-package-manager` and `libarchive-tools`, `patchelf`, `fakeroot`), which the Linux runner installs in `.github/workflows/release.yml`; appimagetool and the AppImage runtime are downloaded pinned by sha256 into `~/.cache/opsis-dev/appimage-tools` (versions and pins in `appimage-tools.ts`).
  - The Windows runner downloads NSIS pinned by sha256 (`NSIS_URL` in `.github/workflows/release.yml`).
- **The release binary and its packages build on the machine that runs `bun run make`, into `target/release`, and in CI on the runner** (`buildAndPackage`): no container builds them on any system, so what ships comes from one runner, from Qt and Skia to the packages.
  - `bun run packager:test` (`scripts/packager-test.ts`) runs `opsis-packager`'s tests the same way, the ignored ones that build each format among them.
- **Every package's program is a copy marked with that package's installer** (`marked_program`): the release program holds a 32-byte marker, `opsis-installer:unmarked`, exactly once, and the packager overwrites it with its installer's name (`app` for both the app and the DMG, which share one marked program) before the format's tool sees the program.
  - A program with no marker, or with two, fails the build, so a stale or foreign binary can't be packaged.
  - On macOS `build_app` then signs FFmpeg and the whole `.app` ad hoc (`codesign --force --sign -`), which signs the marked program again inside the bundle.
- **Update files are signed when `OPSIS_UPDATE_KEY` is set** (`sign_update`, with `OPSIS_UPDATE_KEY_PASSWORD` when the key is encrypted): the AppImage, the NSIS installer and the macOS `.app.tar.gz` each get a minisign `.sig` and a `.update.json` naming the feed key, the file and the signature.
- **A feed key is `<os>-<arch>-<installer>`**: Rust's `std::env::consts::OS` and `ARCH` and the installer's name (`feed_key`, `Installer::name`, `crates/update/src`), such as `windows-x86_64-nsis`.
  - The key is the base64 minisign box the git-ignored `signing/opsis.key` holds, encrypted with the password; `bun` reads both from the ignored `.env`, CI from the repository's secrets, and `opsis-packager` gets them through its environment, never on a command line.
  - The deb, rpm and pacman packages aren't signed: they can't replace themselves, so the app sends their users to the release page.
- **A `vX.Y.Z` tag drafts the release** (the `draft` job, which runs on tags only; a run started by hand builds the packages as artifacts and drafts nothing): `release-feed.ts` merges the `.update.json` files into `latest.json` with the version (which must match the tag) and that version's section of `CHANGELOG.md`, writes the GitHub release's notes (`githubNotes`: that same section, then the FFmpeg section of `THIRD_PARTY_NOTICES.md` unchanged), and `gh release create --draft` uploads every package with them. A person publishes the draft after the release test pass; until then `releases/latest` still serves the previous feed.
  - `latest.json` is `{ version, notes, pub_date, platforms }`, `platforms` mapping each feed key to `{ url, signature }` (`feed`; read by `Feed` in `crates/update/src/feed.rs`).
  - It refuses any count of update files but `SELF_UPDATING_KEYS`: the AppImage from the Linux runner, NSIS from the Windows one, and the macOS app from each of the two macOS runners (Apple silicon and Intel). A new self-updating format or runner changes that number.
- **`opsis-packager` refuses a program that loads Qt, ICU or KDDockWidgets, or looks for libraries in an absolute folder** (`check_self_contained`), so a development build can't be packaged.
- **Every Linux package installs the same files**: the programs in `/usr/bin`, the resources in `/usr/lib/opsis`, the desktop entry and the hicolor icons, all staged by `stage_linux`; the AppImage's AppDir holds the same tree under `usr/`. `tests/packages.rs` compares the deb's, the rpm's, the pacman package's and the AppImage's files and checks each program's marker; the deb test runs everywhere, the others in the container (`bun run packager:test`, which hands the pinned AppImage tools to the test as `OPSIS_APPIMAGETOOL` and `OPSIS_APPIMAGE_RUNTIME`).
- **Package dependencies come from the libraries the program loads**: `linux_deps.rs` names each one's deb and pacman package, the rpm requires the libraries themselves, and every format also needs `ca-certificates` for the downloads the app makes when asked. A library with no entry fails the build.
- **`bun run package:check` installs each Linux package from `~/.cache/opsis-dev/build` in a plain `debian:trixie` container, the way its format installs, and runs the installed program through the `views` scenario on the offscreen platform**: the deb with apt (and again without CA certificates), where the installed program also opens the changelog example and exports it through the Local API with the dev engine and the bundled FFmpeg reads the video back, the rpm with `rpm` into a separate root, the pacman package with `pacman` (Debian's `pacman-package-manager`), the AppImage with only the system libraries it leaves out.
  - Each check also asks the installed program which installer made it; the deb, rpm and pacman checks also find `THIRD_PARTY_NOTICES.md` where the package puts its resources.
  - After the deb's export, the installed `opsis-mcp` runs a Lua script on the still-open project over stdio, and the installed `opsis-agent` answers an ACP `initialize`, so a package whose tool server can't reach the app, or whose agent doesn't start, fails.
  - The checks install as root; the deb's export runs the program as your user (`setpriv` with `OPSIS_CHECK_UID` and `OPSIS_CHECK_GID`) on a work folder it gets as `OPSIS_CHECK_WORK`.
- **The AppImage bundles every library `ldd` finds for the program except the base system's and those left to the system with everything they load** (`LEFT_TO_THE_SYSTEM` in `appimage.rs`).
  - The bundled libraries go in `usr/lib` with the runpath `$ORIGIN`, and the program gets `$ORIGIN/../lib` (`patchelf`), so nothing changes `LD_LIBRARY_PATH` for the shells and programs Opsis starts.
  - `APPIMAGE_SYSTEM_PACKAGES` in `package-check.ts` installs the deb packages of those libraries, so the installed AppImage fails the check when a library is neither bundled nor there; nothing compares the two lists themselves.
  - appimagetool runs unpacked when a package is built (`APPIMAGE_EXTRACT_AND_RUN=1`, set by `buildAndPackage` on Linux), and so does the AppImage in the check's container, so neither needs FUSE.
- **Windows installs the program, FFmpeg, the renderer program, `opsis-mcp`, `opsis-agent`, the resources and `opsis.ico` (`brand/icons/opsis.ico`) in one folder.** The NSIS installer installs per user into `%LOCALAPPDATA%\Programs\Opsis` without asking for administrator rights; `/P` makes it passive (no pages, closes itself), which is how an update runs it. A test keeps the NSIS uninstaller's list in step with the files the installer places.
- **macOS packages are the `.app` (the program, FFmpeg, the renderer program, `opsis-mcp` and `opsis-agent` in `Contents/MacOS`, the resources in `Contents/Resources`), its `.app.tar.gz` for updates, and the DMG for first installs.**
- **`bun run make` caps cargo at 8 jobs unless `CARGO_BUILD_JOBS` sets another number** (`scripts/lib/release.ts`).
- **There is one build: it ships FFmpeg, the renderer program (`opsis-renderer`, built from `opsis-effects`) `opsis-mcp` (built from `crates/mcp`) and `opsis-agent` (built from `crates/agent`, both in [assistant.md](assistant.md)) beside the app and never the recording browser.**
- **`stage.ts` empties `resources/`**, writes the browser's Chromium credits into the gitignored `resources/engine-licences/LICENSES.chromium.html`, and copies the FFmpeg licence from `setup`'s FFmpeg.
  - `opsis-tools install-engine` puts the pinned headless shell in `~/.cache/opsis-dev/stage-engine`; the credits are read from `chrome://credits` through `playwright-core` in the full Chrome for Testing of the same version (`fullChrome`, `scripts/lib/engine.ts`), downloaded and unpacked with `@zip.js/zip.js` into `~/.cache/opsis-dev/chromium-credits`, keeping the macOS app's symlinks and executable bits.
  - `setup` fetches FFmpeg for the host target (`rustc -vV`) as `opsis-ffmpeg-<target triple>[.exe]`, checked against the pins; the packager copies that program and stage copies its licence to `resources/LICENSE.ffmpeg.txt`.
- **A release build finds FFmpeg beside its own program as `opsis-ffmpeg`, never `ffmpeg`**, so a package can't clash with the distribution's `ffmpeg`; a debug build takes `OPSIS_FFMPEG` when it names a file by an absolute path (`bundled_ffmpeg`).
- **Release builds use `opt-level = 3`, full LTO and one codegen unit, and are stripped**; expect a slow, memory-heavy link.
- **The app reads its resources from the folder of its program, from `../lib/opsis` when `THIRD_PARTY_NOTICES.md` is there and not beside the program (every Linux package and the AppImage), or from `../Resources` on macOS (`resources_for`)**: `public/` (the app's only copy of the `app:` files), `engine-licences`, `LICENSE.ffmpeg.txt`, `LICENSE`, `THIRD_PARTY_NOTICES.md`, `QT_NOTICES.generated.md`. In development everything comes from the repository.
- **CI is three workflows**:
  - `.github/workflows/build.yml` builds every branch push on every platform in the dev profile and builds no installer: on Linux x64 setup, typecheck, lint, format, `bun run test` and `opsis-vt` in a release build; on Linux arm64, Windows x64 and macOS Intel setup, Clippy over the workspace and the Rust tests, with `opsis-e2e-input`, which is Wayland only, left out off Linux. Typecheck, the TypeScript lint, the format checks, cargo-deny and the comment check run once, on Linux x64, since they don't change with the system; Clippy runs everywhere, since each system compiles its own `cfg` code.
  - `.github/workflows/test.yml`, started by hand, runs on the same four machines plus Linux x64: setup with the engine, every e2e scenario the system runs ([e2e.md](e2e.md)) and every `#[ignore]`d test (the engine, the renderer program, the internet), with lavapipe as Linux's Vulkan driver and the recording browser's SwiftShader and Vulkan loader on macOS and Windows.
  - Neither has a macOS Apple Silicon job until Opsis builds its own FFmpeg ([plans/ffmpeg.md](../plans/ffmpeg.md)).
  - The three share one setup cache per system and processor (`setup-<os>-<arch>-<hash of the setup scripts>`, the same folders in each), so a release or a Test run restores what Build made. It is restored before setup and saved right after setup succeeds (`actions/cache/restore` and `actions/cache/save`), not at the end of the job, so a later failing step doesn't throw away the hour Qt, Skia and Filament take to build; the Rust cache saves on failure (`cache-on-failure`).
  - Build and Test share one Rust cache per system and processor (rust-cache's `shared-key`, `<os>-<arch>`), and setup keeps only what the later builds read, so every machine's caches fit in GitHub's 10 GB per repository: past it GitHub evicts the oldest entries, and the next run on that machine builds Qt, Skia and Filament again.
  - Every text file is checked out with LF line endings on every system (`.gitattributes`), since tests compare committed files with what the code writes byte for byte, and Windows runners otherwise check out CRLF.
  - Every step after setup runs even when one before it fails, and the Rust tests run with `--no-fail-fast`, so one run shows every failure.
  - On Linux the Test workflow runs the ignored tests inside their own D-Bus session with gnome-keyring unlocked (`dbus-run-session`, an empty line as its password), which the Secret Service tests need, and installs the same packaging tools as the release, since the packages test builds the deb, rpm and pacman packages.
  - The Test workflow names each runner's processor first, since the software graphics driver compiles its shaders for it and a picture golden can move a few pixels between processors.
  - On Linux the ignored-test step logs memory and disk every 30 s: a hosted runner that runs out of either is stopped with only a shutdown signal in the log (exit 143), as the arm64 runner's 16 GB of memory and 14 GB of disk allow.
  - The Test workflow's ignored tests get `OPSIS_UPDATE_KEY` and `OPSIS_UPDATE_KEY_PASSWORD` from the repository's secrets, as the release does, for the test that signs an update file.
  - The AppImage test needs the pinned AppImage tools and `patchelf`, so the general ignored run skips it and a Linux step runs it through `bun run packager:test`, which downloads the tools and names them (`OPSIS_APPIMAGETOOL`, `OPSIS_APPIMAGE_RUNTIME`).
  - `.github/workflows/release.yml`, on `vX.Y.Z` tags (`v[0-9]+.[0-9]+.[0-9]+`) and by hand, checks the source notice's links, builds each platform's installers, runs the FFmpeg capability test on every runner and `package:check` on the Linux runner only, and drafts the release on tags.
- **The packaging tests are Linux only** (`#![cfg(target_os = "linux")]`, `crates/packager/tests/packages.rs`, and `reads_the_libraries_a_real_program_loads`): they build Linux installers and read ELF programs, and the macOS and Windows installers have no test yet.
- **Check the workflows with `actionlint` after changing them.**

### Icons

- **`brand/logo.svg` is the one source for the app icon.** `bun run brand:icons` renders `brand/icons/` with the recording browser (ImageMagick draws the gradients wrong): the one `OPSIS_HEADLESS_SHELL` names, or else the pinned one it installs.
  - It also writes `brand/icons/opsis.ico` from the sizes up to 256 px (`ico`, `scripts/lib/ico.ts`): `crates/ui/build.rs` embeds it in the Windows program as `IDI_ICON1` (`embed-resource`), which Explorer, the taskbar and Qt's own window icon read, and the NSIS installer places it beside the program for its shortcuts and Add/Remove Programs.
  - The editor sets the PNGs as its window icon on every system (`AppIcon`, `crates/qt/cpp/app.cc`, through the Qt resources), so a development build shows it too.

### Licences

- **Opsis is GPL-3.0-or-later.** `LICENSE` is the official GPLv3 text from gnu.org, unchanged; the "or later" is declared in `package.json` and `Cargo.toml`.
- **Every dependency must be GPLv3-compatible**: a permissive licence, MPL-2.0 without the "Incompatible With Secondary Licenses" notice, GPLv3 or LGPLv3.
  - `cargo deny` (`bun run lint:deny`) checks the crates against `deny.toml`'s `allow`, which lists the licences crates use; nothing checks npm packages, so a new one's licence is checked by hand against that list.
- **Qt and KDDockWidgets are used under the GPL-3.0, and a release links them statically, with Qt built without ICU**, so no Qt or ICU files ship beside the program; development builds link the same static Qt, and how it is built is in [toolchain.md](toolchain.md). Their notices, and the MIT ones of the libraries KDDockWidgets compiles in, are in `THIRD_PARTY_NOTICES.md`; `QT_NOTICES.generated.md` holds the notices of the third-party code compiled into the Qt modules and plugins the program links, read from the static Qt's bill of materials; run `bun run qt:notices` again whenever Qt or `build.rs`'s modules and plugins change.
- **`deny.toml` holds the crate allow-list, worked out for the shipped platforms only** (its `targets`), so a licence only another platform pulls in never counts. It also denies yanked crates.
- **An advisory with no safe upgrade is an `ignore` entry with a `reason` saying where the crate comes from**, reviewed whenever dependencies move.
- **Vendored code and the icon data copied from the glyph sets (`GLYPH_SETS`, `scripts/lib/glyph-sets.ts`) keep their notices**; `glyphs:bundle` refuses a set whose notice is missing.
- **FFmpeg ships as a separate program, the unchanged ffmpeg-static GPLv3 build**, with the release's licence as `LICENSE.ffmpeg.txt`, listed in Settings → Licences from the resource folder.
- **Its source notice in `THIRD_PARTY_NOTICES.md` links upstream only** (FFmpeg's source and the ffmpeg-static release, which a test keeps on the pinned release); no source tarballs are attached, and every run of the release workflow checks the links (`bun run notice:links`).
  - Each GitHub release's notes carry the whole section after the changelog (`githubNotes`, `scripts/release-feed.ts`), read through `noticeSection` (`scripts/lib/notices.ts`), which the link check shares; `latest.json`'s notes, which the About page shows, keep the changelog only.
- **Built-in sounds, songs and fonts carry their credits in `THIRD_PARTY_NOTICES.md`** ([audio.md](audio.md), [fonts.md](fonts.md)).

## Deliberate limits

- **Programs aren't code signed** ([plans/release.md](../plans/release.md), code signing): macOS gets an ad-hoc signature only, and Windows none; only update files carry Opsis's minisign signature.
- **The macOS and Windows packages have never been built**: the static Qt, the editor's static link and the packages build there as they do on Linux (`runNatively`, [toolchain.md](toolchain.md); `buildAndPackage`), but no run of the release workflow has happened, so the first one is where they meet a real Mac and Windows runner ([plans/release.md](../plans/release.md) section 2).
- **A macOS package needs macOS 14.4 or newer** (`MACOS_MINIMUM` in `crates/packager/src/app.rs` and `scripts/lib/static-qt.ts`, kept equal by `static-qt.test.ts`): the oldest macOS Qt 6.12 runs on, and the deployment target the static Qt and the release build are compiled for.
- **The Windows release program is a GUI program** (`windows_subsystem` in `crates/ui/src/main.rs`, release builds only), so starting it opens no console window; a debug build keeps its console for the log.
- **The notices of the crates and npm packages compiled into the app are deliberately not shipped.**
