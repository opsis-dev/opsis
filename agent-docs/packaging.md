# Packaging and licences

How a release build and its installers are made, what they ship, how update files are signed and listed, where the app reads its resources, the app icon, and the licence rules for dependencies, vendored code and the bundled FFmpeg. Paths are relative to the repository root. The engine and FFmpeg at run time are in [engine.md](engine.md), the app's side of updates in [updates.md](updates.md); see also [AGENTS.md](../AGENTS.md).

## Rules

### Building

- **`bun run make` runs `bun run stage`, builds the release binary against `setup`'s static Qt, then `opsis-packager` builds the installers into `~/.cache/opsis-dev/build` (`buildAndPackage`).** It builds the deb on Linux, the macOS app and dmg on macOS, NSIS and MSI on Windows; `--formats` names others from `deb`, `rpm`, `appimage`, `pacman`, `nsis`, `msi`, `app` and `dmg`, and the remaining arguments go to `cargo build`.
- **Each installer is made by its format's own documented tool, which `opsis-packager` runs**: `dpkg-deb` (zstd), `rpmbuild` (zstd payload), `makepkg`, `appimagetool` with the AppImage runtime, `makensis`, WiX v7's `wix build`, and on macOS `iconutil`, `codesign`, `ditto`, `tar` and `hdiutil`. A tool that isn't on the PATH fails the build by name.
  - A format builds only on its own system (`Format::builds_on`); naming another fails with `WrongPlatform`. Naming both `app` and `dmg` builds the app once, since they share it.
  - Linux's tools come from Debian, installed in the trixie container (`PACKAGES` in `trixie.ts`); appimagetool and the AppImage runtime are downloaded pinned by sha256 into `~/.cache/opsis-dev/appimage-tools` (versions and pins in `appimage-tools.ts`).
  - The Windows runner downloads NSIS pinned by sha256 and installs WiX with `dotnet tool install` (`NSIS_URL` and `WIX_VERSION` in `.github/workflows/release.yml`); `wix build -acceptEula wix7` accepts WiX's Open Source Maintenance Fee EULA, which charges only above US$10,000 of yearly revenue.
- **On Linux the release binary and its packages always build in one plain `debian:trixie` container run (Docker, `runInTrixie`, which passes its script as `OPSIS_TRIXIE_SCRIPT`), into `target/trixie`, in CI too**, because the program then needs only trixie's glibc 2.41, the AppImage bundles libraries from the system that builds it, and Ubuntu has no `makepkg`. On macOS and Windows, `CI=true` builds on the runner into `target/release`. The container builds as your user (`setpriv`), with the repository, Cargo, rustup, Zig, the folders `setup` made for Qt, KDDockWidgets, Skia, Filament and FFmpeg, the AppImage tools and the output folder mounted at their own paths, and Debian's package downloads cached in `~/.cache/opsis-dev/trixie-apt`.
- **Every package's program is a copy marked with that package's installer** (`marked_program`): the release program holds a 32-byte marker, `opsis-installer:unmarked`, exactly once, and the packager overwrites it with its installer's name (`app` for both the app and the DMG, which share one marked program) before the format's tool sees the program.
  - A program with no marker, or with two, fails the build, so a stale or foreign binary can't be packaged.
  - On macOS `build_app` then signs FFmpeg and the whole `.app` ad hoc (`codesign --force --sign -`), which signs the marked program again inside the bundle.
- **Update files are signed when `OPSIS_UPDATE_KEY` is set** (`sign_update`, with `OPSIS_UPDATE_KEY_PASSWORD` when the key is encrypted): the AppImage, the NSIS installer, the MSI and the macOS `.app.tar.gz` each get a minisign `.sig` and a `.update.json` naming the feed key, the file and the signature.
- **A feed key is `<os>-<arch>-<installer>`**: Rust's `std::env::consts::OS` and `ARCH` and the installer's name (`feed_key`, `Installer::name`, `crates/update/src`), such as `windows-x86_64-msi`.
  - The key is the base64 minisign box the git-ignored `signing/opsis.key` holds, encrypted with the password; `bun` reads both from the ignored `.env`, CI from the repository's secrets, and the container gets them by name only (`passEnv` in `trixie.ts`), never on a command line.
  - The deb, rpm and pacman packages aren't signed: they can't replace themselves, so the app sends their users to the release page.
- **A `v*` tag drafts the release** (the `draft` job, which runs on tags only; a run started by hand builds the packages as artifacts and drafts nothing): `release-feed.ts` merges the `.update.json` files into `latest.json` with the version (which must match the tag) and that version's section of `CHANGELOG.md`, writes the GitHub release's notes (`githubNotes`: that same section, then the FFmpeg section of `THIRD_PARTY_NOTICES.md` unchanged), and `gh release create --draft` uploads every package with them. A person publishes the draft after the release test pass; until then `releases/latest` still serves the previous feed.
  - `latest.json` is `{ version, notes, pub_date, platforms }`, `platforms` mapping each feed key to `{ url, signature }` (`feed`; read by `Feed` in `crates/update/src/feed.rs`).
  - It refuses any count of update files but `SELF_UPDATING_KEYS`: the AppImage from the Linux runner, NSIS and MSI from the Windows one, and the macOS app from each of the two macOS runners (Apple silicon and Intel). A new self-updating format or runner changes that number.
- **`opsis-packager` refuses a program that loads Qt, ICU or KDDockWidgets, or looks for libraries in an absolute folder** (`check_self_contained`), so a development build can't be packaged.
- **Every Linux package installs the same files**: the programs in `/usr/bin`, the resources in `/usr/lib/opsis`, the desktop entry and the hicolor icons, all staged by `stage_linux`; the AppImage's AppDir holds the same tree under `usr/`. `tests/packages.rs` compares the deb's, the rpm's, the pacman package's and the AppImage's files and checks each program's marker; the deb test runs everywhere, the others in the container (`bun run packager:test`, which hands the pinned AppImage tools to the test as `OPSIS_APPIMAGETOOL` and `OPSIS_APPIMAGE_RUNTIME`).
- **Package dependencies come from the libraries the program loads**: `linux_deps.rs` names each one's deb and pacman package, the rpm requires the libraries themselves, and every format also needs `ca-certificates` for the downloads the app makes when asked. A library with no entry fails the build.
- **`bun run package:check` installs each Linux package from `~/.cache/opsis-dev/build` in a plain `debian:trixie` container, the way its format installs, and runs the installed program through the `views` scenario on the offscreen platform**: the deb with apt (and again without CA certificates), where the installed program also opens the changelog example and exports it through the Local API with the dev engine and the bundled FFmpeg reads the video back, the rpm with `rpm` into a separate root, the pacman package with `pacman` (Debian's `pacman-package-manager`), the AppImage with only the system libraries it leaves out.
  - Each check also asks the installed program which installer made it; the deb, rpm and pacman checks also find `THIRD_PARTY_NOTICES.md` where the package puts its resources.
  - The checks install as root; the deb's export runs the program as your user (`setpriv` with `OPSIS_CHECK_UID` and `OPSIS_CHECK_GID`) on a work folder it gets as `OPSIS_CHECK_WORK`.
- **The AppImage bundles every library `ldd` finds for the program except the base system's and those left to the system with everything they load** (`LEFT_TO_THE_SYSTEM` in `appimage.rs`).
  - The bundled libraries go in `usr/lib` with the runpath `$ORIGIN`, and the program gets `$ORIGIN/../lib` (`patchelf`), so nothing changes `LD_LIBRARY_PATH` for the shells and programs Opsis starts.
  - `APPIMAGE_SYSTEM_PACKAGES` in `package-check.ts` installs the deb packages of those libraries, so the installed AppImage fails the check when a library is neither bundled nor there; nothing compares the two lists themselves.
  - appimagetool and the AppImage run unpacked in a container (`APPIMAGE_EXTRACT_AND_RUN=1`), since there is no FUSE.
- **Windows installs the program, FFmpeg, the renderer program, the resources and `opsis.ico` (written by `ico` from `brand/icons/`) in one folder.** The NSIS installer installs per user into `%LOCALAPPDATA%\Programs\Opsis` without asking for administrator rights; `/P` makes it passive (no pages, closes itself), which is how an update runs it. The MSI installs per machine into Program Files, with a major upgrade replacing an older version. A test keeps the NSIS uninstaller's list in step with the files the installer places.
- **macOS packages are the `.app` (the program, FFmpeg and the renderer program in `Contents/MacOS`, the resources in `Contents/Resources`), its `.app.tar.gz` for updates, and the DMG for first installs.**
- **`bun run make` caps cargo at 8 jobs unless `CARGO_BUILD_JOBS` sets another number** (`scripts/lib/release.ts`), in the container too.
- **There is one build: it ships FFmpeg and the renderer program (`opsis-renderer`, built from `opsis-effects`) beside the app and never the recording browser.**
- **`stage.ts` empties `resources/`**, writes the browser's Chromium credits into the gitignored `resources/engine-licences/LICENSES.chromium.html`, and copies the FFmpeg licence from `setup`'s FFmpeg.
  - `install-engine` puts the pinned headless shell in `~/.cache/opsis-dev/stage-engine`; the credits are read from `chrome://credits` through `playwright-core` in the full Chrome for Testing of the same version (`fullChrome`, `scripts/lib/engine.ts`), downloaded and unpacked with `@zip.js/zip.js` into `~/.cache/opsis-dev/chromium-credits`, keeping the macOS app's symlinks and executable bits.
  - `setup` fetches FFmpeg for the host target (`rustc -vV`) as `opsis-ffmpeg-<target triple>[.exe]`, checked against the pins; the packager copies that program and stage copies its licence to `resources/LICENSE.ffmpeg.txt`.
- **A release build finds FFmpeg beside its own program as `opsis-ffmpeg`, never `ffmpeg`**, so a package can't clash with the distribution's `ffmpeg`; a debug build takes `OPSIS_FFMPEG` when it names a file by an absolute path (`bundled_ffmpeg`).
- **Release builds use `opt-level = 3`, full LTO and one codegen unit, and are stripped**; expect a slow, memory-heavy link.
- **The app reads its resources from the folder of its program, from `../lib/opsis` when `THIRD_PARTY_NOTICES.md` is there and not beside the program (every Linux package and the AppImage), or from `../Resources` on macOS (`resources_for`)**: `public/` (the app's only copy of the `app:` files), `engine-licences`, `LICENSE.ffmpeg.txt`, `LICENSE`, `THIRD_PARTY_NOTICES.md`, `QT_NOTICES.generated.md`. In development everything comes from the repository.
- **CI is two workflows**: `.github/workflows/build.yml` checks every push (typecheck, lint, format, tests, the `wayland` scenario, `opsis-vt` in a release build and the FFmpeg capability test in one job, the other e2e scenarios in another) and builds no installer; `.github/workflows/release.yml`, on `v*` tags and by hand, checks the source notice's links, builds each platform's installers, runs the FFmpeg capability test on every runner and `package:check` on the Linux runner only, and drafts the release on tags.
- **Check both workflows with `actionlint` after changing them.**

### Icons

- **`brand/logo.svg` is the one source for the app icon.** `bun run brand:icons` renders `brand/icons/` with the recording browser (ImageMagick draws the gradients wrong): the one `OPSIS_HEADLESS_SHELL` names, or else the pinned one it installs.

### Licences

- **Opsis is GPL-3.0-or-later.** `LICENSE` is the official GPLv3 text from gnu.org, unchanged; the "or later" is declared in `package.json` and `Cargo.toml`.
- **Every dependency must be GPLv3-compatible**: a permissive licence, MPL-2.0 without the "Incompatible With Secondary Licenses" notice, GPLv3 or LGPLv3.
  - `cargo deny` (`bun run lint:deny`) checks the crates against `deny.toml`'s `allow`, which lists the licences crates use; nothing checks npm packages, so a new one's licence is checked by hand against that list.
- **Qt and KDDockWidgets are used under the GPL-3.0, and a release links them statically, with Qt built without ICU**, so no Qt or ICU files ship beside the program; development builds link the same static Qt, and how it is built is in [toolchain.md](toolchain.md). Their notices, and the MIT ones of the libraries KDDockWidgets compiles in, are in `THIRD_PARTY_NOTICES.md`; `QT_NOTICES.generated.md` holds the notices of the third-party code compiled into the Qt modules and plugins the program links, read from the static Qt's bill of materials; run `bun run qt:notices` again whenever Qt or `build.rs`'s modules and plugins change.
- **`deny.toml` holds the crate allow-list, worked out for the shipped platforms only** (its `targets`), so a licence only another platform pulls in never counts. It also denies yanked crates.
- **An advisory with no safe upgrade is an `ignore` entry with a `reason` saying where the crate comes from**, reviewed whenever dependencies move.
- **Vendored code and the icon data copied from the glyph sets (`GLYPH_SETS`, `scripts/lib/glyph-sets.ts`) keep their notices**; `glyphs:bundle` refuses a set whose notice is missing.
- **FFmpeg ships as a separate program, the unchanged ffmpeg-static GPLv3 build**, with the release's licence as `LICENSE.ffmpeg.txt`, listed in Settings → Licences from the resource folder.
- **Its source notice in `THIRD_PARTY_NOTICES.md` links upstream only** (FFmpeg's source and the ffmpeg-static release, which a test keeps on the pinned release); no source tarballs are attached, and every run of the release workflow checks the links (`bun run notice:links`).
  - Each GitHub release's notes carry the whole section after the changelog (`githubNotes`, `scripts/release-feed.ts`), read through `noticeSection` (`scripts/lib/notices.ts`), which the link check shares; `latest.json`'s notes, which the About page shows, keep the changelog only.
- **Built-in sounds, songs and fonts carry their credits in `THIRD_PARTY_NOTICES.md`** ([audio.md](audio.md), [fonts.md](fonts.md)).

## Deliberate limits

- **Programs aren't code signed** ([plans/release.md](../plans/release.md), code signing): macOS gets an ad-hoc signature only, and Windows none; only update files carry Opsis's minisign signature.
- **The macOS and Windows packages have never been built**: the static Qt, the editor's static link and the packages build natively there (`buildsNatively`, [toolchain.md](toolchain.md)), but no run of the release workflow has happened, so the first one is where they meet a real Mac and Windows runner ([plans/release.md](../plans/release.md) section 2).
- **A macOS package needs macOS 14.4 or newer** (`MACOS_MINIMUM` in `crates/packager/src/app.rs` and `scripts/lib/static-qt.ts`, kept equal by `static-qt.test.ts`): the oldest macOS Qt 6.12 runs on, and the deployment target the static Qt and the release build are compiled for.
- **The Windows release program is a GUI program** (`windows_subsystem` in `crates/ui/src/main.rs`, release builds only), so starting it opens no console window; a debug build keeps its console for the log.
- **The MSI has no installer pages of its own**: it shows Windows Installer's basic progress, since a WiX dialog set needs a licence page in RTF; it is the package for administrators deploying it.
- **The Windows program has no embedded icon**: shortcuts and Add/Remove Programs use `opsis.ico` beside it.
- **The notices of the crates and npm packages compiled into the app are deliberately not shipped.**
