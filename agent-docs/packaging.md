# Packaging and licences

How a release build and its installers are made, what they ship, how update files are signed and listed, where the app reads its resources, the app icon, and the licence rules for dependencies, vendored code and the bundled FFmpeg. Paths are relative to the repository root. The engine and FFmpeg at run time are in [engine.md](engine.md), the app's side of updates in [updates.md](updates.md); see also [AGENTS.md](../AGENTS.md).

## Rules

### Building

- **`bun run make` runs `bun run stage`, builds the release binary against the static Qt, then `opsis-packager` builds the installers into `~/.cache/opsis-dev/build` (`buildAndPackage`).** It builds the deb on Linux, the macOS app and dmg on macOS, NSIS and MSI on Windows; `--formats` names others from `deb`, `rpm`, `appimage`, `pacman`, `nsis`, `msi`, `app` and `dmg`, and the remaining arguments go to `cargo build`.
- **Each installer is made by its format's own documented tool, which `opsis-packager` runs**: `dpkg-deb` (zstd), `rpmbuild` (zstd payload), `makepkg`, `appimagetool` with the AppImage runtime, `makensis`, WiX v7's `wix build`, and on macOS `iconutil`, `codesign`, `tar` and `hdiutil`. A tool that isn't on the PATH fails the build by name.
  - Linux's tools come from Debian, installed in the trixie container (`PACKAGES` in `trixie.ts`); appimagetool and the AppImage runtime are downloaded pinned by sha256 into `~/.cache/opsis-dev/appimage-tools` (versions and pins in `appimage-tools.ts`).
  - The Windows runner downloads NSIS pinned by sha256 and installs WiX with `dotnet tool install` (`NSIS_URL` and `WIX_VERSION` in `.github/workflows/release.yml`); `wix build -acceptEula wix7` accepts WiX's Open Source Maintenance Fee EULA, which charges only above US$10,000 of yearly revenue.
- **On Linux the release binary and its packages always build in one plain `debian:trixie` container run, into `target/trixie`, in CI too**, because linking the static Qt needs X11 and xcb development files a desktop doesn't have, the AppImage bundles libraries from the system that builds it, and Ubuntu has no `makepkg`; the program then needs glibc 2.41. On macOS and Windows, `CI=true` builds on the runner into `target/release`. The container runs as your user, with the repository, Cargo, rustup, Zig, both Qt folders and the AppImage tools mounted at their own paths.
- **The static Qt is built only on Linux** ([toolchain.md](toolchain.md)), so the release workflow's Windows and macOS jobs can't build yet ([plans/release.md](../plans/release.md) section 2).
- **Every package's program is a copy marked with that package's installer** (`marked_program`): the release program holds a 32-byte marker, `opsis-installer:unmarked`, exactly once, and the packager overwrites it with its installer's name (`app` for both the app and the DMG, which share one marked program) before the format's tool sees the program.
  - A program with no marker, or with two, fails the build, so a stale or foreign binary can't be packaged.
  - On macOS the marked program is signed again (ad hoc) afterwards, since patching breaks the linker's signature.
- **Update files are signed when `OPSIS_UPDATE_KEY` (with `OPSIS_UPDATE_KEY_PASSWORD`) is set** (`sign_update`): the AppImage, the NSIS installer, the MSI and the macOS `.app.tar.gz` each get a minisign `.sig` and a `.update.json` naming the feed key (`{os}-{arch}-{installer}`), the file and the signature.
  - The key is the base64 minisign box the git-ignored `signing/opsis.key` holds, encrypted with the password; `bun` reads both from the ignored `.env`, CI from the repository's secrets, and the container gets them by name only (`passEnv` in `trixie.ts`), never on a command line.
  - The deb, rpm and pacman packages aren't signed: they can't replace themselves, so the app sends their users to the release page.
- **A `v*` tag drafts the release** (the `draft` job, which runs on tags only; a run started by hand builds the packages as artifacts and drafts nothing): `release-feed.ts` merges the `.update.json` files, refusing any count but `SELF_UPDATING_KEYS`, into `latest.json` with the version (which must match the tag) and that version's section of `CHANGELOG.md`, and `gh release create --draft` uploads every package with it. A person publishes the draft after the release test pass; until then `releases/latest` still serves the previous feed.
- **`opsis-packager` refuses a program that loads Qt, ICU or KDDockWidgets, or looks for libraries in an absolute folder** (`check_self_contained`), so a development build can't be packaged.
- **Every Linux package installs the same files**: the programs in `/usr/bin`, the resources in `/usr/lib/opsis`, the desktop entry and the hicolor icons, all staged by `stage_linux`; the AppImage's AppDir holds the same tree under `usr/`. `tests/packages.rs` compares the deb's, the rpm's, the pacman package's and the AppImage's files and checks each program's marker; the deb test runs everywhere, the others in the container (`bun run packager:test`).
- **Package dependencies come from the libraries the program loads**: `linux_deps.rs` names each one's deb and pacman package, the rpm requires the libraries themselves, and every format also needs `ca-certificates` for the downloads the app makes when asked. A library with no entry fails the build.
- **`bun run package:check` installs each Linux package from `~/.cache/opsis-dev/build` in a plain `debian:trixie` container, the way its format installs, and runs the installed program through the `views` scenario on the offscreen platform**: the deb with apt (and again without CA certificates), where the installed program also opens the changelog example and exports it through the Local API with the dev engine and the bundled FFmpeg reads the video back, the rpm with `rpm` into a separate root, the pacman package with `pacman` (Debian's `pacman-package-manager`), the AppImage with only the system libraries it leaves out.
- **The AppImage bundles every library `ldd` finds for the program except the base system's and those left to the system with everything they load** (`LEFT_TO_THE_SYSTEM` in `appimage.rs`).
  - The bundled libraries go in `usr/lib` with the runpath `$ORIGIN`, and the program gets `$ORIGIN/../lib` (`patchelf`), so nothing changes `LD_LIBRARY_PATH` for the shells and programs Opsis starts.
  - `APPIMAGE_SYSTEM_PACKAGES` in `package-check.ts` installs the deb packages of those libraries, so the installed AppImage fails the check when a library is neither bundled nor there; nothing compares the two lists themselves.
  - appimagetool and the AppImage run unpacked in a container (`APPIMAGE_EXTRACT_AND_RUN=1`), since there is no FUSE.
- **Windows installs the program, FFmpeg, the resources and `opsis.ico` (written by `ico` from `brand/icons/`) in one folder.** The NSIS installer installs per user into `%LOCALAPPDATA%\Programs\Opsis` without asking for administrator rights; `/P` makes it passive (no pages, closes itself), which is how an update runs it. The MSI installs per machine into Program Files, with a major upgrade replacing an older version. A test keeps the NSIS uninstaller's list in step with the files the installer places.
- **macOS packages are the `.app` (the program and FFmpeg in `Contents/MacOS`, the resources in `Contents/Resources`), its `.app.tar.gz` for updates, and the DMG for first installs.**
- **`bun run make` caps cargo at 8 jobs unless `CARGO_BUILD_JOBS` sets another number** (`scripts/lib/release.ts`), in the container too.
- **There is one build: it ships FFmpeg as a program beside the app and never the recording browser.**
- **`stage.ts` empties `resources/`, builds the film and terminal pages without source maps**, writes the browser's Chromium credits into the gitignored `resources/engine-licences/LICENSES.chromium.html`, and stages FFmpeg again.
  - The credits are read from `chrome://credits` through `playwright-core`, in Chrome for Testing of the version `install-engine` downloads into `~/.cache/opsis-dev/stage-engine`, unpacked with `@zip.js/zip.js` into `~/.cache/opsis-dev/chromium-credits` keeping the macOS app's symlinks and executable bits.
  - FFmpeg is staged for the host target (`rustc -vV`) as `target/ffmpeg/opsis-ffmpeg-<target triple>[.exe]`, checked against the pins, with its licence as `resources/LICENSE.ffmpeg.txt`.
- **A release build finds FFmpeg beside its own program as `opsis-ffmpeg`, never `ffmpeg`**, so a package can't clash with the distribution's `ffmpeg`; a debug build takes `OPSIS_FFMPEG`. The app starts it with its own process code.
- **Release builds use `opt-level = 3`, full LTO and one codegen unit, and are stripped**; expect a slow, memory-heavy link.
- **The app reads its resources from the folder of its program, from `../lib/opsis` when `THIRD_PARTY_NOTICES.md` is there and not beside the program (every Linux package and the AppImage), or from `../Resources` on macOS (`resources_for`)**: the film page (whose `public/` files are the app's only copy of the `app:` files), the terminal page, `engine-licences`, `LICENSE.ffmpeg.txt`, `LICENSE`, `THIRD_PARTY_NOTICES.md`, `QT_NOTICES.generated.md`. In development everything comes from the repository.
- **CI is two workflows**: `.github/workflows/build.yml` checks every push (typecheck, lint, format, tests, the `wayland` scenario, `opsis-vt` in a release build and the FFmpeg capability test in one job, the other e2e scenarios in another) and builds no installer; `.github/workflows/release.yml`, on `v*` tags and by hand, checks the source notice's links, builds each platform's installers, runs `package:check` on the Linux runner only, and drafts the release on tags.
- **Check both workflows with `actionlint` after changing them.**

### Icons

- **`brand/logo.svg` is the one source for the app icon.** `bun run brand:icons` renders `brand/icons/` with the recording browser (ImageMagick draws the gradients wrong).

### Licences

- **Opsis is GPL-3.0-or-later.** `LICENSE` is the official GPLv3 text from gnu.org, unchanged; the "or later" is declared in `package.json` and `Cargo.toml`.
- **Every dependency must be GPLv3-compatible**: MIT, MIT-0, BSD-2-Clause, BSD-3-Clause, 0BSD, ISC, Zlib, Apache-2.0 with or without the LLVM exception, BSL-1.0, bzip2-1.0.6, CC0-1.0, IJG, Unicode-3.0, Unlicense, MPL-2.0 without the "Incompatible With Secondary Licenses" notice, GPLv3, LGPLv3.
  - `cargo deny` (`bun run lint:deny`) checks the crates against `deny.toml`'s `allow`, which lists only the licences crates use; nothing checks npm packages, so a new one's licence is checked by hand.
- **Qt and KDDockWidgets are used under the GPL-3.0, and a release links them statically, with Qt built without ICU**: in the spike the static build without ICU was one program with no Qt or ICU files beside it, and it started at 112 MiB of memory against 192 MiB with shared Qt; development builds link the prebuilt shared Qt ([toolchain.md](toolchain.md)). Their notices, and the MIT ones of the libraries KDDockWidgets compiles in, are in `THIRD_PARTY_NOTICES.md`; `QT_NOTICES.generated.md` holds the notices of the third-party code compiled into the Qt modules and plugins the program links, read from the static Qt's bill of materials; run `bun run qt:notices` again whenever Qt or `build.rs`'s modules and plugins change.
- **`deny.toml` holds the crate allow-list, worked out for the shipped platforms only** (its `targets`), so a licence only another platform pulls in never counts. It also denies yanked crates.
- **An advisory with no safe upgrade is an `ignore` entry with a `reason` saying where the crate comes from**, reviewed whenever dependencies move.
- **Vendored code and the icon data copied from the six glyph sets keep their notices**; `glyphs:bundle` refuses a set whose notice is missing.
- **FFmpeg ships as a separate program, the unchanged ffmpeg-static GPLv3 build**, with the release's licence as `LICENSE.ffmpeg.txt`, listed in Settings → Licences from the resource folder.
- **Its source notice in `THIRD_PARTY_NOTICES.md` links upstream only** (FFmpeg's source and the ffmpeg-static release, which a test keeps on the pinned release); no source tarballs are attached, and every run of the release workflow checks the links (`bun run notice:links`).
- **Built-in sounds, songs and fonts carry their credits in `THIRD_PARTY_NOTICES.md`** ([audio.md](audio.md), [fonts.md](fonts.md)).

## Deliberate limits

- **Programs aren't code signed** ([plans/release.md](../plans/release.md), code signing): macOS gets an ad-hoc signature only, and Windows none; only update files carry Opsis's minisign signature.
- **The macOS and Windows packages are built only in CI, and can't be until the static Qt builds on those platforms.**
- **The MSI has no installer pages of its own**: it shows Windows Installer's basic progress, since a WiX dialog set needs a licence page in RTF; it is the package for administrators deploying it.
- **The Windows program has no embedded icon**: shortcuts and Add/Remove Programs use `opsis.ico` beside it.
- **The notices of the crates and npm packages compiled into the app are deliberately not shipped.**
