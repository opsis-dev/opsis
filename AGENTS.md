# Working on Opsis

Read `README.md` for what the app does and `plans/` for planned work. This file is about changing it.

## Hard rules

**No comments. Any kind. Anywhere.** No `//`, `///`, `//!`, no `/* */`, no JSDoc, no file headers, no CSS comments, in source, tests, scripts and config, in TS and in Rust. If something needs explaining, the name is wrong or the function is too big; constraints that span the codebase go in this file. The only allowed comment-shaped lines are functional directives: `oxlint-disable…`, `/// <reference …>`, `@ts-…`; Rust attributes (`#[allow(…)]`, `#[cfg(…)]`) are not comments. Check:

```bash
rg -n '^\s*//|/\*|\*/' --glob '*.{ts,tsx,mts,css,rs}' apps packages crates scripts e2e *.config.ts -g '!packages/video/src/elements/**' -g '!packages/video/src/lib/**' -g '!packages/video/src/hooks/**' -g '!apps/ui/src/components/**' -g '!apps/ui/src/routeTree.gen.ts' -g '!e2e/node_modules/**' -g '!**/generated/**' | rg -v 'oxlint-|/// <reference|@ts-|"[^"]*(/\*|\*/)[^"]*"|/\\s\*'
```

**File names are kebab-case** in TS (`trace-panel.tsx`, `keycap-hud.tsx`), like the shadcn components; the code inside keeps its usual names (`TracePanel`). oxlint enforces it (`unicorn/filename-case`); the only exception is TanStack Router's `__root.tsx`. Rust module files are snake_case, because a module name must be an identifier. To rename a TS file, use the TypeScript rename edits (`getEditsForFileRename`, what VS Code calls on file move) so imports follow, then search for the old name in strings, configs and docs.

`fixtures/**` holds golden files: what the code made for fixed inputs, stored with those inputs (compile results, node, settings and problem cases, the catalogue, FFmpeg arguments, filter and mix graphs, analysis, probes, capture tables, the TodoMVC take, the 3D text typefaces and 3D element stills, and the hashes of a few renders), plus test models with the counts Google's Draco decoder reads from them. When a change is intended, record them again with `OPSIS_WRITE_GOLDEN=1` (`cargo test -p <crate>`, plus `-- --ignored` for the ones that need the dev engine, the video bundle or the internet) and review the diff; never edit them by hand.

Fixes to installed registry elements are unified diffs in `scripts/registry-patches/<element>.patch` (`<registry>-<element>.patch` when two registries share the name, one patch per element folder): edit the installed file, save `git diff` of it, and put a line before the diff saying why. The ingest applies every patch after installing (`applyPatches`, with the `diff` package), leaves an applied one alone and fails when one no longer fits the element.

One documented exception in `apps/ui/src/components/ui`: `DropdownMenuContent` (`dropdown-menu.tsx`) and `TooltipContent` (`tooltip.tsx`) take a `container` prop and pass it to their `Portal`. Dice UI's media player (`media-player.tsx`) needs it, and its docs list adding it as a prerequisite: in full screen it portals its menus and tooltips into the player, because only the full-screen element shows. Without the prop, the media player fails the type check. shadcn's own versions don't have it, so after `shadcn add dropdown-menu`/`tooltip --overwrite`, add it again (an optional prop, nothing else changes). When installing a Dice UI item, answer no to overwriting these two.

**Dependencies go through the package managers.** `bun add`, `bun add -d`, `bun remove` for TS, `cargo add` / `cargo remove` for Rust; never edit dependency blocks by hand. Always the latest release, except:

- every `remotion` / `@remotion/*` package is pinned to the same exact version (`bun add --exact`); mismatches break silently;
- `typescript` is pinned to `6.0.3` until TypeScript 7.1. Remotion's esbuild loader reads `tsconfig.json` through `typescript.sys`, which TS 7.0 does not expose, and the Remotion bundle then compiles with the classic JSX runtime. Do not patch around this; upgrade when 7.1 ships;
- `specta` is pinned to `=2.0.0-rc.26` and `specta-typescript` and `specta-serde` to `=0.0.13`: `tauri-specta` 2.0.0-rc.26 requires `specta =2.0.0-rc.26` and the 0.0.13 line of the other two, so any of them moving alone breaks the build; move all four together;
- WebdriverIO stays on 9.x (`webdriverio`, `@wdio/*` in `e2e/`): `@wdio/tauri-service` 1.5.1 and its embedded driver need `webdriverio ^9`.

**Tooling:** bun is the package manager; scripts run on Node through `tsx` (`tsx scripts/x.ts`), so they import TypeScript without file extensions like the rest of the code. Only the sidecar runs under Bun's runtime (`bun run apps/sidecar/src/main.ts`, started by `opsis-render`). The app is Rust (Tauri 2) and the editor runs in the system webview: WebKitGTK on Linux, WKWebView on macOS, WebView2 on Windows. Every tool config is a `*.config.ts`. `bun start` runs `tauri dev` in `crates/desktop` (it builds the preview page and serves the editor first); exports also need the prebuilt video bundle, `bun run video:bundle`, made again whenever `packages/video` changes. `OPSIS_USER_DATA` moves the app's data folder (default `<config dir>/Opsis`), for tests and side-by-side runs.

**Workspace.** A Bun workspace run by turbo (`turbo.json`) next to a Cargo workspace (`Cargo.toml`, members `crates/*`, `Cargo.lock` at the root). Apps build things and nothing imports them: `apps/ui` (`@opsis/ui`, the editor, a Vite app with its own `vite.config.ts` and `index.html`), `apps/preview` (the preview page the headless shell loads) and `apps/sidecar` (`@opsis/sidecar`, Remotion renders). The end-to-end suite, `e2e/`, is not in the workspace: it has its own `package.json`, `bun.lock` and `node_modules` (`bun install` inside it), extends `tsconfig.base.json`, `scripts/lib/oxlint-base.ts` and `scripts/lib/oxfmt-base.ts` by path, and is checked only by its own `typecheck`, `lint` and `format` scripts; the root checks skip it. `packages/video` (`@opsis/video`) is source the apps compile: the Remotion root, the registry elements and the helpers both the video and the editor use (`src/common`). Each declares the dependencies it imports (`bun add` inside its folder) and has its own `tsconfig.json` (extending `tsconfig.base.json`), `vitest.config.ts` (`scripts/lib/vitest-base.ts`) and `oxlint.config.ts` (`scripts/lib/oxlint-base.ts`); root scripts run each check everywhere plus the root's own (`typecheck:app`, `lint:app`, `test:app` cover `scripts`). Installs are bun's default isolated layout: a folder can only import what it or the root declares, and scripts read a package's files from the package that owns it. Workspace members import each other only by package name and through their `exports` (`@opsis/video/common/*`, `@opsis/video/generated/spec`, `@opsis/video/root`…). A member imports its own files through its `package.json` `imports` with its own prefix, `#video/…`, `#sidecar/…`, never `#/` (Rspack rejects it); `sidecar` is all `.ts` and imports without extensions, `video` mixes `.ts` and `.tsx` and imports with them (`#video/core/frame.tsx`), and its vendored registry code keeps upstream's own relative imports. Only the editor uses `@/` (`apps/ui/src`), since no other build compiles it; oxlint rejects `@/` in `video`, whose `tsconfig.json` keeps the alias only so the registry ingest's shadcn run can place files.

Rust crates live in `crates/<domain>`, named `opsis-<domain>`, one domain each; nothing Rust lives in `apps/`. `opsis-types` holds every shape that crosses a boundary; `opsis-compile` node definitions, settings, compile, cards, validation, the Inspector context, the timeline flattener, chapters, the mix plan and the catalogue; `opsis-store` the app database (`schema.sql` and the queries on it), settings, view state, recent projects, window bounds, the font rows, the keyring key and sealed sign-ins; `opsis-project` project folders (create from `templates.json`, open and save with versions, watching with `notify` through `notify-debouncer-mini`, asset and model import with `gltf`, file stamps, the last run); `opsis-fonts` the font library (`wuff` unwraps WOFF and WOFF2, `skrifa` reads names, weights, italics and axes), the computer's fonts (`fontdb`) and online fonts; `opsis-engine` the engine paths, the installer (downloads checked against the pinned sha256 and size), the tool helpers (version, file stamp and hash, `EngineFiles`), licences, child temp folders, the file server (`ServeDir`) and the file and hash helpers; `opsis-traces` the trace store; `opsis-runner` the run (plan, cache keys, saved results, run events and progress); `opsis-media` FFmpeg (argument builders, runs and probes behind the `MediaTools` trait so tests can fake them), the media executors, mix stems with their levels (`hound`) and loudness (`ebur128`), and waveform and filmstrip analysis; `opsis-render` the sidecar protocol and client, the saved pictures, the output executors and Export as code; `opsis-prepare` the prepared files (see Prepared files); `opsis-image` the image nodes on `image`, `fast_image_resize`, `imageproc` and `moxcms`; `opsis-capture` the recording browser over CDP (`chromiumoxide`): sessions, selectors, actions, the screencast encoder, sign-in steps and stills; `opsis-stream` the streamed views (preview, sign-in, element picker); `opsis-api` the Local API; `opsis-desktop` the Tauri app that composes them: windows, menus, commands and events, the exit flow, the file server for the editor. `opsis-golden` is a development dependency only: the golden-file helper the tests share. Only the desktop crate opens windows or dialogs. Node settings are Rust structs with `serde` defaults and `schemars` attributes (field metadata as `x-` keywords, our own checks as `x-check`), validated with `jsonschema`; registry elements are the ingest's JSON.

**Verify with** `bun run typecheck`, `bun run lint:fix`, `bun run format:fix`, `bun run test`. Rust runs inside them: `lint:fix` runs `cargo clippy --workspace --all-targets -- -D warnings`, `format:fix` runs `cargo fmt --all`, `test` runs `cargo test --workspace`. The `:fix` variants fix and report the rest; do not run the non-fix variants first. TS tests are `*.test.ts` on Node (in each package's `src`, the apps' `src` and `scripts`); a test that renders React components or hooks is `*.test.tsx` and runs in happy-dom with Testing Library (the two `projects` in `scripts/lib/vitest-base.ts`). The editor's tests read the catalogue and compiled films from Rust through the `editor-data` binary (`crates/compile/src/bin/editor-data.rs`), which their global setup builds in release. Tests that need the dev engine or a built page are `#[ignore]`d with the reason (`cargo test -p <crate> -- --ignored`); the render ones also need a video bundle named by `OPSIS_VIDEO_BUNDLE`.

**End-to-end tests** (`bun run test:e2e`: `e2e:app` builds the app with the `e2e` feature, then `e2e/` runs; run `bun install` in `e2e/` once) drive the real app through WebdriverIO and `@wdio/tauri-service` with its embedded driver: `tauri-plugin-wdio-webdriver`, compiled in only with the `e2e` Cargo feature, which refuses to build without debug assertions (`compile_error!` in `crates/desktop/src/lib.rs`) and adds the `wdio-webdriver` capability (`crates/desktop/capabilities/e2e`, picked by `build.rs`). The build goes to `target/e2e` so `cargo test` never overwrites it. The tests run in a virtual display only: `xvfb-run` with `WAYLAND_DISPLAY` unset and `GDK_BACKEND=x11` (otherwise GTK opens the window on the desktop's Wayland display), and `wdio.conf.ts` and `src/close-check.ts` refuse to start without that. Never open a test window on the real screen and never move the real pointer. Each run gets a fresh data folder in `~/.cache/opsis-e2e` (`OPSIS_USER_DATA`, the database seeded with the API on and the dev engine's three programs as `settings.engine` paths, which the app checks at start, `examples/` copied); specs that record or export wait for that check (`engineReady`); failure screenshots go to `~/.cache/opsis-e2e/failures`. The close check runs on its own after the suite, because closing the app ends the driver.

**Do not commit or push.** Leave changes in the working tree unless asked.

**Large files go to `~/.cache/opsis-*`** (browser binaries, clones, renders, release builds); `/tmp` is for small scripts and screenshots only. Long-running processes start with `run_in_background`.

## Invariants that must not regress

**Runtime boundaries.** `packages/video` is compiled by the editor (its `common/` helpers and generated types), by the preview page and by the video bundle the sidecar renders with: no `node:*`, `playwright-core`, `@remotion/renderer` or `@remotion/bundler` there (oxlint enforces it). Node-only code lives in `apps/sidecar` and `scripts`; everything else that touches the system is Rust. Element metadata (`registry.generated.json`) never names a component; implementations are keyed separately in `packages/video/src/registry`.

**Rust is the source of types.** Every shape that crosses a boundary (commands, events, the timeline spec, run events, the sidecar's messages) is a Rust type, exported with specta (`bun run types:export`) into `apps/ui/src/generated/bindings.ts`, `packages/video/src/generated/spec.ts` and `apps/sidecar/src/generated/protocol.ts`; tests fail when an export is stale. Never write such a type by hand in TS. JSON Schema for the Inspector and the Local API comes from the same types (`schemars`).

**Numbers and errors are typed.** Whole numbers are integers: frame lengths, sizes, frame rates, counts and settings in milliseconds are `u32`, a sound's start (which can fall before its clip) `i32`, timestamps `i64` milliseconds since the epoch; only values that can be fractional (positions in a remapped clip, action times, volumes, rates) are `f64`. Rounding a float into a whole number goes through `opsis_types::numbers` (`whole`, `whole_signed`, `signed`), and widening uses `f64::from`, never `as`. Kinds that form a fixed set are enums (`BrowserAction` for the steps of a browser session, `Sign` for linked settings), and node types the code names are constants next to their definitions (`OPEN_BROWSER_TYPE`, `RENDER_TYPE`). Core element props are built and read through their structs (`CoreElementProps`, `StillProps`, `PlaceholderProps`); only registry elements, whose settings come from data, stay JSON maps. Each module has its own error enum (`thiserror`: `SettingsError`, `CompileError`, `StartupError`…), turned into text only where it reaches a person or a JSON field, and a missing value falls back to a default only when the default is what it means.

**The sidecar only renders.** `apps/sidecar` runs `renderMedia` and `renderStill` for jobs Rust sends, one JSON message per line on stdin and stdout, and imports nothing from the other packages at run time. stdout is only for messages: `console.*` and `process.stdout.write` go to stderr, which Rust writes to the app's log. When stdin closes it cancels its jobs and exits; a crash fails the jobs in flight and the next job starts a new sidecar.

**Every animation in `packages/video` is a pure function of `useCurrentFrame()`.** No Framer Motion, `motion`, GSAP, CSS transitions or Tailwind `animate-*` (oxlint: `no-restricted-imports`, `opsis/no-animate-class`). Randomness uses `random(seed)`; async work uses `delayRender()`.

**Nodes never generate Remotion code.** A node definition (`crates/compile/src/nodes`, built with `NodeDef` in `node.rs`) has ports, settings and an optional pure `compile`; executors are keyed by node type (`opsis-media`, `opsis-render` and `opsis-capture` each register theirs). Every node with `executes: true` has an executor (`crates/render/tests/executors.rs`). Compile produces a `TimelineSpec`; the single `DemoTimeline` composition renders it in both the streamed preview (`apps/preview`) and the sidecar's `renderMedia()`, so preview equals render. Every timeline item has a `kind`: `group` and `recording` items carry typed props (`GroupProps`, `RecordingProps`, `crates/types/src/timeline.rs`) and are drawn by kind, `element` items name a registry `component`; read them by narrowing on `kind`, never by component name. The spec schema is recursive (a group holds tracks of items), so the Remotion root passes no `schema` to `<Composition>`: Remotion stringifies the composition list before every render, and a recursive schema makes every export and still fail.

**Nodes pass resources forward.** Every port carries a resource (`PortType`, `crates/types/src/workflow.rs`: browser session, recording, recording style, grade, clip, sound, captions, image, file, file info, folder), and an output connects to an input of the same type or one the conversion table turns it into (`conversion` and `can_connect` in `crates/compile/src/ports.rs`), lossless and settings-free only (an image or a recording is a file). `gather_inputs` (`crates/compile/src/compile.rs`, also the runner's inputs in `crates/runner/src/context.rs`) converts every value with `convert_input`, so a node always receives the type its port declares; anything that needs choices (fit, length, volume, start) is a node. Export nodes take a `clip`, and `compile_workflow` fills `specs` from it.

**Browser nodes are virtual.** Open browser starts a `browser-session` value (`{ browser, steps }`) and every other browser node appends its own step (id, type, label and parsed, interpolated params) in `compile()`; a skipped one passes its input through, so it never enters the list. Record take and Screenshot read the session at their `session` input and play `steps` as given, in one take. The video starts at the first Start recording step; the steps before it run off camera, and without one it starts with the first step. Nothing walks the graph backwards to find a chain: the element picker and the Run page script warning read the compiled session too.

**Recording style is a list too.** Style nodes (cursor, click ripple, keystroke chips, spotlight, highlight box, tooltip, callout arrow, follow cursor, skip quiet parts, backdrop, motion blur, window frame) are `recording-style? → recording-style` and append `{ nodeId, type, params }` (`style_modifier` in `crates/compile/src/node.rs`); Zoom here, Pan and Speed ramp need one take's frames and times, so they are `recording → recording` and append to the recording's own `style` (`recording_modifier`). Each gives its definition a `restyle` or `retime`, which `restyle_with`/`retime_with` (`crates/compile/src/style.rs`) apply. Auto zoom builds the props from its own fields, then applies the style's entries, then the take's own: the most specific wins. Apply style (`clip + recording-style → clip`) styles every recording in a clip, for takes joined in a Sequence or Layers.

**A colour grade is a list too.** Grade nodes (`crates/compile/src/nodes/grade.rs`: Colour and light, Look file, Black and white and tint, Texture, Lens, Auto fix) are `grade? → grade` and append `{ nodeId, type, params }` (`grade_modifier`); a skipped one passes its input through. Nothing converts into a `grade`. Each step's card row and neutral check come from one list of changes, so a card's "No change" and the empty filter always agree (`is_neutral_entry`). Apply grade (`media.applyGrade`, `file + grade → file`) turns the list into one filter graph (`grade_filters`, `crates/media/src/grade.rs`, pure and tested by string: steps that need no blend are joined with commas, a step below full strength splits and blends back, a look image is the next numbered input to `haldclut`, paths are escaped for the graph) and encodes once, so the sound is copied when the container holds it. Texture's dark-edges spot shows a frame of the file that reaches Apply grade (`graded_file`, `crates/compile/src/inspector.rs`). Picture look (`effect.look`) stays the live path; grade nodes are for a finished file.

**Params carry their own inspector UI** through `schemars` attributes on the settings structs: the label is the `description`, limits are ranges, and the rest are `x-` keywords: `x-help`, `x-widget`, `x-step`, `x-unit`, `x-accept`, `x-labels`, `x-zero-label`, `x-unconnected-zero-label`, `x-presets`, `x-presets-label`, `x-show-if`, `x-show-if-file`, `x-advanced`, `x-hidden`, `x-pauses`, `x-time-key`, `x-length-key`, `x-themes`, `x-frames-at`, and `x-check` for our own checks (`{ rule, message }`, such as the colour rule). The editor builds its forms from that JSON Schema (`apps/ui/src/core/schema.ts`, `editor/schema-form.tsx`); registry elements carry the same keywords from the ingest. `x-unit: "ms"` and `"frames"` are stored as-is and shown in seconds. Widgets: `textarea`, `code`, `asset`, `target`, `action` (an action node, for a sound placed on its mark), `timezone`, `keys`, `datetime`, `variable`, `backdrop`, `offsets`, `spot`, `quality`, `loudness`, `transition`, `multiselect`, `color`, `envelope`, `sound` (built-in sounds or a project file, with a play button), `font` (project, built-in and library fonts; picking a library font copies it into the project), `boxes` (areas drawn over a frame of the upstream recording, stored as fractions of the frame), `gradient` (a CSS gradient edited as straight or round with 2–6 draggable stops), `camera` (camera keys with time, easing, turn, tilt, distance and height, and "Add key at playhead"), `theme` (`{ mode, colors }`: a light/dark switch and the token colours of the preset in `x-themes`, only changed tokens stored). Widget names are listed in `FIELD_WIDGETS` (`crates/compile/src/elements/introspect.rs`, a test fails on any other, and the editor's list in `core/schema.ts`); a `spot` field keeps its y in `spotYKey(name)` and shows the frame at the time in its `x-time-key` setting, and a `target` field the picked element's role in `targetRoleKey(name)`. Rust sends what a form needs beyond the schema with every compile (`InspectorContext`: variables, layers, actions, the spot's frame, the picker's page, the project's colours, connected inputs). Plain text fields render variables as chips (`VarText`); never show `{{…}}` to a user. Fields write on every keystroke, so the Inspector wraps a focused text field in a gesture (`useTypingAsOneUndoStep`): typing until the field loses focus is one undo step. Lists pick their input from the item schema: text items a text list (Enter adds an item, pasting lines adds one per line), numbers a number list (pasting a spreadsheet column fills it), colours a palette, objects rows (each row is a nested form, so any widget works in a column; rows drag to reorder, duplicate and collapse); all of them honour the array's `minItems`/`maxItems` and drag through the Dice UI `Sortable`, one undo step per drop. The colour field (`form/color-picker.tsx`, our own, on culori) keeps the format a value is written in (`#hex`, `rgb()`, `hsl()`, `oklch()`, with alpha) and rewrites it only when the user picks; its popover is one gesture and offers the project's colours as swatches. `x-zero-label` on a colour, file or text field means empty is unset: compile drops the empty value (`map_leaves` in `element_props`, also inside rows and nested objects) and the field shows the label ("Theme", "Built-in image"); on an optional number (no default) it is the placeholder and clearing the field unsets it. `x-unconnected-zero-label` takes its place while none of the node's inputs is connected (a wrapper whose clip is optional plays its usual length alone). `x-show-if-file: { path: ["image"] }` shows a field only when that setting holds a file of that kind.

**Every value a user would want to change is a setting.** Colours, copy, content lists, images, visible sizes and weights, light or dark, and the length of a still are settings in the Inspector. Only timing the Timeline owns (`delay`, `holdSeconds`, `exitAtInFrames`…), animation tuning, functions and React nodes stay in code. Registry elements get settings through `scripts/registry-ingest.list.ts` (`SETTINGS`, `NEUTRAL_DEFAULTS`); every component prop the ingest reads (the props type, through `extends` and relative imports, plus every destructured default) must be a control, a fixed prop, a wrapper's output or in `omit` with a reason (`timing`, `function`, `react-node`, `internal` or `sound`, plus free text; global ones in `HIDDEN_PROPS`), or the ingest fails. It also fails on a required prop with no value, a control it can't write, rows without columns (columns come from the default rows, the element's row type and `columns`), a list control with no default, and library, company or product names in defaults (`namesLibrary`), including the text of hidden defaults and the constants they name. Colour lists named `…colors` become palettes, colour-named text settings become colour fields, and a colour with no default takes the component's own. On themed elements a colour the component falls back to a theme token for (`prop ?? t.token`) is empty ("Theme") by default unless its default differs from that token, so the theme switch reaches it. Prop wrappers in `packages/video/src/registry/framing.tsx` turn flat settings into what a component takes: `nested` (`nest`: flat keys into nested props), `listsFromRows` (`lists`: rows into one list per column, an all-empty column left out), `marksFromImages` (`marks`), `ticksFromWords` (`ticks`: yes/no cells), `treeFrom` (`tree`: paths into a file tree) and `themed` (`theme`: the mode and changed colours by prop for snapcn; for remocn the whole light or dark preset with the changed colours on top, since its components force light mode). A `sound` setting on an element (with `<key>Volume`) never reaches the component: compile turns it into a music item on the node's own Mixer channel (`element_sounds`), and the component's own audio props are omitted with `sound`. After an ingest, `bun run elements:render` (`crates/render/src/bin/render-elements.rs`) compiles every registry element with its defaults in Rust and renders its middle frame as a 480 px JPEG through the sidecar into `~/.cache/opsis-element-stills` (it needs the engine in the dev data folder and `bun run video:bundle`; it isn't part of `bun run test` because shaders need WebGL), and a test checks every element's defaults pass its own schema. Opsis's own video code keeps colour literals only for internal fallbacks a finished film never shows (the full-page styles' `PAGE_BG`/`BLEED_BG`, empty-clip placeholders), shadows and the window frames; `packages/video/src/colors.test.ts` lists each one with its reason and fails on a new one. The grain gradient element mounts its shader with the blob shape's `clamp` bounds in order (`shader-grain-gradient.patch`): the library's `clamp(0., 1., length(…))` is undefined, which graphics cards read as `min(1., …)` and Software drawing (export `gl: "swangle"`) as 1, so Grain dissolve drew no blobs there.

**Node cards.** Every visible node has a `description` and a `card` returning up to four `row(icon, text)` lines (`crates/compile/src/node.rs`), computed from interpolated params, run results, saved sign-ins and connected inputs (their lengths, takes, files, captions, session step types and style entry types); the editor shows the rows Rust sends with every compile (`cards`). Row icons are the `Icon` enum (`crates/types/src/cards.rs`, lucide names); `NODE_ICONS` in `apps/ui/src/editor/icons.ts` maps every one of them, so the type check fails on a missing icon, and `icons.test.ts` fails when an entry isn't the lucide icon of its name. A node's own icon is its look in `NODE_LOOKS` (`apps/ui/src/nodes/looks.ts`, one entry per node type, registry elements included): a stroke-only glyph (`lucide:<key>` or `tabler:<key>`, never a filled icon) and at most one hover animation, a `motion` from `NODE_MOTIONS` or a `morph` into another glyph. Animate a node only when the motion shows what it does (every transition and every text effect, the click, the drag, the morphs between two states); most nodes stay still. Two nodes may share a glyph only if they move differently (`looks.test.ts`). `NodeBadge` draws it (`node-glyph.tsx`): the glyph data comes from `node-glyphs.generated.ts` (run `bun run glyphs:bundle` after changing a look; it fails on aliases, typos and fills), morphs use `morphicons` with `reducedMotion="user"`, and motions are `motion` keyframes in `node-motions.ts` with the easing on each keyframe, played once when the node card or list row (`GLYPH_HOST`) is hovered and skipped under reduced motion. Cards show no picture: no stills, poster frames or live thumbnails; a node's output is seen in the Preview and Run panels.

**User-facing copy.** No library, tool or format names (Playwright, Remotion, Chromium, FFmpeg, CRF, DPR, page.evaluate…) in node titles, descriptions, field labels, badges, toasts or error messages; the exceptions are the Remotion licence notice (Settings and the first-run screen), which must name it, and Settings → Licences and About, which list what Opsis includes by name; technical settings go under `advanced`. Sentence case. Durations in seconds. Browser nodes are "actions", never "steps". Elements are described in words (`element_name`). The node's name (`node.label`) is also its camera, chapter and caption label. Categories keep their internal ids; display names come from `Category::label` (`crates/compile/src/node.rs`), sent with the catalogue. Registry element descriptions come from the registry item JSON at ingest time, with overrides in `DESCRIPTIONS` (`scripts/registry-ingest.list.ts`). Element defaults never name a library and never load from the internet: neutral copy and `app:` placeholders (`public/placeholders`, `public/backdrops`) go in `NEUTRAL_DEFAULTS` / `NEUTRAL_FIXED_PROPS`, and the ingest fails on any default that breaks this, for every registry. `crates/compile/tests/unit/nodes_c.rs` enforces descriptions and the banned words. Copy never names Tauri, Rust, Bun, CDP or any crate either.

**Editor panels.** The node list, Inspector and bottom panel collapse (Ctrl/Cmd+B, Ctrl/Cmd+Alt+B, Ctrl/Cmd+J, also in the View menu and the top bar); `apps/ui/src/editor/panels.ts` owns their handles, open state and the active tab, and layouts persist through `useDefaultLayout`. A collapsed node list becomes a 44 px category rail with popovers. The bottom panel is **tabs**, not a split row: Timeline, Mixer, Run (Ctrl/Cmd+1…3, `dock.tsx`), Timeline by default. Any tab opens in its own window (`open_panel_window`, `crates/desktop/src/windows.rs`, route `#/panel/<name>`, bounds saved in the app database); closing that window docks the tab back. The Timeline has its own clock and nothing else: `TimelineClock` (`apps/ui/src/editor/timeline/timeline-clock.ts`, mounted in the editor window) owns `usePlayback`, moves the playhead on animation frames at the shuttle rate, loops the film or the in and out points (`loopOf`/`wrapInLoop`, `apps/ui/src/core/playhead.ts`) and plays only the film's master stem (`StemPlayer`, `apps/ui/src/editor/stem-player.ts`: an `<audio>` through a Web Audio chain, kept within two frames of the playhead). Play and Space in the Timeline, the Mixer's meters, the camera field and the node rings all follow that playhead: the canvas rings the nodes whose span holds it (`activeAt` over the compiled `spans`, `setActive`) and the Timeline brightens the bars under it (`BarFrame`). Selecting a node moves the playhead to its start.

**The Preview is its own window, opened on demand.** The Preview button beside Run in the top bar (View → Preview, Ctrl/Cmd+Alt+P, `view:preview`) opens it (`open_preview_window`, route `#/preview`, label `preview`, bounds saved in the app database); it is not a tab, never docks and never reopens with a project. It mirrors the editor like a panel window (`useWindowSync`) but not the Timeline's playhead: it has its own player, clock and sound (`usePreviewPlayback`, `apps/ui/src/editor/preview-playback.ts`, and a `StemPlayer` of its own), and neither follows the other. Opening it starts the stream: the Player runs in the headless shell (`apps/preview`, `Preview` in `crates/stream/src/preview.rs`) and the window draws its frames on a canvas (`preview-player.tsx`, `useStreamedPreview` in `preview-stream.ts`). Closing it shuts the stream down (`preview_close`, and `Views::close_preview` when the window is destroyed), so nothing streams while it is closed. Its controls are ours (`preview-controls.tsx`: play, seek, time in the ruler's mode, volume, full screen of the view and its bar; the toolbar has Fast/Exact and the shape) and drive the page through the `preview_*` commands; the page reports its frame and whether it plays (`PreviewReported`), which `usePreviewPlayback` follows. Selecting a node seeks the preview to its start too. Videos and sounds in the Run panel and Replay play through Dice UI's media player (`file-player.tsx`), never the browser's own controls; images there open full size in a dialog on click (`image-preview.tsx`).

**View state is per project, on this computer.** The active tab, panel sizes and collapsed panels, timeline ruler and snapping, and Fast/Exact preview are saved in the app database's `view_state` table, one row per project and key. `open_project` returns the project's view with the workflow, and `loadViewState` puts it in the editor's cache (`apps/ui/src/store/view-prefs.ts`), which `readPref` and the panel layouts (`layoutStorage`) read synchronously; `writePref` updates the cache and sends `set_view_pref`, which Rust broadcasts as `ViewPrefChanged` so every window's cache follows, and panel windows get the cache in the sync `state` message. Nothing is saved while no project is open, and a project made again in the same folder starts with no saved view. A project with nothing saved opens with the defaults (Timeline tab). The main window's size and maximized state are saved per project too (key `mainWindow`, written by `crates/desktop/src/windows.rs` while a project is open, applied on open): a project with none saved opens maximized, and the start screen leaves the window as it is (1600×1000 at launch). Pop-out window bounds stay global.

**Starting and closing.** Settings → Starting and closing: on start show the start screen, open the last project, or open New project (once per app launch, `__root.tsx`); and "Ask before closing". Closing or quitting the main window goes through `crates/desktop/src/exit.rs`: it prevents the close and asks the editor to show `ExitDialog` (in-app, never a native dialog, `ConfirmClose`). With asking on: "Are you sure you want to exit?" with "Don't ask again". With it off, it only appears when work is unfinished (a run, engine setup, font download, unsaved changes, including a value still being typed in a field: `useHeldDrafts`), without the checkbox; flushing the save commits those values first (`commitHeldDrafts`). Unfinished work is always listed and the button becomes "Close anyway"; closing flushes the pending save and stops the run. Register new long app work in `AppState.tasks` (`begin(label)`/`end(label)`, `crates/desktop/src/state.rs`) so it's listed. The dialog answers `close_shown` as soon as it receives the request; if nothing does within 2 s (the window crashed or is showing an error), Rust saves and closes without asking, so a broken window can always close. Once a close is allowed, a window whose page dies or doesn't finish unloading within 3 s is destroyed (`close_even_if_page_dies`) and the quit goes on, so the app never waits on a dead page. Never hold a lock across a call that may take it again (the settings lock and `announce`, which reads the settings): a database lock held that way once hung the close. Render errors show `ErrorScreen` (`apps/ui/src/app/error-screen.tsx`, the router's `defaultErrorComponent`, so every route has its own boundary and the root, the exit dialog and the title bar stay up): the app bar, Try again, Reload window and the message under Details. Components that read a node by id must handle it being gone: the Inspector's fading-out panel renders once more after a delete.

**App state is one database.** `<data folder>/opsis.db` (SQLite through `sqlx` with the bundled SQLite, WAL, foreign keys on, `crates/store`) holds settings (one row per section), every project ever opened (recent projects are a query: newest first, folders that still hold a project, first 20), each project's view state, window bounds and the font library index. Only Rust opens it (`AppState::db()`, a pool, so every query is async); windows go through commands. The tables are `crates/store/schema.sql`, plain SQL with snake_case columns, which the store embeds and runs on an empty database. Every query is a checked `sqlx::query!`/`query_as!`/`query_scalar!` macro against that schema; `.sqlx/` at the root is the committed offline cache and `.cargo/config.toml` sets `SQLX_OFFLINE=true`, so builds need no database. After changing the schema or a query, run `bun run db:prepare` (it needs `sqlx-cli` built with SQLite). The settings also live in memory in `AppState` (read with `settings()`, written only through `AppState::patch_settings`, one patch at a time), so handlers that can't wait, like the close request, read them without a query. Setup spawns the start (`open` in `crates/desktop/src/lib.rs`): it opens the database, registers every piece of state at once and then opens the main window, so no command runs before the state exists, and a failed start logs why and exits. Nothing blocks on the async runtime; the keyring is the exception that is made in setup itself, because the Linux Secret Service store blocks inside `zbus` and panics on a runtime thread. There are no migrations: the `meta` table holds the sha256 of that SQL, and a database made for another schema is deleted and made again at startup. Real migrations come with the first release. Projects stay plain folders: nothing about a project's contents goes in the database. The editor keeps nothing in local storage. Secrets use the OS keyring (`keyring-core` with the Apple, Windows and Secret Service stores, `crates/store/src/keys.rs`): sign-ins are sealed with AES-256-GCM under one key kept there, and saving refuses when the platform has no secure store.

**Settings is its own window** (`open_settings`, `crates/desktop/src/windows.rs`, route `#/settings?page=<page>`, bounds in the app database), opened from the menu, Ctrl/Cmd+, and any Settings button; it closes with the main window. A sidebar picks the page (`apps/ui/src/app/settings/`). Its app bar has no menu; menu shortcuts pressed there go to the main window (the `relay` command). Settings are written with `patchSettings` (one section at a time, so windows never overwrite each other) and every window follows them through `useAppSettings` (`apps/ui/src/store/app-settings.ts`), which Rust keeps current with `SettingsChanged`. Saved results (clear cache) belong to the project, in the project Inspector.

**Projects folder.** New projects are suggested in `settings.projects.lastDir` (the last place one was created) or else the default folder: `settings.projects.defaultDir`, empty meaning `~/OpsisProjects` on every OS, like JetBrains' `~/IdeaProjects`. Changing the default clears `lastDir`. Open project starts in the default folder. The New project dialog shows the folder it will create (the `project_folder` command); started from a template card, it shows only that template with Change.

**The project file can change under the app.** `open_project` returns the file's `version` (a hash of its text), kept as `fileVersion` in the workflow store. Every save sends it (`save_workflow(dir, workflow, base)`, through `apps/ui/src/editor/save.ts`); Rust refuses to write when the file on disk has another version and returns that version instead. Rust watches the open project's file (`watch_project`; the folder is watched because saves replace the file) and ignores its own writes (`ProjectFileChanged`). With nothing unsaved the editor loads the outside change as one undo step and says so; with unsaved edits, or when a save is refused, `DiskChangeDialog` asks: Load the file (undoable) or Keep mine (saves over it). Nothing saves while that question is open. Always save through `save()`. The files a project names can change under it too: the editor sends the exact files it loads, every `project:` ref in the compiled values plus the project's font files (`useWatchLoadedFiles`, `projectRefsIn`), Rust watches those files (`watch_project_files`, never the app's own `.opsis` files), compiles again and sends every app window each changed file's size and modified time (`ProjectFilesChanged`). Windows keep them as file versions (`useProjectFiles`, keyed by `fileVersionKey`): specs carry them in `assets.versions`, so `resolveAssetRef` adds `?v=` to that file's address and every loader keyed by address (pictures, videos, Lottie, fonts, 3D models) loads it again; the preview, Timeline waveforms and filmstrips follow them. Renders never carry versions; their cache keys stamp files themselves.

**Local API.** Off by default; Settings → API switches it (`settings.api.enabled`, global and persistent, shown as an API badge in every app bar). `crates/api` serves plain HTTP with `axum` on `<data folder>/api.sock`, or the absolute path in `OPSIS_API_SOCKET` (mode 0600; a stale socket from a crash is replaced, a live one from another copy of the app is left alone and reported, and anything that isn't a socket is never deleted). Socket paths are capped at 100 bytes (`api_address`, `crates/api/src/address.rs`; the OS limits are 107 on Linux and 103 on macOS): a longer or relative path is refused before listening, and Settings → API says to set `OPSIS_API_SOCKET` to a shorter full path. There is no automatic fallback location. On Windows the variable is ignored and the API uses the named pipe `\\.\pipe\opsis-api-<user>`, never a TCP port (the current-user-only ACL is still to do, `plans/release.md`). Without an open project it answers `/openapi.json`, `/status`, `/nodes`, `/nodes/{type}`, `/validate` and `/open`. Under `/project`, reads come from Rust and edits go to the editor window as one typed `EditorRequest` (`crates/api/src/bodies.rs`; the editor's side is `apps/ui/src/editor/api-bridge.ts`), so each request is one store update: one undo step, autosaved, mirrored to other windows. Rust checks bodies, node types, connections and settings first and adds the problems to the editor's answer (`workflow_problems`), so the bridge holds no validation. `/open` waits until the new editor has registered (`setEditorApi`); a request waits until the editor window reports its listener (`api_listening`), up to 20 s, and a reload or a closed window answers the requests in flight at once. Run events also stream on `/project/run/events`. The OpenAPI document (`crates/api/src/openapi.rs`, from the `schemars` schemas of the bodies) stays small (a test keeps it under 100 KB and checks every route is documented); node settings schemas come from `/nodes/{type}`. Validation is `check_workflow`/`workflow_problems`, the same checks the editor shows. Routes live in `crates/api/src/routes.rs`; add an endpoint to `openapi.rs` whenever you add a route.

**Canvas.** `settings.editor.canvasMode`: `mouse` (the default: wheel zooms, drag pans) or `touchpad` (two-finger scroll pans, pinch zooms), chosen in the canvas toolbar and remembered for every project. The minimap shows or hides from the toolbar, View → Minimap or Ctrl/Cmd+Shift+M, per project (`minimap` view pref). The React Flow attribution is hidden (`proOptions.hideAttribution`); the library prints a console note asking for a Pro subscription when you do. The workflow store owns node positions and the UI store owns selection; React Flow's own per-node state (measured size, a drag or resize in progress) lives only in `useFlowNodes` (`apps/ui/src/editor/use-flow-elements.ts`), merged over the store's nodes, so a drag writes one position at drag stop instead of one undo step per frame. The node list's group titles stay pinned while their group scrolls (sidebar list only).

**Windows share one editor.** The editor window owns the project store and undo. Panel windows mirror it through Rust: `relay(to, message)` sends a message to another window as a `Relayed` event (`apps/ui/src/app/relay-channel.ts`, used by `sync.ts`): edits go back as `replace`/gesture messages (`mirrorEditsTo`), menu commands are forwarded, run events are relayed, and the Timeline's playhead runs in the editor window, which sends its frames to the panel windows while they forward play, pause and seek to it (`apps/ui/src/store/playback.ts`); the Preview window mirrors the project the same way but keeps its own playback. Compile results reach every window: the editor sends each change to `compile` and the other windows follow the `Compiled` event, after taking the latest result as the answer to `latest_compile` when they mount (an event sent before their listener is registered would be lost); a window drops a result older than the newest it has seen (`seq`). Live recording frames go to every window that watches them, each over its own `Channel` (`watch_live`). Commands and events are declared once in Rust (`crates/desktop/src/bindings.rs`, tauri-specta) and the editor reaches them through the `window.opsis` facade (`apps/ui/src/app/opsis.ts`); capabilities (`crates/desktop/capabilities`) let only the editor, its panel windows, the Preview, Settings and the streamed views call them. Engine set-up progress, settings changes and API status go to every app window.

**Timeline.** `flatten_spec` (`crates/compile/src/timeline/flatten.rs`, sent with every compile as `flat`, with each bar's clock for drawing frames, `clocks`) turns the compiled spec into bars on lanes (greedy packing in drawing order), audio bars, transitions and action marks, mapping frames through trims, loops and speed remaps. Edits never touch the spec: compile records `handles` (`move`, `trimStart`, `trimEnd`, `speed`, `volume` as `ParamRef`s) on items, and container children carry a `slot` (container node + port). `apps/ui/src/timeline/edits.ts` applies an edit to the owning setting or, when nothing owns it, inserts a named node ("Delay from timeline", "Trim from timeline", "Speed from timeline", split parts) at the slot edge or right after the clip. Every handle has a round-trip test in `edits.test.ts`; add one when a node gains a handle. Drags call `beginGesture`/`endGesture` so a drag is one undo step. Keyframes are an `envelope` setting (`crates/compile/src/envelope.rs`, frames local to the item) shown on the timeline and in the Inspector (`envelope` widget); they compile onto `TimelineItem.envelope`/`AudioItem.envelope` and stay pure functions of the frame.

**Mixer.** Mix settings are `workflow.mix` (`crates/types/src/mix.rs`): a strip per channel (keyed by node id: Music, each Sound effect, each clip with sound), buses (Music, Effects, Clips built in, plus user buses) with sidechain ducking, and a master with EQ, compressor, limiter and loudness target. `normalizeWorkflow` (`apps/ui/src/core/workflow.ts`) prunes channels of deleted nodes. `build_mix_plan` (`crates/compile/src/mix/plan.rs`) and the FFmpeg filter graphs (`crates/media/src/mix/graph.rs`, tested by string) are pure; `crates/media/src/mix/render.rs` renders channel, bus and master stems into `.opsis/cache/mix/` (content-hashed, recent plans kept), with per-frame peak/RMS, compressor gain reduction and EBU R128 loudness. Exports always play the master stem (`with_master_stem`): the render executor draws the picture once without sound into `.opsis/cache/pictures/<pictureKey>` (`crates/render/src/picture.rs`; the key leaves out the spec's audio, mix and asset address; recent pictures kept) and adds the master stem with FFmpeg (`mux_args`, `crates/media/src/codecs.rs`), so a mix or sound-only change never renders the picture again. Bump `PICTURE_VERSION` (`crates/engine/src/versions.rs`) whenever how a spec is drawn changes (anything in `packages/video` that the spec doesn't record): it keys the saved pictures and every render-phase node's cache key, so exports are made again. The Timeline and the Preview play the latest stem for their film (the Preview shows "Updating sound" while a new one renders); a stem player applies the mixer drags made in its own window at once through its Web Audio chain (`applyMixerDrags` in `stem-player.ts`), so the Timeline's sound follows a docked Mixer's drags before the new stem is ready. Mute and solo are saved and apply to exports. Strip selection is the editor's node selection (Ctrl/Cmd-click toggles, Shift-click takes the range in strip order); a strip menu on a selected strip applies to every selected strip in one `setMix` call, so it is one undo step. Bump `MIX_VERSION` (`crates/media/src/mix/render.rs`) when stem output changes.

**Run state.** Run events go through one reducer, `apply_run_event` (`crates/runner/src/progress.rs`), which keeps the active run's progress in Rust so `run_status` can return it, and its copy `applyRunEvent` (`apps/ui/src/core/run-progress.ts`) in the editor's run store; an editor that opens the project mid-run calls `resume(progress)`, never a fresh start. A run clears status, progress, errors and traces only for the nodes it includes (`run:start` `nodeIds`), so a **Run this** never hides an earlier failure; `run:done` names `failedNodeIds` and `skippedNodeIds` apart, and the panel shows each failed node as a link. The panel's exports list comes from the results of every `output.*` node, newest first (`exportedArtifacts`), not from the last run's `outputs`.

**Chapters in exports.** `film_chapters` (`crates/compile/src/timeline/chapters.rs`) reads the Chapter action marks from `flatten_spec`, starts the first at 0:00 (or adds an "Intro" chapter when the first starts 10 s or more in) and merges chapters under 10 s into the one before, YouTube's rules. Export video writes them as FFmpeg chapter metadata in the finishing copy (`finish_args`, with the web-ready move), so a chapter change never renders the picture again; GIFs get none. The optional `.youtube-chapters.txt` needs at least three chapters.

**Drag action.** `browser.drag` drags onto an element (measured again after the press, failing when it isn't on screen), by an offset, or along a path; the smooth method presses, waits `holdMs`, nudges 6 px (pages start drags past a threshold) and walks the points with the same 8 ms sampler as glides (pure curves in `crates/capture/src/drag_path.rs`; glides must keep their exact samples). The action logs `tDown`, `t` (the release), `path` (at most 64 points) and `drop`; `toClickLog` (`packages/video/src/camera/action-log.ts`) makes one camera event covering both ends when they fit in half the window, else a pick-up and a drop event, and `cursorAt` keeps the arrow pressed until `tUpMs`. The baked cursor follows `dragover` too. The picker's Shift-click returns a spot as `x, y`, in a window sized to the take's browser.

**One engine.** Capture, the streamed views and Remotion's renders launch the same Chrome Headless Shell: the build Remotion's pinned `TESTED_VERSION` names for the platform (Remotion's own build on Linux x64/arm64 and Apple Silicon, Google's Chrome for Testing elsewhere), pinned with FFmpeg and ffprobe (the ffmpeg-static GitHub release) by sha256 and size in `crates/engine/src/downloads.generated.json` (`bun run engine:downloads`). The app ships none of it. Settings store the three programs as paths (`settings.engine`: `browser`, `ffmpeg`, `ffprobe`, each with its version, sha256, size and modified time), and nothing else locates them: Settings → Engine either downloads them into `<data folder>/engine` (`crates/engine/src/install.rs`) and saves those paths, or saves a program the user chooses. Either way the same full check runs before a path is saved (`crates/desktop/src/engine.rs`): the browser answers `--version` and opens a page over CDP when started headless (`check_browser`, `crates/capture/src/browser.rs`); `ffmpeg` has every encoder, decoder, format and filter Opsis uses (`REQUIRED_*` in `crates/media/src/capabilities.rs`, a test fails when a golden filter graph uses one the list lacks); `ffprobe` reads a small WAV. A failed choice leaves the saved program as it was. At start each saved program's size and modified time are compared (`verify_on_start`); a changed one is hashed, and only a different hash runs the full check again, so a moved or replaced file shows as a problem in Settings. A browser of another version than the pinned one is allowed with a warning. `settings.engine` is written only by Rust (`RUST_ONLY_SECTIONS`, refused by `patch_settings`), and runs, views and analysis take the programs that passed (`engine_files`, `EngineFiles`). Never fall back to Playwright's browsers, the system Chrome or the webview for capture or render. Capture keeps Playwright's launch switches, injected page script, clock and keyboard (`crates/capture/src/playwright/*.generated.*`) but talks CDP itself; `playwright-core` is only a dev dependency for `bun run playwright:scripts`.

**Capture timing comes from frames, not markers.** Screencast JPEGs go into `FrameEncoder` (`crates/capture/src/encoder.rs`) through `offer`, which never waits: Chrome sends the next frame only after the last one is acknowledged, so waiting on the encoder loses any page change painted during an encoder stall. Encoder errors surface at `finish`. The encoder writes a constant-rate stream from the first frame after the setup steps; action timestamps share that origin. Live frames for the editor PiP are the same frames, throttled to the live fps setting, sent as raw bytes over a `Channel` to each window that watches them.

**Interactive browsing is streamed.** The element picker and Sign in are pages in the headless shell (`crates/stream`: `pick`, `sign_in`), streamed to a window of their own at route `#/view/<id>` (`StreamView`, `apps/ui/src/app/stream-view.tsx`): frames arrive as raw JPEG bytes over a `Channel`, mouse, wheel, keys and text go back as `view_input`, the page keeps its own size and the input is mapped through the letterboxing, and dialogs, file choosers and popups are answered from the window. Sign-in state is kept as storage-state JSON and sealed (see App state). Sign in (`browser.signIn`) is an ordinary executing node in the action chain: its executor opens the view, the size of the session's browser, only when the sign-in named in Save as isn't saved yet or the node is run on its own (`forced`), and its step in the take adds the saved cookies and, per origin, the page storage (an init script, plus the current page when it is that origin). `secret_params` on a node definition names the settings whose saved sign-in goes into the node's cache key (`sign_in_stamp`), so a new sign-in runs every take after it again; the runner works the keys out again as soon as such a node has run (`rekey`), so a take recorded right after a new sign-in is saved under its new key and the next run doesn't record it again. A take that lands on the Sign in step's address fails with "Signed out during the take. Run “<name>” again."; nothing retries across nodes. The sign-in finishes on an address change or a selector, in single-page apps too.

**Traces** are recorded per capture unless retention is `off`, in our own format (`crates/traces`): per take a zstd JSON manifest (header, viewport, actions with their node ids, console, page errors, requests) and its frames as content-addressed JPEG blobs in `.opsis/traces`, shared across runs and pruned by the retention setting. Blob files keep their extension (`<sha>.jpeg`) so screenshots load straight through the file server. The Trace tab in Replay (`TracePanel`) is our own shadcn UI over `read_trace`; never embed Playwright's Trace Viewer.

**Nothing uses the internet unless the user asks.** The app works offline. Anything that needs the network (setting up the engine, getting fonts online) sits behind a button and asks first, and what it downloads is saved locally (`<data folder>/engine`, `<data folder>/fonts`). Never load fonts, images, scripts or sounds from a remote URL at preview or render time. User-facing copy never names the services behind it.

**Fonts.** 16 families (Latin, all weights, italics where they exist, about 1 MB) are bundled from Fontsource into `public/fonts/bundled`. The user's library lives in `<data folder>/fonts` (the files, served by the file server under `fonts/`) and the app database's `fonts` table (one row per family; a row that no longer parses is kept as it is) and is filled from font files or ZIPs (`crates/fonts`: `skrifa` reads names, weights and italics, one file per style, variable and woff2 first), fonts installed on the computer (`fontdb`, `installed_font_families`), or Fontsource online. A project copies the library fonts it uses into `assets/fonts/<id>/` and lists them in `settings.fonts.families`, so it works anywhere. `settings.fonts` also holds the roles `main`, `heading` (empty = main) and `code`. In the video, `FontProvider` registers fonts through `packages/video/src/fonts/registry.ts`: `df-main`, `df-heading` and `df-code` point at the role fonts, `Inter` follows `main` and `JetBrains Mono` follows `code`, so every element follows the project fonts; per-node fonts (the `font` widget, stored as a family name, turned into a CSS stack by `fontStack`) load by name. Elements' `@remotion/google-fonts/<Name>` imports are redirected in every bundler (the `localFonts` Vite plugin in `apps/ui` and `apps/preview`, the Rspack hook in `apps/sidecar/src/bundler-override.ts`) to the generated modules in `packages/video/src/fonts/google/`, which load the bundled copy; `fonts:bundle` fails if an element imports a font that isn't bundled. Export cache keys include the project settings, so changing fonts re-exports.

**Element time and size.** remocn and snapcn elements (not their transitions, Spring settle or the two scene templates) count time on a clock of 30 frames a second: their patches read `useAuthoredFrame()`/`useAuthoredConfig()` (`packages/video/src/core/authored-clock.ts`) instead of Remotion's hooks, and a `<Sequence from>` inside them takes `useRealFrames()`, so a 60 fps project plays them at their own speed. Their timing settings counted in frames are listed in `SECONDS` (`scripts/registry-ingest.list.ts`): the ingest writes them as seconds with `framesAt: 30` in the field meta, and compile turns them back into frames (`frames_from_seconds`, also inside rows and comma lists). An element's Length defaults to 0, "Fit the animation", when `crates/compile/src/elements/lengths.rs` knows how its animation ends (`element_timing`, checked against the elements' own length helpers by `packages/video/src/registry/lengths.test.ts` through `length-cases.generated.json`) or when it runs on the 30 fps clock; `animation_length` keeps the designer's hold after the last animation. Elements laid out in fixed pixels carry a `design` size (`design: FULL_HD` in the ingest list) and draw in a box of that size scaled to fit the frame (`DesignBox`), so other shapes and 4K keep them whole and in proportion.

**3D elements** (`packages/video/src/three`, all in `LAZY_CORE_ELEMENTS` in `packages/video/src/registry/index.ts`, so three.js loads only when one is used) draw with `@remotion/three`'s `ThreeCanvas` through `Stage3D`, and every pose is a pure function of the frame: oxlint bans `useFrame` and `opsis/no-three-clock` bans three's clocks and animation loops. Model animations call `mixer.setTime`, never `update`. Assets load through `useHeldLoad`, which releases its hold only after the loaded value has rendered, so a still is never captured between a load and the canvas it mounts. 3D text, models, SVG logos and textures load prepared files (see Prepared files): the element only fetches an address. Model import copies a model's side files into `assets/models/<name>/` and refuses paths outside its folder or on the internet (`crates/project/src/model.rs`). The 3D screen shows its clip as a page layer placed with `matrix3d` from `project.ts`; with **End facing the camera** its last pose fills the frame exactly, so it cuts pixel for pixel to the same clip. Camera keys are the `camera` param, active when the element's motion or move is Keyframes; compile puts them on `TimelineItem.camera`, `flatten_spec` turns them into `cameraKeys` marks, and the Timeline moves them with `moveCameraKeyMark`.

**Picture look and Blur areas use `@remotion/effects`.** Both attach to a recording's page `<Video>`: Blur areas (`effect.blurAreas`, `recording → recording`, areas drawn on any frame of the take) stay on the page as the camera moves, and Picture look (`effect.look`, `clip → clip`) changes the page footage of a recording and the whole picture of a video or image, not a recording's window or backdrop. A blur that can't get WebGL must fail the export, never draw without the blur. The Mac cursor (`cursorLook.shape === "mac"`) reads the page's own cursor keyword while recording a synthetic cursor: once when a glide settles and after each click, stored as `c` on the cursor sample, keywords only (a `url()` cursor is never loaded).

**Prepared files.** Work the video would repeat in every render tab is done once in Rust (`crates/prepare`) and kept: 3D text typefaces (the face is picked in compile like the page picks it, then `wuff` and `skrifa` draw its outlines at the weight into three.js typeface JSON, checked against `fixtures/prepare/typefaces.json`), 3D models (`draco-gltf` decodes Draco and meshopt meshes into a plain GLB with every image packed in, so the page uses a plain `GLTFLoader`), SVG logos (flattened by `usvg`) and textures (images over 4096 px on the long side are made smaller; others are served as they are). Compile turns those settings into `prepared:<kind>/[weight/]<project|app>/<path>` refs (`PreparedRef`, `crates/compile/src/asset_ref.rs`; `prepare_props`), `resolveAssetRef` turns them into `.opsis/prepared/<path>` on the spec's project base, and the render and preview file servers answer that path (`prepared_routes`), preparing the file on first request into `.opsis/cache/prepared/<sha256 of the path, the source's size and time and PREPARED_VERSION>`. Export as code writes every prepared ref into its `public/project/.opsis/prepared/`. Bump `PREPARED_VERSION` (`crates/engine/src/versions.rs`) whenever a preparer's output changes: it keys the prepared files, the saved pictures and every render-phase node. `crates/render/tests/three_stills.rs` (ignored; needs the engine and the bundle) renders the 3D elements and compares them with `fixtures/prepare/stills`.

**Image nodes** (`crates/compile/src/nodes/image.rs`, executors in `crates/image`, category Image): Resize image, Crop image, Rotate and flip, Adjust image, Blur and sharpen, Place image and Image format. Their inputs are file ports, so imported pictures, screenshots and grabbed frames all connect, and they output an image. Every image is loaded upright (its EXIF orientation applied) and in sRGB (an embedded ICC profile converted with `moxcms`), keeping 16 bits and transparency; between nodes it is a PNG, and Image format makes PNG, JPEG (see-through parts filled with a background), lossless WebP or AVIF. The sizes a node makes are pure functions (`resized_size`, `crop_rect`, `rotated_size`) shared by the executors and the cards, which warn when an image is enlarged more than 2× or a crop leaves under 64 px. Their Inspector picture is the connected input.

**Registry elements load lazily.** `components.generated.ts` holds `import()` loaders; `DemoTimeline` waits on `delayRender` until an element's module is loaded, so unused elements never run their side effects (font loads).

**Asset refs are host-independent.** Specs hold `project:<relative path>` or `app:<public path>`; `resolveAssetRef` joins `project:` refs to the spec's `assets.projectBase`, which every host sets: the editor's file server, the preview's project server, the render asset server, or `static:` for Export as code. `app:` always goes through `staticFile()`. The editor loads project, font and `app:` files from the desktop file server (`crates/desktop/src/file_server.rs`, `fileUrl` in `apps/ui/src/editor/file-url.ts`): plain HTTP on 127.0.0.1 under a token made at each launch, with ranges, never a custom URL scheme, because WebKitGTK can't play video or audio from one (tauri-apps/tauri#3725). Exports must stay readable like any file the user makes: atomic writes keep the umask's mode (`partial_file`, `crates/engine/src/files.rs`).

**Cache keys.** A node hash is `sha256(ENGINE_VERSION, type, interpolated params, upstream hashes)`, plus the size and modified time of every project file its settings name (`file_stamps`, so a file replaced in place runs again) and, for render-phase nodes, the project settings, the variables (a node such as Choose by variable reads their values directly), the mix, `PICTURE_VERSION` and `PREPARED_VERSION` (`crates/runner/src/keys.rs`). An executing node that reads the project's width, height or frame rate sets `uses_project_size` so those are in its key too. Node keys and picture keys also hold the app's version, and node keys the three engine programs' hashes (`Release` in `crates/runner/src/keys.rs`), so a new release or another FFmpeg or browser runs everything again; between releases, bump `ENGINE_VERSION` (`crates/runner/src/keys.rs`) whenever an executor's output format changes. Every key that picks a file on disk is a sha256 (`versioned_hash`, `crates/engine/src/hash.rs`); the 64-bit `lookup_key` (`crates/compile/src/mix/plan.rs`) only matches values in memory, such as a mix plan to its result. Cached JSON is read into typed structs (`read_json`, `crates/engine/src/files.rs`), never trusted as-is.

**No old formats.** Nothing has been released, so there is no migration or fallback code for older project files, settings, engine folders or caches: when a format changes, change it everywhere, write `examples/` again (`bun run examples`, `crates/project/src/bin/write-examples.rs`, from `examples()` in `crates/project/src/templates.rs`) and delete local test projects. A test opens every example and fails when one isn't what the templates write today; the formatter leaves `examples/` alone, so they stay exactly as the app saves a project.

**Packaging.** `bun run make` (extra arguments go to `tauri build`, for example `-- --bundles deb`) runs `bun run stage` and then `tauri build --config tauri.release.conf.json` in `crates/desktop`. There is one build: the recording browser and FFmpeg are never shipped (see One engine). Locally, build the deb only, cap cargo with `CARGO_BUILD_JOBS` and put the output in the cache (`CARGO_TARGET_DIR=~/.cache/opsis-build`); CI builds every format.

- `scripts/stage.ts` fills the gitignored `resources/`: the video bundle (`bun run video:bundle`), the sidecar compiled into one executable (`resources/binaries/opsis-render-<target triple>`, `bundle.externalBin`; `bun build --compile --minify` for the Bun target matching the Rust host triple, `bunTarget`, with no source maps and no bytecode), the platform's compositor package (passed as `binariesDirectory`) with `COPYING.GPLv2` and `SOURCES.md` beside it, the Export as code sources (`resources/export-src`, from `source-layout.generated.json`) and the browser's Chromium credits (`resources/engine-licences/LICENSES.chromium.html`, written from a browser `install-engine` downloads into `~/.cache/opsis-stage-engine`).
- The compositor carries Remotion's own FFmpeg (GPLv2 or later), the one FFmpeg Opsis distributes; ours (ffmpeg-static, GPLv3) is downloaded or chosen. `licences/compositor-sources.json` names the exact source of that build (Remotion's compositor → `rust-ffmpeg` → `rust-ffmpeg-sys` → `rust-ffmpeg-splitter` commit, FFmpeg's tag and each library's pinned source), the stage refuses to run when it names another Remotion version than the one installed (and so does a test), `SOURCES.md` points at the source attached to each release, and `bun run compositor:sources` downloads it with its SHA256SUMS (CI's `compositor-sources` job on `v*` tags). Update the manifest whenever Remotion moves.
- The bundle settings (targets, resources, the sidecar, the deb's `gstreamer1.0-libav` dependency, NSIS per-user install, macOS hardened runtime) live only in `tauri.release.conf.json` (deb, rpm, AppImage, NSIS, MSI, the macOS app and DMG); the base `tauri.conf.json` stays bundle-free so `tauri dev` and the e2e build need no staged files. Tauri packs every binary target of `opsis-desktop`, so dev-only binaries sit behind a feature (`export-bindings`). Release builds use `opt-level = 3`, full LTO and one codegen unit, and are stripped (`[profile.release]` in `Cargo.toml`); expect a slow, memory-heavy link. The stage builds the video bundle with `video:bundle -- --release`, which writes no source maps (`sourceMaps: false` in `bundleRemotionProject`) and reads the maps libraries ship (`extractSourceMap` on their JavaScript), so their `sourceMappingURL` comments don't reach the bundle: a render opens every map a comment names, and a missing one fails it. Development bundles keep their maps so render errors point at source lines.
- A packaged app reads its resources from Tauri's resource folder (`AppPaths`, `crates/desktop/src/paths.rs`: the preview page, the video bundle, whose `public/` is the app's only copy of the `app:` files, `export-src`, the compositor, `engine-licences`, `LICENSE`, `THIRD_PARTY_NOTICES.md`) and starts the sidecar beside its own executable; in development everything comes from the repository and the sidecar runs as `bun run apps/sidecar/src/main.ts`.
- Linux ships deb, rpm and AppImage (CI only for the last two); Windows NSIS; macOS the app, zipped, signed and notarized in CI with the `APPLE_*` secrets, where every Mach-O inside is checked with `codesign`. Check the workflow with `actionlint`.
- Icons: `brand/logo.svg` is the source; `bun run brand:icons` renders `brand/icons/` with the recording browser, and `bun run app:icons` makes `crates/desktop/icons` from the 1024 px PNG with `tauri icon`.
- Renders pass the Remotion licence key from Settings (`"free-license"` when empty). Remotion ignores tsconfig `paths`, so the video bundle has no `@` alias. Export as code copies `video` and the bundler override into the exported project (`EXPORTED_SOURCES`, `apps/sidecar/src/source-layout.ts`), writes each copied package's `imports` map into its folder, and its `remotion.config.ts` (Rspack) and `tsconfig.json` (`allowImportingTsExtensions`) map `@opsis/video` to its own copy.
- Not yet: the updater, signing and the Windows and macOS checks (`plans/release.md`). The notices of the crates and npm packages compiled into the app are deliberately not shipped.

**Other shapes.** Exports and the Preview's shape switcher (per project, `previewShape`) size the spec with `variantSize`. A recording in a shape narrower than itself keeps its own shape inside the frame (`containBox`) and the camera zooms harder (`zoomBoost`, `narrowPose`): it never rests fully zoomed out and aims at the cursor between actions. In a narrower shape the camera plans for that frame (`tuning.narrow`): `frameFor` fits each target to the frame's width, centred, up to the boosted maximum. The full-page styles (Proof, Ledger) show the whole page in any other shape (`NarrowBleedClip`) over a blurred copy of the footage, with that same camera only when narrower. Window styles in wider shapes, and the `center`/`fit` choices, keep the old crop or bars. Overlays size by the long side (`overlayScale`) and keep clear of `shapeInsets`; outside landscape, lower thirds move to the top so captions own the bottom. A Layers node with **Keep this layout in other shapes** wraps its layers in a group with `design` (the project's size), drawn scaled to fit, for marks placed over a picture. Everything is in `packages/video/src/core/frame.ts`, except `containBox`, which lives in `packages/video/src/core/still-layout.ts` and also sizes screenshot windows (the capture's own copy is `crates/capture/src/still_layout.rs`).

**Transitions.** A transition overlaps the clips by its length unless **Keep every clip whole** is on (`TransitionRef.hold`): then `sequence_clips` holds the outgoing clip's last frame and the incoming clip's first frame for the transition (group `remap`) and delays the incoming clip's sound, so no clip loses screen time. Cards warn when a transition covers more than 40% of a clip (`cover_row`, fed `inputFrames`), when it is squeezed below 40% of its designed length, when Fit length cuts or speeds a lot, and when an element is shorter than 60% of its usual length; the Timeline outlines heavy transitions (`TransitionMark.covers`). A Sequence's `cuts` give the cut before a port (`before`: `in2`…`in6`, so connecting other clips never moves it) its own transition, length and hold (`cuts_for`, last entry for a port wins, entries for empty ports are kept and ignored); `splitBar` splits inside any Sequence, shifting later ports and cuts by one and joining the halves with a plain cut. Transition marks carry the `slot` that owns them, and clicking a mark's label on the Timeline selects that node.

**Ports that take several connections.** A `many()` input port (Add sound's Sounds) accepts any number of edges; `gather_inputs` merges every value on it (their sounds, concatenated). Sounds take only `audio`: a file becomes a sound through Music or Sound effect, which own its volume and timing. A Sound effect with **On an action** stores the action's node id; Add sound places it at that action's mark in the clip (`anchor_sounds`, via `flatten_spec`), plus an offset that may be negative.

**Window frames.** Auto zoom's `frame` (none, macOS, Windows, Linux) with `frameTheme` and `addressBar`, and Device frame's browser `windowStyle`, draw the title bar in `WindowFrame`; the address bar shows the take's first page address. New Device frames take the computer's OS style (`hostDefaults` in the workflow store).

**Child temp folders.** Every child program gets a temp folder under `<data folder>/tmp`, named `<app pid>-<kind>-<id>` (`crates/engine/src/temp.rs`) and passed as `TMPDIR`, `TEMP` and `TMP`, so whatever the render library, the browser or the bundle puts in the system temp folder lands there: each run its own (`run`), the streamed views and their browsers one per app launch (`shell-views`, `AppPaths::views_temp`) and the sidecar one per launch (`sidecar-render`). They are made when the app starts or the run begins, deleted when it ends, and at start `clear_stale_child_temps` deletes folders whose app process is gone. Never write intermediates to the system temp folder from the app. A child started in a folder nobody made fails, so `e2e/src/specs/views.spec.ts` opens the picker and the preview on a fresh data folder.

**Canvas transitions preview as they export.** The canvas transitions and filters (`makeCanvasPresentation`/`makeCanvasFilter`) draw their shaders only where Chromium's Canvas Draw Element is on, and fall back to CSS elsewhere. The render library turns it on for exports, so the preview's shell turns it on too (`PREVIEW_SWITCHES`, `crates/stream/src/preview.rs`, checked by `draws_canvas_transitions_as_renders_do`); never remove the switch. Feature switches are merged, not replaced (`effective_switches`, `crates/capture/src/browser.rs`), because Chromium keeps only the last `--enable-features`. On that path a transition hands each side's captured frame to `onElementImage`; `TransitionWrap` pairs the outgoing and incoming sides of a cut by the frame the cut starts on (`CutBoardProvider`, `packages/video/src/core/transition-cuts.tsx`, one board per set of tracks) and draws both through the incoming side, as the render library's own transition series does. A no-op there leaves the scene blank for the whole transition.

**Renders use one tab.** The sidecar passes `concurrency: 1` (`apps/sidecar/src/render.ts`). With Remotion's default (half the cores) the shader backgrounds fail to get a WebGL context ("WebGL is not supported") once a few tabs draw them at once, and on a 20-core machine one tab was also the fastest: 220 shader-heavy frames took 21.8 s with one tab, 32.8 s with four, 44.3 s with six; 300 recording frames took 28.5 s, 33.0 s and 35.6 s with one, two and four. Measure again before raising it.

**Screenshots.** The Screenshot node captures through `Page.captureScreenshot` with a clip `scale` from `capture_scale` (`crates/capture/src/still_layout.rs`): enough pixels to draw the shot at the largest export (twice the project size), never below the page's pixel ratio, capped by a surface budget for very large regions. Its image carries the region's size, that scale and, for one element, the element's box inside the padded region; `StillElement` lays it out with `windowLayout` (the shot's own shape; a page more than 1.5 times taller than the frame's shape takes the frame's shape and is cut only at the bottom), `cutoutLayout` (the element fitted, at most 1.5× the captured pixels) and `bleedLayout` (covers the frame, keeping the top).

**Preview quality.** The editor preview defaults to Fast: `TimelineSpec.quality = "fast"` makes `RecordingClip` play the 960 px `recording.preview.mp4` (made by the Record executor, keyframe every half second) and skip camera motion blur, whose 8 samples each decode the full recording. Exact matches the export; renders never set `quality`, so they are always exact.

**Audio.** Built-in sounds are CC0 files in `public/sfx`, listed in `crates/compile/src/data/sounds.json` (label, `app:` ref, length; the editor reads the same file) with credits in `THIRD_PARTY_NOTICES.md`; never add a sound without a checked free licence, and never link to a remote sound at render time. Ducking is a bus setting in the Mixer: rendered stems use `sidechaincompress`; channels shorter than the bus's `ignoreShorterMs` never key it (`duck_keys_for`, `crates/compile/src/mix/plan.rs`); the Timeline draws the ducked level from the same spans (`apps/ui/src/core/duck.ts`). Sound effects carry `role: "effect"` and their natural `lengthFrames`. A `keepMusic` sound effect never keys the ducking.

**Editor look and motion.** Panels, menus and the top bar sit on `bg-sidebar`; the canvas and page backgrounds on `bg-background`; colours are dark zinc greys (hue 286, slight colour, never pure black or white; panels about `#17171B` like Tailwind zinc-900, canvas `#101013`) and only change through the tokens in `apps/ui/src/index.css` (the window background, `BACKGROUND` in `crates/desktop/src/windows.rs`, matches the canvas token, which `apps/ui/src/app/window-background.test.ts` checks). Editor animation uses `motion` through the small components in `apps/ui/src/app/motion.tsx` (`MotionProvider` respects reduced motion). Motion Primitives registry components are installed only when they pass the type check as-is (today: `text-shimmer`); otherwise write a small equivalent in `motion.tsx`. `motion` stays banned in `packages/video`. Pressed toggles and toggle-group items use `--toggle-on` (and `--toggle-on-border` for outline groups), with unpressed ones in the muted text colour, set once in `index.css` because the installed toggle's own pressed colour barely shows on panels; a toggle with its own pressed colour (Mixer mute and solo) sets `data-custom-pressed`. Run success is the `--success` token: the Run panel's checks and the node card's Done border, which `flow-node.tsx` draws itself because the installed status indicator's success border is a plain Tailwind colour. Vertical separators in a centred row need `data-vertical:self-center`, since the separator stretches by default.

**Animation names are global.** React Flow UI's `node-status-indicator.tsx` injects `@keyframes spin` (with a −50% translate) while a node runs, so Tailwind's `animate-spin` is remapped to `icon-spin` in `apps/ui/src/index.css`. Never name a keyframe `spin`.

**One title bar.** The window has no system title bar. macOS uses `titleBarStyle: Overlay` with a hidden title (traffic lights inside our bar at 16, 16) and the native menu in the system menu bar (`crates/desktop/src/native_menu.rs`); Windows and Linux use undecorated windows with no native menu; the window buttons are ours (`WindowControls`: minimize, maximize/restore, close through the `window_role` command, icon following `WindowStateChanged`), and `WindowBorder` draws a 1 px edge while the window is neither maximized nor full screen. Every screen renders `AppBar` (`apps/ui/src/app/app-bar.tsx`): the `app-drag` utility makes it the window's drag handle and every control inside it `no-drag`; on Windows/Linux it shows the in-app menu (full Menubar from 1280 px, one Menu button below). Menus come from one list, `app_menu` (`crates/desktop/src/menu.rs`), built natively on macOS and sent to the editor for the in-app menu (`app_menu_sections`); `useMenuShortcuts` handles its accelerators in the page on Windows/Linux (leaving cut/copy/paste/select-all/undo/redo to text fields while one is focused), roles run through `run_role` in Rust, and navigation commands are handled once in the root route.

**Editor hosting.** Hash history only. Tauri serves `apps/ui/dist` (in development the Vite server on `localhost:5173`); the CSP is `app.security.csp` in `crates/desktop/tauri.conf.json`, which allows the file server's `http://127.0.0.1:*` for pictures, media, fonts and fetches. `index.html` loads `apps/ui/public/page-errors.js` (the editor's only public file) and `src/app/boot.ts` before the app: uncaught errors, rejections, `console.error` and `console.warn` from every window go to the app's log (`page_log`, target `page`), and nothing may read `window.opsis` while a module loads (the platform comes from the user agent, `apps/ui/src/lib/platform.ts`): a chunk that ran before boot once left the window black.
