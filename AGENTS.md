# Working on Opsis

Read `README.md` for what the app does and `plans/` for planned work. This file is about changing it.

## Hard rules

**No comments. Any kind. Anywhere.** No `//`, `///`, `//!`, no `/* */`, no JSDoc, no file headers, no CSS comments, in source, tests, scripts and config, in TS, Rust and Zig. If something needs explaining, the name is wrong or the function is too big; constraints that span the codebase go in this file. The only allowed comment-shaped lines are functional directives: `oxlint-disable…`, `/// <reference …>`, `@ts-…`; Rust attributes (`#[expect(…)]`, `#[cfg(…)]`) are not comments, and neither is a lint exception's `reason`. `bun run lint:comments` (`scripts/comments.ts`, part of `lint` and `lint:fix`) checks every TS file through `oxc-parser` (TypeScript 7 has no parser API; its native compiler only type-checks here), and CSS, Rust and Zig files line by line, everywhere but the installed and generated code.

**File names are kebab-case** in TS (`trace-panel.tsx`, `keycap-hud.tsx`), like the shadcn components; the code inside keeps its usual names (`TracePanel`). oxlint enforces it (`unicorn/filename-case`); the only exception is TanStack Router's `__root.tsx` (its pathless layouts such as `_main.tsx` pass as kebab-case). Rust module files are snake_case, because a module name must be an identifier. To rename a TS file, use the TypeScript rename edits (`getEditsForFileRename`, what VS Code calls on file move) so imports follow, then search for the old name in strings, configs and docs.

**Components are named functions** (`export function Title({ … }: ElementSettings["title"])`), never `React.FC` constants; `opsis/use-function-components` (`scripts/oxlint-plugin-opsis.ts`) enforces it.

**Every function is a declaration.** Write `function name(…) { … }`, never a function assigned to a `const` (`const name = (…) => …`), at the top of a module or inside another function; inline callbacks passed as arguments stay arrows, and installed code keeps its upstream style. `opsis/use-function-declarations` enforces it and `bun run lint:fix` rewrites what it safely can; it leaves to you a `const` with a type annotation, a named function expression and an arrow that uses `this` or `arguments`. A function declared inside another is hoisted, so it doesn't see a narrowing of the outer scope's variables (`if (!gl) return`): pass the checked value in as a parameter, or move the code after the check into a function that takes it. The other Opsis rules fix what they can too: `opsis/use-find-by-id`, `opsis/use-type-guards`, `opsis/use-function-components` and `opsis/use-percent-text` (only `Math.round(x * 100)%`) rewrite the code and add the import from `common/`; two fixes that add imports to one file land on separate passes, so run `lint:fix` again until it reports nothing.

**Never hand-edit installed or generated code.**

`crates/desktop/gen/` (capability schemas from `tauri-build`, which differ with the `e2e` feature) is written by every build and not committed.

`fixtures/**` holds golden files: what the code made for fixed inputs, stored with those inputs (compile results, node, settings and problem cases, the catalogue, FFmpeg arguments, filter and mix graphs, analysis, probes, capture tables, the TodoMVC take, the 3D text typefaces and 3D element stills, and the hashes of a few renders), plus test models with the counts Google's Draco decoder reads from them. The tests compare with them through `opsis-golden` (`crates/golden`: numbers within one part in a billion, every difference listed by its path). When a change is intended, record them again with `OPSIS_WRITE_GOLDEN=1` (`cargo test -p <crate>`, plus `-- --ignored` for the ones that need the dev engine, the film page or the internet) and review the diff; never edit them by hand.

Every element is written the same way, whatever it started as: one file per element, `crates/compile/src/elements/<category>/<element>.rs` (categories `media`, `text`, `overlay`, `transition`, `background`, `effect`, `ui`, `data`, `scene`, `device`), holding its settings struct, the rows and choices only it uses, and `definition()`, which registers it with the one builder (`element`, `meta` in `elements/entry.rs`: kind, key, title, description, category, length, design size, fixed props, kind props, the 30 fps clock, look). Choices several elements share are in `elements/shared.rs`, and the theme preset tables (`elements/theme.rs`: `neutral_themes` and `warm_themes` for the two UI kits, and one per family of elements with a palette of their own, such as `code_themes`, `keystroke_themes`, `stat_card_themes` and `data_story_themes`, each built with `with_themes`) reach theme settings through a `schemars` transform. `elements()` (`elements/mod.rs`) lists every `definition()` in the order the node list shows them. Every element's key is its plain name (`title`, `soft-blur-in`), its node type `fx.<key>` or, for a transition, `transition.<key>`; no name, type, path or field says where an element came from, which only `THIRD_PARTY_NOTICES.md` records. On the page every element is laid out the same way too: its component is `packages/video/src/elements/<category>/<key>.tsx`, or a folder `<key>/` with `index.tsx` when it has files of its own; parts several elements share are in `packages/video/src/parts/`; helpers are in `packages/video/src/lib/<purpose>/` (`motion`, `transitions`, `charts`, `code`, `paths`, `text`, `layout`, `backgrounds`, the two UI kits `neutral-ui` and `warm-ui`, which hold only their themes, and `ui-kit`, the colour, motion, step and timeline helpers both kits use), and plain helpers both the video and the editor use are in `src/common` (`math.ts`, `geometry.ts`…): use those before writing a local copy; and one table, `ELEMENTS` in `packages/video/src/elements/index.ts`, maps every key to its implementation. All of it is Opsis's own code, under the same rules, checks and formatting as the rest.

One documented exception in `apps/frontend/src/components/ui`: `DropdownMenuContent` (`dropdown-menu.tsx`) and `TooltipContent` (`tooltip.tsx`) take a `container` prop and pass it to their `Portal`. Dice UI's media player (`media-player.tsx`) needs it, and its docs list adding it as a prerequisite: in full screen it portals its menus and tooltips into the player, because only the full-screen element shows. Without the prop, the media player fails the type check. shadcn's own versions don't have it, so after `shadcn add dropdown-menu`/`tooltip --overwrite`, add it again (an optional prop, nothing else changes). When installing a Dice UI item, answer no to overwriting these two.

**Dependencies go through the package managers.** `bun add`, `bun add -d`, `bun remove` for TS, `cargo add` / `cargo remove` for Rust; never edit dependency blocks by hand, with one exception below. Every Rust dependency's version lives once in the root `Cargo.toml`'s `[workspace.dependencies]`: the workspace's own crates as path entries (`opsis-types = { path = "crates/types" }`), every other crate at its loose major (`"1"` from 1.0 on, `"0.<minor>"` before), and crates take them with `dep.workspace = true` or `dep = { workspace = true, features = [...] }` in `[dependencies]`, `[dev-dependencies]` and `[build-dependencies]`. `cargo add -p <crate> <dep>` reuses a dependency already in the root table. A new one needs its pin added to the root table by hand, the only dependency block edited by hand, before `cargo add -p` adds it to the crate. A root entry carries only the features every crate that uses it needs, since crates can add features but never remove them, and `default-features = false` wherever any crate turns them off; a crate that wants them then says `default-features = true` (`image`). `Cargo.lock` holds the exact versions, and adding or updating a dependency still takes the latest release, except:

- `specta` is pinned to `=2.0.0-rc.26` and `specta-typescript` and `specta-serde` to `=0.0.13`, in the root table: `tauri-specta` 2.0.0-rc.26 requires `specta =2.0.0-rc.26` and the 0.0.13 line of the other two, so any of them moving alone breaks the build; move all four together;
- WebdriverIO stays on 9.x (`webdriverio`, `@wdio/*` in `e2e/`): `@wdio/tauri-service` 1.5.1 and its embedded driver need `webdriverio ^9`;
- Ghostty's terminal engine is pinned in `crates/vt/zig/build.zig.zon` to the lib-vt source tarball of v1.4.0 (commit `83fb956`) by URL and hash, written with `zig fetch --save=ghostty <url>` in `crates/vt/zig`, never by hand; Ghostty builds only with the Zig version it names, so moving it may move Zig too.

**Tooling:** bun is the package manager and runs every script (`bun scripts/x.ts`, the end-to-end close check too), which import TypeScript without file extensions like the rest of the code. Never run scripts through `tsx` or Node. There is no live preview: a film is watched as an export. The app is Rust (Tauri 2) and the editor runs in the system webview: WebKitGTK on Linux, WKWebView on macOS, WebView2 on Windows. Every tool config is a `*.config.ts`, except the Rust ones, which are TOML at the root (`rust-toolchain.toml`, `rustfmt.toml`, `deny.toml`). Rust builds on one pinned nightly, `nightly-2026-10-29` in `rust-toolchain.toml` (with `rustfmt` and `clippy`), and `rust-version` in `[workspace.package]`, inherited by every crate, refuses an older compiler. To move it, change the date in `rust-toolchain.toml` and in every `dtolnay/rust-toolchain` step of `.github/workflows/build.yml` together, raise `rust-version` to the new compiler's, run `rustup default` with the new toolchain and uninstall the old one so the computer keeps one nightly, and move `~/projects/agent-os/rust-toolchain.toml` to the same date (left uncommitted there). Zig 0.17 builds `opsis-vt`'s wrapper (Ghostty needs the same major and minor version): `crates/vt/build.rs` runs `zig build` (the `ZIG` variable names another program) and refuses any other version, CI installs 0.17.0 with `mlugg/setup-zig` in every job and runs `zig build --fetch` before Cargo, and Zig 0.17 unpacks the packages into `crates/vt/zig/zig-pkg` (ignored by git; the tarballs stay in Zig's global cache). `build.rs` always names the target (`x86_64-linux-gnu`, `aarch64-macos`, `x86_64-windows-msvc`…), because Zig's native target compiles for the building computer's processor. `bun run lint:zig` builds the wrapper as a check and `bun run format:zig` runs `zig fmt` on it. Rust imports are grouped std, external crates, then the workspace's own, one `use` per module; `rustfmt.toml` keeps them so (`group_imports = "StdExternalCrate"`, `imports_granularity = "Module"`, unstable options only the nightly applies), and struct fields use the shorthand. `bun start` (`scripts/start.ts`) stages FFmpeg when it's missing and runs `tauri dev` in `crates/desktop` (it serves the editor first); exports also need the prebuilt film page, `bun run film:bundle`, made again whenever `packages/video` or `packages/runtime` changes. `OPSIS_USER_DATA` moves the app's data folder (default `<config dir>/Opsis`), for tests and side-by-side runs. `OPSIS_FFMPEG` (an absolute path, read only by builds with debug assertions: `tauri dev`, `cargo test`, the e2e build) names the FFmpeg the app and the tests start; `bun start`, `bun run test:rust` and the e2e runner set it to the staged program, and a test that starts FFmpeg reads it through `opsis_golden::ffmpeg()`. To see a change in the running app, use the `check-app` project skill (`.claude/skills/check-app`): it seeds `~/.cache/opsis-check` (short, so the API socket fits), starts `bun start` in a virtual display and drives it through the Local API.

**Workspace.** A Bun workspace run by turbo (`turbo.json`) next to a Cargo workspace (`Cargo.toml`, members `crates/*`, `Cargo.lock` at the root). Apps build things and nothing imports them: `apps/frontend` (`@opsis/frontend`, the editor, a Vite app with its own `vite.config.ts` and `index.html`) and `apps/film` (`@opsis/film`, the film page the frame driver renders, a Vite app that mounts `@opsis/video/film`). The end-to-end suite, `e2e/`, is not in the workspace: it has its own `package.json`, `bun.lock` and `node_modules` (`bun install` inside it), extends `tsconfig.base.json`, `scripts/lib/oxlint-base.ts` and `scripts/lib/oxfmt-base.ts` by path, and is checked only by its own `typecheck`, `lint` and `format` scripts, which CI runs after the root checks; the root checks skip it. `packages/video` (`@opsis/video`) is source the apps compile: the film (`film.tsx`, `DemoTimeline`), the registry elements and the helpers both the video and the editor use (`src/common`). `packages/runtime` (`@opsis/runtime`) is the film's page runtime the elements build on: the clock (`useFrame`, `useFilm`), `Sequence`, `Freeze` and `Loop`, the render holds (`holdRender`, `failRender`, `useHeldLoad`), `AbsoluteFill` and `Img`, the render environment, the maths (`interpolate`, `Easing`, `spring`, `random`, our own, property-tested), the page protocol (`page.tsx`) and the test harness (`test-frame.tsx`). Each declares the dependencies it imports (`bun add` inside its folder) and has its own `tsconfig.json` (extending `tsconfig.base.json`), `vitest.config.ts` (`scripts/lib/vitest-base.ts`) and `oxlint.config.ts` (`scripts/lib/oxlint-base.ts`); root scripts run each check everywhere plus the root's own (`typecheck:app`, `lint:app`, `test:app` cover `scripts`). Installs are bun's default isolated layout: a folder can only import what it or the root declares, and scripts read a package's files from the package that owns it. Workspace members import each other only by package name and through their `exports` (`@opsis/video/common/*`, `@opsis/video/generated/spec`, `@opsis/video/film`…). A member imports its own files through its `package.json` `imports` with its own prefix, `#video/…`, `#runtime/…`, `#film/…`, never `#/`; `video` and `runtime` mix `.ts` and `.tsx` and imports with them (`#video/core/frame.tsx`); nothing imports by a relative path. Only the editor uses `@/` (`apps/frontend/src`), since no other build compiles it, and it must for anything two or more folders up (oxlint bans `../../` in `apps/frontend/src`; the brand logo, outside the package, is the one import with a lint directive); oxlint rejects `@/` in `video`.

Rust crates live in `crates/<domain>`, named `opsis-<domain>`, one domain each; nothing Rust lives in `apps/`. `opsis-types` holds every shape that crosses a boundary; `opsis-compile` node definitions, settings, compile, cards, validation, the Inspector context, the timeline flattener, chapters, the mix plan, the catalogue and the edits (`edits/`: workflow, mixer, marker and timeline edits, and which nodes an edit touched); `opsis-store` the app database (`schema.sql` and the queries on it), settings, view state, recent projects, window bounds, the font rows, the keyring key and sealed sign-ins; `opsis-document` the open project's document (`Document`: the workflow, undo and redo, gestures, revisions, the saved revision and file version, the nodes each change edited); `opsis-project` project folders (create from `templates.json`, open and save with versions, watching with `notify` through `notify-debouncer-mini`, asset and model import with `gltf`, file stamps, the last run); `opsis-fonts` the font library (`wuff` unwraps WOFF and WOFF2, `skrifa` reads names, weights, italics and axes), the computer's fonts (`fontdb`) and online fonts; `opsis-engine` the engine paths, the installer (downloads checked against the pinned sha256 and size), the bundled FFmpeg (its pins, `bundled_ffmpeg` and the staging), the tool helpers (version, file stamp and hash, `EngineFiles`), licences, child temp folders, the file server (`ServeDir`) and the file and hash helpers; `opsis-traces` the trace store; `opsis-runner` the run (plan, cache keys, saved results, run events and progress); `opsis-media` FFmpeg (argument builders, runs and probes behind the `MediaTools` trait so tests can fake them), the media executors, mix stems with their levels (`hound`) and loudness (`ebur128`), and waveform and filmstrip analysis; `opsis-render` the film renders (`frames.rs`: frames into FFmpeg, stills), the saved pictures and the output executors; `opsis-prepare` the prepared files (see Prepared files); `opsis-image` the image nodes on `image`, `fast_image_resize`, `imageproc` and `moxcms`; `opsis-footage` the film's footage frames (one streaming FFmpeg decoder per source during a render, the source's grade in its filter graph, Redact's areas per frame by their time ranges, JPEG 4:4:4 through `jpeg-encoder`, served under `.opsis/footage/<id>/<µs>` beside the prepared files; nothing is cached on disk); `opsis-probe` reads a media file's length, container, picture (codec, size, frame rate, pixel format) and sound (codec, sample rate, channels) from the file's own bytes, the way ffprobe reports them, for every probe the app makes (`MediaTools::probe`; its parity test, `crates/probe/tests/ffprobe.rs`, ignored, compares it with an ffprobe kept in `~/.cache/opsis-ffmpeg`, which nothing downloads, making its samples with the staged FFmpeg on samples it makes in `~/.cache/opsis-probe-samples`); `opsis-vt` Ghostty's terminal engine (libghostty-vt, see `plans/terminal.md`): a Zig wrapper of our own (`crates/vt/zig/src/vtwrap.zig`) imports Ghostty's `ghostty-vt` Zig module and exports a C interface shaped for Opsis, `build.rs` links it as static archives (the wrapper and Ghostty's SIMD libraries), and Rust calls it through hand-written declarations in `src/ffi.rs` behind one safe `Terminal` (owned handle, `&mut self` everywhere, `Send` and not `Sync`) that checks the interface's version and struct sizes when it is made; nothing else depends on it but the terminal takes' crate; `opsis-capture` the browser over CDP (`chromiumoxide`): sessions, selectors, actions, the screencast encoder, sign-in steps and stills, and the film's `FrameDriver`; `opsis-stream` the streamed views (sign-in, element picker); `opsis-api` the Local API; `opsis-desktop` the Tauri app that composes them: windows, menus, commands and events, the exit flow, the file server for the editor. `opsis-golden` is a development dependency only: the golden-file helper the tests share, with the small readers and builders more than one crate's tests use (`repo`, `home`, `typed`, `text`, `number`, `cases`, `node`, `edge`); helpers only one crate's tests share live in its `tests/support/mod.rs`. `opsis-macros` holds the procedural macros (`proc-macro2`, `syn`, `quote`; no `paste` or `pastey`, since `quote` and `format_ident!` build every name). Only the desktop crate opens windows or dialogs. Node settings are Rust structs with `serde` defaults and `schemars` attributes (field metadata as `x-` keywords, our own checks as `x-check`), validated with `jsonschema`; elements, core and registry alike, are settings structs registered in `crates/compile/src/elements`. The root `Cargo.toml`'s `[workspace.lints.rust]` denies `unsafe_code` in every crate but one: `opsis-vt`, whose `lib.rs` allows it with `#![allow(unsafe_code, reason = …)]` and keeps its `unsafe` in `src/ffi.rs` and `src/terminal.rs`. Every public type implements `Debug` (`missing_debug_implementations`): it derives it, private types it holds derive it too, and where a field has none (a closure, a trait object) the type writes `Debug` by hand, listing the fields that have it and ending with `finish_non_exhaustive`.

**Verify with** `bun run typecheck`, `bun run lint:fix`, `bun run format:fix`, `bun run test`. Rust runs inside them: `lint:fix` runs `cargo clippy --workspace --all-targets -- -D warnings` and `cargo deny check advisories licenses` (`lint:deny`, with cargo-deny's shared advisory database; CI installs cargo-deny 0.19.8). Clippy runs the `pedantic` and `nursery` groups as warnings (`[workspace.lints.clippy]` in the root `Cargo.toml`), and `-D warnings` fails on any of them. The permanent workspace allows are `missing_errors_doc` and `missing_panics_doc`, which ask for doc comments the no-comments rule bans; `option_if_let_else`, which would turn every `if let … else` into `map_or_else`; `too_many_lines`, which caps functions at 100 lines; `must_use_candidate`, which asks for `#[must_use]` on every function whose result could be ignored; `struct_excessive_bools`, which flags structs with more than three `bool` fields, mostly settings structs with their switches; `significant_drop_tightening`, which guesses a lock's lifetime from its last use and so flags guards that something still borrows and locks held across an `await` on purpose (a lock that blocks others needlessly is still tightened by hand, as `check_media_files` does); and `module_name_repetitions`, which flags item names that repeat their module's name and is off today only because it sits in `restriction`, so the allow keeps it off if it moves back to `pedantic`. A lint exception is local, on the item or the statement, never a new workspace line, and it is `#[expect(lint, reason = "…")]`: the reason says why the flagged code is meant, and the compiler reports the expectation once the lint stops firing there (`unfulfilled_lint_expectations`), so no exception outlives its cause. An exception that holds in only some builds sits in a `cfg_attr` for those builds (`native_menu`, dead outside macOS). `#[allow]` is only for code where an expectation can't hold in every build that compiles it, such as test helpers shared by several test binaries that each use part of them (`crates/capture/tests/support/mod.rs`), and then as an inner `#![allow(…, reason = "…")]`. Clippy's `allow_attributes` and `allow_attributes_without_reason` (in `[workspace.lints.clippy]`) enforce this: an outer `#[allow]`, or an exception without a reason, fails `lint`. `lint:fix` also builds the Zig wrapper (`lint:zig`), `format:fix` runs `cargo fmt --all` and `zig fmt` (`format:zig`), `test` runs `cargo test --workspace`. The `:fix` variants fix and report the rest; do not run the non-fix variants first. A pure function with an invariant (a round trip, a bound, an order, a count) is tested as a property over generated inputs, `proptest` in Rust and `fast-check` in TS, with a hand-written case only where it pins exact text people see; a test never restates a lookup table or checks a pure function against itself. TS tests are `*.test.ts` on Node (in each package's `src`, the apps' `src` and `scripts`); a test that renders React components or hooks is `*.test.tsx` and runs in happy-dom with Testing Library (the two `projects` in `scripts/lib/vitest-base.ts`). The editor's tests read the catalogue and compiled films from Rust through the `editor-data` binary (`crates/compile/src/bin/editor-data.rs`), which their global setup builds in release. Tests that need the dev engine or a built page are `#[ignore]`d with the reason (`cargo test -p <crate> -- --ignored`); the render ones also need the film page (`bun run film:bundle`).

**End-to-end tests** (`bun run test:e2e`: `e2e:app` builds the app with the `e2e` feature, then `e2e/` runs; run `bun install` in `e2e/` once) drive the real app through WebdriverIO and `@wdio/tauri-service` with its embedded driver: `tauri-plugin-wdio-webdriver`, compiled in only with the `e2e` Cargo feature, which refuses to build without debug assertions (`compile_error!` in `crates/desktop/src/lib.rs`) and adds the `wdio-webdriver` capability (`crates/desktop/capabilities/e2e`, picked by `build.rs`, which tells cargo to watch the `capabilities` folder: with its own pattern `tauri_build` watches only `tauri.conf.json`, so an edited capability was never compiled in). The build goes to `target/e2e` so `cargo test` never overwrites it. The tests run in a virtual display only: `xvfb-run` with `WAYLAND_DISPLAY` unset and `GDK_BACKEND=x11` (otherwise GTK opens the window on the desktop's Wayland display), and `wdio.conf.ts` and `src/close-check.ts` refuse to start without that. Never open a test window on the real screen and never move the real pointer. Each run gets a fresh data folder in `~/.cache/opsis-e2e` (`OPSIS_USER_DATA`, the database seeded with the API on and the dev engine's recording browser as the `settings.engine` path, which the app checks at start, `examples/` copied, and `OPSIS_FFMPEG` set to the staged FFmpeg by `wdio.conf.ts`); specs that record or export wait for that check (`engineReady`); failure screenshots go to `~/.cache/opsis-e2e/failures`. The virtual display hides the window but not the sound, so a spec mutes any player it presses Play on; the specs share one project folder and the app's selection, so a spec deletes the nodes it adds (the Run panel lists the selected node's files, not the exports). The close check runs on its own after the suite, because closing the app ends the driver.

**Do not commit or push.** Leave changes in the working tree unless asked.

**Large files go to `~/.cache/opsis-*`** (browser binaries, clones, renders, release builds); `/tmp` is for small scripts and screenshots only. Long-running processes start with `run_in_background`.

## Invariants that must not regress

**Runtime boundaries.** `packages/video` and `packages/runtime` are compiled by the editor (the `common/` helpers and generated types) and by the film page: no `node:*` or `playwright-core` there (oxlint enforces it). Node-only code lives in `scripts`; everything else that touches the system is Rust. Element metadata (the entries in `crates/compile/src/elements`) never names a component; implementations are keyed separately in `packages/video/src/registry`.

**Rust is the source of types.** Every shape that crosses a boundary (commands, events, the timeline spec, run events) is a Rust type, exported with specta (`bun run types:export`) into `apps/frontend/src/generated/bindings.ts` and `packages/video/src/generated/spec.ts`; tests fail when an export is stale. Never write such a type by hand in TS. JSON Schema for the Inspector and the Local API comes from the same types (`schemars`).

**Numbers and errors are typed.** Whole numbers are integers: frame lengths, sizes, frame rates, counts and settings in milliseconds are `u32`, a sound's start (which can fall before its clip) `i32`, timestamps `i64` milliseconds since the epoch; only values that can be fractional (positions in a remapped clip, action times, volumes, rates) are `f64`. No number is converted with `as`: widening uses `f64::from`, integers `try_from`, and everything else `opsis_types::numbers` (`whole` and `whole_signed` round a float into a whole number, `truncate` cuts one toward zero like a cast, `float`, `float_wide` and `narrow` go to `f64` and `f32`, `count` and `signed` narrow integers, `millis` reads a `Duration`, and `byte_size` writes a size in binary units, "1.5 KiB", the one way sizes read in the app; the editor's `formatBytes` writes the same). Floats are compared exactly only through `exact_eq`, for a setting at its neutral value, whole numbers kept as `f64` and exact properties in tests; a plain `==` on floats fails Clippy's `float_cmp`, which skips functions with `eq` in their name, so `exact_eq` needs no exception. Clippy's `pedantic` group, on for the whole workspace (`[workspace.lints.clippy]` in `Cargo.toml`, `[lints] workspace = true` in every crate), includes the cast lints, so a new cast fails `lint`. Kinds that form a fixed set are enums (`BrowserAction` for the steps of a browser session, `Sign` for linked settings), and node types the code names are constants next to their definitions (`OPEN_BROWSER_TYPE`, `RENDER_TYPE`). Every element's settings are a struct; the props a page receives are built from them as JSON maps (`element_props`), exported for the page as one map, `ElementSettings` (`crates/compile/src/elements/props.rs`, every element by key, with `StillProps` and `PlaceholderProps`). Each module has its own error enum (`thiserror`: `SettingsError`, `CompileError`, `StartupError`…), turned into text only where it reaches a person or a JSON field, and a missing value falls back to a default only when the default is what it means.

**The film page and the frame driver.** The film page (`apps/film`, built into `film-bundle/`) is served by the render file server at `/.opsis/film/` (`FILM_FOLDER`, `folder_routes`) beside the project's files, and `mountFilm` (`packages/runtime/src/page.tsx`) gives it `window.opsis`: `load(spec)` mounts the film at frame 0 and resolves with its size, rate and length once every hold is released and the fonts are ready, `seek(frame)` commits the frame with `flushSync` and resolves the same way, and `holds()` names what is still open. `FrameDriver` (`crates/capture/src/film.rs`) launches the browser with the film's own switches (`film_switches`: the GL choice and the element-drawing feature) and, on Linux, under begin-frame control: it probes that once a test page draws, tries again, and otherwise takes a screenshot per frame and the run log says so; the page loads while display-less frames tick, and each frame is a seek and then one `beginFrame` with its picture (a frame with no damage repeats the last picture). A frame that isn't ready within 30 s fails with the holds still open. The page only draws when the driver asks, so while a seek is still waiting on holds the driver issues frames it doesn't capture (`seek` in `film.rs`); a hold may therefore wait for an animation frame or a canvas `paint` event (`untilPainted` in `lib/transitions/canvas-presentation.tsx`), and the frame it captures comes after them. Canvas effects draw into a canvas that is on the page: frames from a canvas given to `transferControlToOffscreen` never reach a begin-frame capture, and reading a WebGL `OffscreenCanvas` back as a bitmap on the page hung it. An SVG element whose CSS `scale` is exactly 0 stops being repainted when its scale changes (the animated bar chart's bars stayed hidden until they settled), so a scale that starts at 0 is kept above it (`PAINTABLE_SCALE`). `crates/render/src/frames.rs` encodes the frames (JPEG at quality 80) through `film_encode_args` (`crates/media/src/codecs.rs`) and draws stills; `crates/render/tests/frames.rs` (ignored; needs the dev engine and `bun run film:bundle`) renders through it.

**Every animation in `packages/video` is a pure function of `useFrame()`.** The film draws through `@opsis/runtime` only (`packages/runtime`: `useFrame`, `useFilm`, `Sequence`, `Freeze`, `Loop`, `holdRender`, `failRender`, `AbsoluteFill`, `Img`, `interpolate`, `Easing`, `spring`, `random`); No Framer Motion, `motion`, GSAP, CSS transitions or Tailwind `animate-*` (oxlint: `no-restricted-imports`, `opsis/no-animate-class`). Randomness uses `random(seed)`; async work holds the frame with `holdRender()` and calls the release it returns; colours between stops mix in OKLCH (`interpolateColors`, `lib/ui-kit/color.ts`). `app:` files reach the page through `assetUrl`.

**Nodes never generate film code.** A node definition (`crates/compile/src/nodes`, built with `NodeDef` in `node.rs`) has ports, settings and an optional pure `compile`; a node that saves something only one node may save (a sign-in name, an export file) says so with `claims` (`Claim`), and validation reports every later node that claims the same (`claim_clashes`, `crates/compile/src/graph.rs`); executors are keyed by node type (`opsis-media`, `opsis-render` and `opsis-capture` each register theirs). Every node with `executes: true` has an executor (`crates/render/tests/executors.rs`). Compile produces a `TimelineSpec`; the film page's one `DemoTimeline` draws it. Every timeline item has a `kind`: `group` and `recording` items carry typed props (`GroupProps`, `RecordingProps`, `crates/types/src/timeline.rs`) and are drawn by kind, `element` items name a registry `component`; read them by narrowing on `kind`, never by component name.

**Nodes pass resources forward.** Every port carries a resource (`PortType`, `crates/types/src/workflow.rs`: browser session, recording, recording style, grade, clip, sound, captions, image, file), and an output connects to an input of the same type or one the conversion table turns it into (`conversion` and `can_connect` in `crates/compile/src/ports.rs`), lossless and settings-free only (an image or a recording is a file). `gather_inputs` (`crates/compile/src/compile.rs`, also the runner's inputs in `crates/runner/src/context.rs`) converts every value with `convert_input`, so a node always receives the type its port declares; anything that needs choices (fit, length, volume, start) is a node. A node says which files its file inputs take with `.needs(FileNeed::…)` after its ports (`crates/compile/src/node.rs`: an image, a picture, something that plays, sound, or a sound file), and validation warns on the node when the connected file, converted, is another kind (`file_need_issues`, `crates/compile/src/graph.rs`), before anything runs. Export nodes take a `clip`, and `film_of` (`crates/compile/src/compile.rs`) makes their film from the clip on that input when they run and when the Timeline picks its film (`picked_film`, `FilmTarget`); the compile result carries no films.

**Browser nodes are virtual.** Open browser starts a `browser-session` value (`{ browser, steps }`) and every other browser node appends its own step (id, type, label and parsed, interpolated params) in `compile()`; a skipped one passes its input through, so it never enters the list. Record take and Screenshot read the session at their `session` input and play `steps` as given, in one take. The video starts at the first Start recording step; the steps before it run off camera, and without one it starts with the first step. Nothing walks the graph backwards to find a chain: the session carries the address the last Go to page opened (`address`, set by that node's `compile`), which the element picker opens and the Run page script warning reads.

**A take is one value whatever made it.** Every take is a `recording` (`RecordingValue`, `crates/types/src/values.rs`): what every take has (its log, length, node and `edits`) and a `source` enum (`TakeSource`: `Browser` with its video and viewport, `Terminal` with its cast file, size and theme) for what only one kind has; the log is in the take's own units (CSS pixels for a browser take). `RecordingValue::file` names the take's own file and `video` only a browser take's. What the page draws is `RecordingProps` (`crates/types/src/recording.rs`) in groups: `camera` (zoom and `CameraTuning`), `shot` (camera style, backdrop, window size, ground, corners, shadow, lifted colours, background blur, motion blur, `inDevice`), `window` (frame, colour, font, the title bar and its typed text and mode), `pointer` (cursor look, size, feel, ripple) and `screen` (`ScreenProps`, what is in the window: the footage with its chain and address). `DemoClip` (`packages/video/src/camera/demo-clip.tsx`) draws the `Screen` (`packages/video/src/core/screen.tsx`) everywhere a picture of the take goes, so every camera style, frame and mark works around any screen. A value can refuse a conversion its port type allows (a terminal take has no video file): `value_converts` and `refused_conversion` (`crates/compile/src/ports.rs`) decide it, every compile sends each output's conversions (`EditorCompile.converts`, `output_conversions`), the canvas's `connects` checks them, `edit_workflow` refuses such an edge (`connection_problem_now`) and validation puts an error on one already there (`value_issues`, `crates/compile/src/graph.rs`). Save take (`output.take`) copies a take's own file to the exports, a video or a cast file by its kind.

**Recording style is a list too.** Clip from take (`camera.take`, `recording + recording-style? → clip`, only its playback speed) makes a clip from a take: it starts from every style node's defaults (Camera, Shot, Motion blur), then applies the style's entries, then the take's own edits: the most specific wins. Style nodes (camera, shot, cursor, click ripple, keystroke chips, spotlight, highlight box, tooltip, callout arrow, follow cursor, skip quiet parts, backdrop, motion blur, window frame) are `recording-style? → recording-style` and append `{ nodeId, type, params }` (`style_modifier` in `crates/compile/src/node.rs`); Zoom here, Pan and Speed ramp need one take's frames and times, so they are `recording → recording` and append to the recording's own `edits` (`recording_modifier`). Each gives its definition a `restyle` or `retime`, which `restyle_with`/`retime_with` (`crates/compile/src/style.rs`) apply; `restyle_with` applies Camera entries before any other, so the nodes that adjust the camera (Follow cursor, Pan) always land on it. Apply style (`clip + recording-style → clip`) styles every recording in a clip, for takes joined in a Sequence or Layers.

**A colour grade is a list too.** Grade nodes (`crates/compile/src/nodes/grade.rs`: Colour and light, Look file, Black and white and tint, Texture, Lens, Auto fix) are `grade? → grade` and append `{ nodeId, type, params }` (`grade_modifier`); a skipped one passes its input through. Nothing converts into a `grade`. Each step's card row and neutral check come from one list of changes, so a card's "No change" and the empty filter always agree (`is_neutral_entry`). Apply grade (`media.applyGrade`, `file + grade → file`) turns the list into one filter graph (`grade_filters`, `crates/media/src/grade.rs`, pure and tested by string: steps that need no blend are joined with commas, a step below full strength splits and blends back, a look image is the next numbered input to `haldclut`, paths are escaped for the graph) and encodes once, so the sound is copied when the container holds it. Texture's dark-edges spot shows a frame of the file that reaches Apply grade (`graded_file`, `crates/compile/src/inspector.rs`). The same list grades footage inside the film through Grade footage (see Footage comes from Rust).

**Params carry their own inspector UI** through `schemars` attributes on the settings structs, written with `#[setting(…)]` on each field of a struct marked `#[settings]` (`opsis_macros::settings`). `#[settings]` writes the struct's derives (`Debug`, `Clone`, `PartialEq`, `SmartDefault`, `Serialize`, `Deserialize`, `JsonSchema`, `specta::Type` with `#[settings(export)]`, for element settings and their rows, and `Eq` with `#[settings(eq)]`, for settings with no floats), `#[serde(rename_all = "camelCase", default)]` and `impl Params`, except with `#[settings(check)]`, where the struct writes its own `impl Params` with `check`; never add a `derive` to it. Each `#[setting(…)]` writes the field's `#[default(…)]` and `#[schemars(…)]`: the label first, then `default = <expr>`, `range(…)`, `length(…)`, `transform = <fn>`, `check = colour` or `colour_or_empty` (the colour rules with "Pick a colour") or a rule object, a bare word for an `x-` keyword that is `true` (`advanced`, `hidden`), any other `word = <value>` for `x-<word>` with `_` as `-` (`help`, `zero_label`, `show_if`), in the order written, and `"key" = <value>` for a schema keyword as it is (`"type"`); never write `#[schemars(…)]` or `#[default …]` on a settings field by hand. Every enum a setting picks from is a `#[choice]` (`opsis_macros::choice`): it writes the derives (`Default` when a variant is `#[default]`, `specta::Type` with `#[choice(export)]`) and `rename_all = "kebab-case"` (another case with `#[choice(rename_all = "…")]`), and `#[label("…")]` on every variant gives the enum's `x-labels`, keyed by each variant's name on the wire, and its `label()`, which cards use instead of matching the variants again. A field's own `labels = {…}` is only for a field that names the choices differently from its enum. The label is the `description`, limits are ranges, and the rest are `x-` keywords: `x-help`, `x-widget`, `x-step`, `x-unit`, `x-accept`, `x-labels`, `x-zero-label`, `x-unconnected-zero-label`, `x-presets`, `x-presets-label`, `x-show-if`, `x-show-if-file`, `x-show-if-take`, `x-advanced`, `x-hidden`, `x-pauses`, `x-time-key`, `x-length-key`, `x-themes`, `x-frames-at`, and `x-check` for our own checks (`{ rule, message }`, such as the colour rule). The editor builds its forms from that JSON Schema (`apps/frontend/src/editor/form/schema.ts`, `editor/schema-form.tsx`); every node's settings schema carries its defaults as its own `default`, and every list of objects its default row as the items' `default` (`with_row_defaults`, `ParamSchema::new`), so the form fills and adds rows without working defaults out; element settings carry the same keywords. The Inspector shows a node's settings on two tabs, Basic (the default, opened again on every node) and Advanced with its count, the settings marked `x-advanced`; a node with none shows no tabs, and nested forms (rows, marks) list all their fields in order (`SchemaForm`'s `tabs`). `x-unit: "ms"` and `"frames"` are stored as-is and shown in seconds. Widgets: `textarea`, `code`, `asset`, `target`, `action` (an action node, for a sound placed on its mark), `marker` (a Timeline marker, listed by label from the workflow's markers), `timezone`, `keys`, `datetime`, `variable`, `backdrop`, `offsets`, `spot`, `quality`, `loudness`, `transition`, `multiselect`, `color`, `cut` and `port` (one of the node's connected numbered inputs; `cut` leaves out the first), `envelope`, `sound` (built-in sounds or a project file, with a play button), `music` (built-in songs or a project file, the same picker), `font` (project, built-in and library fonts; picking a library font copies it into the project), `boxes` (areas drawn over a frame of the upstream recording, stored as fractions of the frame), `marks` (a list of marks drawn on the inspected picture with Konva, `form/marks-field.tsx`: a tool bar, drag to draw, the ends of arrows, boxes and ovals as handles, each drag written once when it ends, and the selected mark's other settings as its nested form; the geometry is in `form/marks.ts`), `gradient` (a CSS gradient edited as straight or round with 2–6 draggable stops; Rust parses it and applies each edit, `gradient_view` and `edit_gradient` over `crates/compile/src/gradient.rs`, and the field only draws what comes back), `camera` (camera keys with time, easing, turn, tilt, distance and height, and "Add key at playhead"), `theme` (`{ mode, colors }`: a light/dark switch and the token colours of the preset in `x-themes`, only changed tokens stored). Widget names are the `FieldWidget` enum (`crates/compile/src/elements/introspect.rs`, a test fails on any other), exported to `packages/video/src/generated/spec.ts`, whose type the editor's forms use; a `spot` field keeps its y in `spotYKey(name)` and shows the frame at the time in its `x-time-key` setting, and a `target` field the picked element's role in `targetRoleKey(name)`. Rust sends what a form needs beyond the schema with every compile (`InspectorContext`: variables, layers, actions, the spot's frame, the picker's page, the project's colours, connected inputs, file kinds). Plain text fields render variables as chips (`VarText`, which reads the variable pattern and pause mark from the catalog's `text`, `VAR_PATTERN`); never show `{{…}}` to a user. Fields write on every keystroke, so the Inspector wraps a focused text field in a gesture (`useTypingAsOneUndoStep`): typing until the field loses focus is one undo step. Lists pick their input from the item schema: text items a text list (Enter adds an item, pasting lines adds one per line), numbers a number list (pasting a spreadsheet column fills it), colours a palette, objects rows (each row is a nested form, so any widget works in a column; rows drag to reorder, duplicate and collapse); all of them honour the array's `minItems`/`maxItems` and drag through the Dice UI `Sortable`, one undo step per drop. The colour field (`form/color-picker.tsx`, our own, on culori) keeps the format a value is written in (`#hex`, `rgb()`, `hsl()`, `oklch()`, with alpha) and rewrites it only when the user picks; its popover is one gesture and offers the project's colours as swatches. `x-zero-label` on a colour, file or text field means empty is unset: compile drops the empty value (`map_leaves` in `element_props`, also inside rows and nested objects) and the field shows the label ("Theme", "Built-in image"); on an optional number (no default) it is the placeholder and clearing the field unsets it. `x-unconnected-zero-label` takes its place while none of the node's inputs is connected (a wrapper whose clip is optional plays its usual length alone). `x-show-if` values are text (`["true"]` for a switch, never `[true]`), because the form compares the setting's value as text; a test fails on any other (`crates/compile/tests/unit/nodes_c.rs`). `x-show-if-file: { path: ["image"] }` shows a field only when that setting holds a file of that kind; Rust sends the kind of every file setting of the inspected node (`InspectorContext.file_kinds`, `kind_from_path`), so the editor never reads extensions. `x-show-if-take: ["browser"]` shows a field only for that kind of take: Rust sends the kind of the take the inspected node reaches, on its own inputs or a later node's (`InspectorContext.take_kind`, `take_kind`), and the field shows while no take is connected.

**Every value a user would want to change is a setting.** Colours, copy, content lists, images, visible sizes and weights, light or dark, and the length of a still are settings in the Inspector. Only timing the Timeline owns (`delay`, `holdSeconds`, `exitAtInFrames`…), animation tuning, functions and React nodes stay in code. Registry elements' settings are their structs, with fixed and kind props on their entries (`.fixed`, `.kind_prop`): a component prop is a setting, a fixed prop, a wrapper's output, or left at the component's own value when it is timing, a function, a React node, internal or a sound. Lists of colours are palettes and colour settings use the `color` widget. On themed elements a colour the component falls back to a theme token for (`prop ?? t.token`) is empty ("Theme") by default unless its default differs from that token, so the theme switch reaches it. Every element's exported component takes its settings exactly as stored, and does in its own file whatever its drawing code needs from them: its own background, centring and placement on the frame, and the conversions in `packages/video/src/lib/settings/shape.ts` (`nestedFrom`: flat keys into nested props, `listsFrom`: rows into one list per column with an all-empty column left out, `ticksFromWords`: yes/no cells, `treeFromPaths`: paths into a file tree). A themed element turns its theme value into its UI kit's provider: the warm kit takes the mode and the changed colours, the neutral kit the whole light or dark preset with the changed colours on top, since its components force light mode; an element with a palette of its own takes its preset for the mode with the changed colours on top (`{ ...PALETTES[theme.mode], ...theme.colors }`). Nothing outside an element reshapes its props; `packages/video/src/registry/framing.tsx` only marks what an implementation is (`component`, `presentation`, `sequencer`). Since a component has no defaults of its own, anything that draws an element for another node (Device frame's screen, the light-leak cut) builds its props from that element's full defaults with its own values on top (`meta.default_props`, then `element_props`), never a partial map. A `sound` setting on an element (with `<key>Volume`) never reaches the component: compile turns it into a music item on the node's own Mixer channel (`element_sounds`), and the component's own audio props are never settings. A prop that follows the kind of a file setting is declared with `kindProps` (`{ media: "src" }` on the text mask): compile sets it from `kind_from_path`, so a component never guesses a file's kind from its name. After changing elements, `bun run elements:render` (`crates/render/src/bin/render-elements.rs`) compiles every element, Opsis's own and the registries', with its defaults in Rust (captions through Captions from script, transitions between two solid colours) and renders its middle frame as a 480 px JPEG through the frame driver into `~/.cache/opsis-element-stills`, with the spec hosted on a file server that answers prepared files as an export's does; elements whose default is no file (image, video, animation, 3D model) render empty (it needs the engine in the dev data folder and `bun run film:bundle`; it isn't part of `bun run test` because shaders need WebGL), and a test checks every element's defaults pass its own schema. Opsis's own video code keeps colour literals only for internal fallbacks a finished film never shows (the full-page styles' `PAGE_BG`/`BLEED_BG`, empty-clip placeholders), shadows and the window frames; `packages/video/src/colors.test.ts` lists each one with its reason and fails on a new one. The grain gradient element mounts its shader with the blob shape's `clamp` bounds in order: the library's `clamp(0., 1., length(…))` is undefined, which graphics cards read as `min(1., …)` and Software drawing (export `gl: "swangle"`) as 1, so Grain dissolve drew no blobs there.

**Node cards.** Every visible node has a `description` and a `card` returning up to four `row(icon, text)` lines (`crates/compile/src/node.rs`), computed from interpolated params, run results, saved sign-ins, connected inputs (their lengths, takes, files, captions, session step types and style entry types) and the names of the actions and markers its `action` and `marker` settings pick (`CardInputs.names`, filled by `picked_names` in `crates/compile/src/cards.rs`, so a card says “Launch”, never an id); the editor shows the rows Rust sends with every compile (`cards`). Row icons are the `Icon` enum (`crates/types/src/cards.rs`, lucide names); `NODE_ICONS` in `apps/frontend/src/editor/icons.ts` maps every one of them, so the type check fails on a missing icon, and `icons.test.ts` fails when an entry isn't the lucide icon of its name. A node's own icon is its look (`NodeLook`, `crates/types/src/looks.rs`), set on its definition with `.look(…)`; an element's node takes its element's (each element's `.look(…)` on its entry), and the catalogue sends it with the node (`nodeLook` in `apps/frontend/src/store/catalog.ts`): a stroke-only glyph from any of the six sets (`GLYPH_SETS` in `crates/types/src/looks.rs`: `lucide:<key>`, `tabler:<key>`, `lucide-lab:<key>`, `hugeicons:<key>`, `iconoir:<key>` and `mynaui:<key>`, never a filled icon; pick the glyph that says the most across all of them, not the first set that has something close) and at most one hover animation, a `motion` (the `NodeMotion` enum) or a `morph` into another glyph. Animate a node only when the motion shows what it does (every transition and every text effect, the click, the drag, the morphs between two states); most nodes stay still. Every node has a look and two nodes may share a glyph only if they move differently (`crates/compile/tests/unit/looks.rs`); two glyph names whose drawings lie within half a stroke of each other everywhere count as the same glyph (`apps/frontend/src/editor/node-glyphs.test.ts`, traced with morphicons' `resampleIcon`), so the same picture can't come back under another set's name. Look-alikes drawn differently (two sets' winds) pass that check, so compare a new glyph with its neighbours by eye. `NodeBadge` draws it (`node-glyph.tsx`): the glyph data comes from `node-glyphs.generated.ts` (run `bun run glyphs:bundle` after changing a look; it reads the looks from the catalogue through the `editor-data` binary, reads each set from its own package (`scripts/lib/glyph-sets.ts`: Lucide's icon modules, Tabler's outline nodes, Lucide Lab's icon nodes, the free Hugeicons modules, Iconoir's regular and MynaUI's outline SVG files), keeps only each shape's geometry so every set draws with the badge's own 2 px stroke (Hugeicons, Iconoir and MynaUI are drawn at 1.5 px upstream), and fails on aliases, typos, fills, groups, any other attribute and a set whose licence isn't in `THIRD_PARTY_NOTICES.md` yet), morphs use `morphicons` with `reducedMotion="user"`, and motions are `motion` keyframes in `node-motions.ts` with the easing on each keyframe, played once when the node card or list row (`GLYPH_HOST`) is hovered and skipped under reduced motion. Cards show no picture: no stills, poster frames or live thumbnails; a node's output is seen in the Run panel.

**User-facing copy.** No library, tool or format names (Playwright, Chromium, FFmpeg, CRF, DPR, page.evaluate…) in node titles, descriptions, field labels, badges, toasts or error messages; the exceptions are Settings → Licences and About, which list what Opsis includes by name; technical settings go under `advanced`. Sentence case. Durations in seconds. Browser nodes are "actions", never "steps". Elements are described in words (`element_name`). The node's name (`node.label`) is also its camera, chapter and caption label. Categories keep their internal ids; display names come from `Category::label` (`crates/compile/src/node.rs`), sent with the catalogue. Element descriptions are on their entries. Element defaults never name a library and never load from the internet: neutral copy and `app:` placeholders (`public/placeholders`, `public/backdrops`). `crates/compile/tests/unit/nodes_c.rs` enforces descriptions and the banned words. Copy never names Tauri, Rust, Bun, CDP or any crate either.

**Editor panels.** The node list, Inspector and bottom panel collapse (Ctrl/Cmd+B, Ctrl/Cmd+Alt+B, Ctrl/Cmd+J, also in the View menu and the top bar); `apps/frontend/src/editor/panels.ts` owns their handles, open state and the active tab, and layouts persist through `useDefaultLayout`. A collapsed node list becomes a 44 px category rail with popovers. The bottom panel is **tabs**, not a split row: Timeline, Mixer, Run (Ctrl/Cmd+1…3, `dock.tsx`), Timeline by default. Any tab opens in its own window (`open_panel_window`, `crates/desktop/src/windows.rs`, route `#/panel/<name>`, bounds saved in the app database); closing that window docks the tab back. The Timeline has its own clock and nothing else: `TimelineClock` (`apps/frontend/src/editor/timeline/timeline-clock.ts`, mounted in the editor window) owns `usePlayback`, moves the playhead on animation frames at the shuttle rate, loops the film or the in and out points (`loopOf`/`wrapInLoop`, `apps/frontend/src/timeline/playhead.ts`) and plays only the film's master stem (`StemPlayer`, `apps/frontend/src/editor/stem-player.ts`: an `<audio>` through a Web Audio chain, kept within two frames of the playhead). Play and Space in the Timeline, the Mixer's meters, the camera field and the node rings all follow that playhead: the canvas rings the nodes whose span holds it (`activeAt` over the compiled `spans`, `setActive`) and the Timeline brightens the bars under it (`BarFrame`). Selecting a node moves the playhead to its start.

**Files play in the media player.** Videos and sounds in the Run panel and Replay, and the sounds in the Inspector's Files list (a made sound plays right below its node's settings), play through Dice UI's media player (`file-player.tsx`), never the browser's own controls; images there open full size in a dialog on click (`image-preview.tsx`).

**View state is per project, on this computer.** The active tab, panel sizes and collapsed panels, timeline ruler and snapping are saved in the app database's `view_state` table, one row per project and key. `open_project` returns the project's view with the workflow, and `loadViewState` puts it in the editor's cache (`apps/frontend/src/store/view-prefs.ts`), which `readPref` and the panel layouts (`layoutStorage`) read synchronously; `writePref` updates the cache and sends `set_view_pref`, which Rust broadcasts as `ViewPrefChanged` so every window's cache follows, and panel windows read it with `view_state` when their project changes. Nothing is saved while no project is open, and a project made again in the same folder starts with no saved view. A project with nothing saved opens with the defaults (Timeline tab). The main window's size and maximized state are saved per project too (key `mainWindow`, written by `crates/desktop/src/windows.rs` while a project is open, applied on open): a project with none saved opens maximized, and the start screen leaves the window as it is (1600×1000 at launch). Pop-out window bounds stay global.

**Starting and closing.** Settings → Starting and closing: on start show the start screen, open the last project, or open New project (once per app launch, `useStartup` in the main window's layout route `routes/_main.tsx`); and "Ask before closing". Closing or quitting the main window goes through `crates/desktop/src/exit.rs`: it prevents the close and asks the editor to show `ExitDialog` (in-app, never a native dialog, `ConfirmClose`). With asking on: "Are you sure you want to exit?" with "Don't ask again". With it off, it only appears when work is unfinished (a run, engine setup, font download, unsaved changes in the document, or a value still being typed in a field, which the editor reports with `report_drafts` from `useHeldDrafts`), without the checkbox; closing first asks the editor to hand those values over (`FlushSave`, `commitHeldDrafts`), then Rust saves. Unfinished work is always listed and the button becomes "Close anyway"; closing flushes the pending save and stops the run. Register new long app work in `AppState.tasks` (`begin(label)`/`end(label)`, `crates/desktop/src/state.rs`) so it's listed. The dialog answers `close_shown` as soon as it receives the request; if nothing does within 2 s (the window crashed or is showing an error), Rust saves and closes without asking, so a broken window can always close. Once a close is allowed, a window whose page dies or doesn't finish unloading within 3 s is destroyed (`close_even_if_page_dies`) and the quit goes on, so the app never waits on a dead page. Never hold a lock across a call that may take it again (the settings lock and `announce`, which reads the settings): a database lock held that way once hung the close. Render errors show `ErrorScreen` (`apps/frontend/src/app/error-screen.tsx`, the router's `defaultErrorComponent`, so every route has its own boundary and the root, the exit dialog and the title bar stay up): the app bar, Try again, Reload window and the message under Details. Components that read a node by id must handle it being gone: the Inspector's fading-out panel renders once more after a delete.

**App state is one database.** `<data folder>/opsis.db` (SQLite through `sqlx` with the bundled SQLite, WAL, foreign keys on, `crates/store`) holds settings (one row per section), every project ever opened (recent projects are a query: newest first, folders that still hold a project, first 20), each project's view state, window bounds and the font library index. Only Rust opens it (`AppState::db()`, a pool, so every query is async); windows go through commands. The tables are `crates/store/schema.sql`, plain SQL with snake_case columns, which the store embeds and runs on an empty database. Every query is a checked `sqlx::query!`/`query_as!`/`query_scalar!` macro against that schema; `.sqlx/` at the root is the committed offline cache and `.cargo/config.toml` sets `SQLX_OFFLINE=true`, so builds need no database. After changing the schema or a query, run `bun run db:prepare` (it needs `sqlx-cli` built with SQLite). The settings also live in memory in `AppState` (read with `settings()`, written only through `AppState::patch_settings`, one patch at a time), so handlers that can't wait, like the close request, read them without a query. Setup spawns the start (`open` in `crates/desktop/src/lib.rs`): it opens the database, registers every piece of state at once and then opens the main window, so no command runs before the state exists, and a failed start logs why and exits. Nothing blocks on the async runtime; the keyring is the exception that is made in setup itself, because the Linux Secret Service store blocks inside `zbus` and panics on a runtime thread. There are no migrations: the `meta` table holds the sha256 of that SQL, and a database made for another schema is deleted and made again at startup. Real migrations come with the first release. Projects stay plain folders: nothing about a project's contents goes in the database. The editor keeps nothing in local storage. Secrets use the OS keyring (`keyring-core` with the Apple, Windows and Secret Service stores, `crates/store/src/keys.rs`): sign-ins are sealed with AES-256-GCM under one key kept there, and saving refuses when the platform has no secure store.

**Settings is its own window** (`open_settings`, `crates/desktop/src/windows.rs`, route `#/settings?page=<page>`, bounds in the app database), opened from the menu, Ctrl/Cmd+, and any Settings button; it closes with the main window. A sidebar picks the page (`apps/frontend/src/app/settings/`). Its app bar has no menu; menu shortcuts pressed there go to the main window (`send_menu_to_editor`). Settings are written with `patchSettings` (one section at a time, so windows never overwrite each other) and every window follows them through `useAppSettings` (`apps/frontend/src/store/app-settings.ts`), which Rust keeps current with `SettingsChanged`. Saved results (clear cache) belong to the project, in the project Inspector.

**Projects folder.** New projects are suggested in `settings.projects.lastDir` (the last place one was created) or else the default folder: `settings.projects.defaultDir`, empty meaning `~/OpsisProjects` on every OS, like JetBrains' `~/IdeaProjects`. Changing the default clears `lastDir`. Open project starts in the default folder. The New project dialog shows the folder it will create (the `project_folder` command); started from a template card, it shows only that template with Change.

**The project file can change under the app.** Rust owns the open project (see Windows share one editor) and saves it itself, 800 ms after the last change (`schedule_autosave`, `crates/desktop/src/document.rs`) or at once on `save_project` and before a run, sending the file's `version` (a hash of its text) as the base; `ProjectFiles::save` refuses to write when the file on disk has another version. The document state says whether a save is coming (`saving`: set when an autosave is scheduled, cleared when a save ends and no newer one is due, `save_due`), so the top bar's pill reads Saving while changes wait for it, Unsaved only when changes have no save coming (a failed or refused save), and Saved otherwise. Rust watches the open project's file from the open (the folder is watched because saves replace the file) and ignores its own writes. With nothing unsaved it loads the outside change as one undo step and tells the editor (`ProjectReloaded`); with unsaved edits, an unreadable file, or a refused save, it asks (`DiskChangeAsked`), and `DiskChangeDialog` answers with `resolve_disk_change`: Load the file (undoable), Keep mine (saves over it) or, for an unreadable file, Wait. Nothing saves while that question is open. The files a project names can change under it too: after each compile Rust follows the exact files the film loads, every `project:` ref in the compiled values plus the project's font files and the project sources of prepared files (`project_refs_in`, `follow_loaded_files`), never the app's own `.opsis` files), compiles again and sends every app window each changed file's size and modified time (`ProjectFilesChanged`). The change names each file by every ref the film uses for it (`LoadedFilesWatch`, `crates/project/src/watch.rs`), and windows keep them as file versions keyed by ref (`useProjectFiles`): the editor's `useFileUrl` adds `?v=` to that file's address, so Timeline waveforms and filmstrips load it again. Renders never carry versions; their cache keys stamp files themselves.

**Local API.** Off by default; Settings → API switches it (`settings.api.enabled`, global and persistent, shown as an API badge in every app bar). `crates/api` serves plain HTTP with `axum` on `<data folder>/api.sock`, or the absolute path in `OPSIS_API_SOCKET` (mode 0600; a stale socket from a crash is replaced, a live one from another copy of the app is left alone and reported, and anything that isn't a socket is never deleted). Socket paths are capped at 100 bytes (`api_address`, `crates/api/src/address.rs`; the OS limits are 107 on Linux and 103 on macOS): a longer or relative path is refused before listening, and Settings → API says to set `OPSIS_API_SOCKET` to a shorter full path. There is no automatic fallback location. On Windows the variable is ignored and the API uses the named pipe `\\.\pipe\opsis-api-<user>`, never a TCP port (the current-user-only ACL is still to do). Without an open project it answers `/openapi.json`, `/status`, `/nodes`, `/nodes/{type}`, `/validate` and `/open`. Under `/project`, every request works on the document in Rust through `ApiHost` (`crates/api/src/routes.rs`, implemented in `crates/desktop/src/api.rs`): an edit is one `WorkflowEdit`, so one undo step, autosaved and shown in every window, whether or not an editor window is open. Rust checks bodies, node types, connections and settings before editing and adds the problems to every answer: the editor's own, from the run results and file checks (`ApiHost::problems`, `workflow_problems_with` plus `file_problems`). `/open` opens the project in Rust and asks the main window to show it (`OpenRequested`); runs start from the document like the editor's. Run events also stream on `/project/run/events`. The OpenAPI document (`crates/api/src/openapi.rs`, from the `schemars` schemas of the bodies) stays small (a test keeps it under 100 KB and checks every route is documented); node settings schemas come from `/nodes/{type}`. Validation is `check_workflow`/`workflow_problems`, the same checks the editor shows. Routes live in `crates/api/src/routes.rs`; add an endpoint to `openapi.rs` whenever you add a route.

**Canvas.** `settings.editor.canvasMode`: `mouse` (the default: wheel zooms, drag pans) or `touchpad` (two-finger scroll pans, pinch zooms), chosen in the canvas toolbar and remembered for every project. The minimap shows or hides from the toolbar, View → Minimap or Ctrl/Cmd+Shift+M, per project (`minimap` view pref). The React Flow attribution is hidden (`proOptions.hideAttribution`); the library prints a console note asking for a Pro subscription when you do. The document owns node positions and the UI store owns selection; React Flow's own per-node state (measured size, a drag or resize in progress) lives only in `useFlowNodes` (`apps/frontend/src/editor/use-flow-elements.ts`), merged over the store's nodes, so a drag writes one position at drag stop instead of one undo step per frame. The node list's group titles stay pinned while their group scrolls (sidebar list only). Tidy up layout (`apps/frontend/src/editor/layout.ts`) lays the top-level cards out with ELK from the handles each card shows, measured on the page (`measuredPorts`), or from the inputs worked out from the edges before a card is drawn, and every edge end is a port, so a numbered input past the catalogue's own is never missing. Edges are smoothstep paths: the edges entering one column each turn in their own lane where their runs overlap (`stepPositions`, `apps/frontend/src/editor/edge-lanes.ts`, worked out from the cards' live positions), and ELK spaces the layers to fit those lanes.

**Each window mounts only what it uses.** The root route (`__root.tsx`) holds only the outlet and the window border. The main window's routes (start screen, setup, editor) sit under the pathless layout `routes/_main.tsx`, which mounts menu shortcuts, menu navigation (`useMenuNavigation`; menu commands reach only the main window), the Local API's open requests (`useApiHost`), the start-up choice (`useStartup`) and `ExitDialog`. The editor route mounts the document and run mirrors; a popped-out panel mounts the document mirror, menu shortcuts and the run mirror only for the Run panel; Settings only menu shortcuts; the streamed views nothing, so their keys reach the page they stream. Add a hook to the windows that need it, never to the root.

**Windows share one editor.** The document lives in Rust (`opsis-document`, held by `AppState`'s editor state): every window edits it with typed commands, `edit_workflow` (`WorkflowEdit`: nodes, connections, settings, fonts, variables, paste, groups, mix, markers, replace) and `edit_timeline` (`TimelineEdit`), plus `undo`, `redo`, `begin_gesture` and `end_gesture`, and follows `DocumentChanged` (the document and the nodes the change edited, whose old run errors the editor forgets), taking `document_state` when it mounts (`useDocumentMirror`). `useWorkflowStore` is only that mirror; `workflowEdits` (`apps/frontend/src/store/workflow.ts`) sends the edits. A gesture (a drag, a text field being typed in, an open colour picker) is one undo step, nested gestures count as one, and undo or redo closes an open gesture. After each change Rust compiles again (`compile::request`, at most one compile running and one waiting) and sends `Compiled` to every window; windows say which node is selected and inspected with `set_compile_focus`, take `latest_compile` when they mount (an event sent before their listener is registered would be lost) and drop a result older than the newest they have seen (`seq`). The rest that windows share lives in Rust too (`crates/desktop/src/shared.rs`, `sync.ts`): the selection and the Timeline's playhead, written with `share_selection` and `share_playhead`, followed through `SelectionShared` and `PlayheadShared` (each names the window it came from, which ignores its own) and read with `shared_state` when a window mounts. The playhead runs in the editor window, which shares every frame; other windows share only their in and out points and send play, pause, seek and rate to it with `control_playback` (`PlaybackCalled`). Menu commands go to the editor with `send_menu_to_editor` and Replay with `show_replay` (`ReplayRequested`), so a popped-out Run panel opens it there. Opening another project clears the shared selection. Live recording frames and live events (only the recording browser's, during Record take and Screenshot) go only to the windows that watch them, each with `watchLive` (`watch_live`, its own `Channel`), stopping with `unwatch_live`, which removes only its own channel (a destroyed window's channel goes too); Rust sends `LiveNoted` only to those windows. Two places show the stream and only one watches at a time: the editor's picture-in-picture (`LivePip`) and the Live window (`open_live_window`, route `#/live`, label `live`, bounds saved like the pop-outs, closed with the main window), which is only the live picture with a LIVE badge (`LiveBadge`, the `--live` token) and keeps no history. The PiP's enlarge button and its picture open the Live window; once the window watches, Rust tells the editor (`LiveWindowWatching`, `live_window_watching`) and the PiP stops watching and hides, and when the window closes the PiP watches again and shows (two streams only while switching). The PiP shows the LIVE badge too. Commands and events are declared once in Rust (`crates/desktop/src/bindings.rs`, tauri-specta) and the editor calls the generated `commands` and `events` from `@/generated/bindings` directly (commands return their value and throw their error, `ErrorHandlingMode::Throw`), with `on` (an event to this window, returning its unsubscribe), `frameChannel`/`readFrame`, `watchLive` and `pathForFile` in `apps/frontend/src/app/tauri.ts`; capabilities (`crates/desktop/capabilities`) let only the editor, its panel windows, Settings and the streamed views call them. Engine set-up progress, settings changes and API status go to every app window.

**Timeline.** `flatten_spec` (`crates/compile/src/timeline/flatten.rs`, sent with every compile as `flat`, with each bar's local frame at every timeline frame for drawing filmstrips and keys, `localFrames`, `VideoBar::local_frames`) turns the compiled spec into bars on lanes (greedy packing in drawing order), audio bars, transitions and action marks, mapping frames through trims, loops and speed remaps. Edits never touch the spec: compile records `handles` (`move`, `trimStart`, `trimEnd`, `speed`, `volume` as `ParamRef`s) on items, and container children carry a `slot` (container node + port). `TimelineEdits` (`crates/compile/src/edits/timeline.rs`) applies an edit to the owning setting or, when nothing owns it, inserts a named node ("Delay from timeline", "Trim from timeline", "Speed from timeline", split parts) at the slot edge or right after the clip; ripples, rolls, splits, volume, camera keys and the removal of selected clips (`timeline_removal`) live there too. The editor only snaps (pixels, beats, markers, the playhead) and sends the snapped delta as a `TimelineEdit` naming the bar by its key. A drag is a gesture: each move applies to the workflow at the gesture's start, against the timeline Rust last sent when the gesture began, with ids salted by the gesture so an added node keeps its id from move to move. Every handle has a round-trip test in `crates/compile/tests/unit/timeline_edits.rs`; add one when a node gains a handle. Keyframes are an `envelope` setting (`crates/compile/src/envelope.rs`, frames local to the item) shown on the timeline and in the Inspector (`envelope` widget). Rust applies every keyframe and camera key edit (`KeyframeEdit`, `apply_keyframe_edit` in `crates/compile/src/edits/keyframes.rs`): the Inspector sends it as a `WorkflowEdit`, the Timeline as a `TimelineEdit`, so a drag applies to the keys as they were when it began; keys are found by their stored position, values are kept in the track's range and frames whole, and the keys are sorted after every edit. The tracks' labels, ranges and rest values, the easing names, the camera dials (which also give `CameraKey` its schema ranges) come in the catalog as `timeline` (`TimelineBook`); the editor only draws them and checks a value's shape; they compile onto `TimelineItem.envelope`/`AudioItem.envelope` and stay pure functions of the frame.

**Mixer.** Mix settings are `workflow.mix` (`crates/types/src/mix.rs`): a strip per channel (keyed by node id: Music, each Sound effect, each clip with sound), buses (Music, Effects, Clips built in, plus user buses) with sidechain ducking, and a master with EQ, compressor, limiter and loudness target. Removing nodes prunes their channels (`remove_nodes`, `crates/compile/src/edits/workflow.rs`; `Workflow::normalized` on open and replace). `build_mix_plan` (`crates/compile/src/mix/plan.rs`) and the FFmpeg filter graphs (`crates/media/src/mix/graph.rs`, tested by string) are pure; `crates/media/src/mix/render.rs` renders channel, bus and master stems into `.opsis/cache/mix/` (content-hashed, recent plans kept), with per-frame peak/RMS, compressor gain reduction and EBU R128 loudness. Exports always play the master stem (`with_master_stem`): the render executor draws the picture once without sound into `.opsis/cache/pictures/<pictureKey>` (`crates/render/src/picture.rs`; the key leaves out the spec's audio, mix and asset address; recent pictures kept) and adds the master stem with FFmpeg (`mux_args`, `crates/media/src/codecs.rs`), so a mix or sound-only change never renders the picture again. Bump `PICTURE_VERSION` (`crates/engine/src/versions.rs`) whenever how a spec is drawn changes (anything in `packages/video` that the spec doesn't record): it keys the saved pictures and every render-phase node's cache key, so exports are made again. The Timeline plays the latest stem for its film; a stem player applies the mixer drags made in its own window at once through its Web Audio chain (`applyMixerDrags` in `stem-player.ts`), so the Timeline's sound follows a docked Mixer's drags before the new stem is ready. The ranges, defaults, built-in buses, loudness targets and strip presets are Rust's (`mixer_book`, `crates/types/src/mix.rs`), sent in the editor catalog as `mixer` and read with `mixerBook()`; each channel's bus, strip and whether it is heard come from the mix plan, and the compile result carries the resolved mix and whether solo is on. Mute and solo are saved and apply to exports. Strip selection is the editor's node selection (Ctrl/Cmd-click toggles, Shift-click takes the range in strip order); a strip menu on a selected strip applies to every selected strip in one `MixEdit`, so it is one undo step. Bump `MIX_VERSION` (`crates/media/src/mix/render.rs`) when stem output changes.

**Results follow the keys.** Compile hands each node its last result, so after every compile the app works out every executing node's key (`refresh`, `crates/desktop/src/node_results.rs`, through the runner's `hash_nodes`): when a node's result was made under another key and `.opsis/cache/<key>` holds one for the current key, that result takes its place (undo brings the earlier result back), and one that still doesn't match goes in the compile's `outdated`, which the node card shows as a Changed badge and the Run panel as Changed since the last run. While a gesture is open (typing in a field, a drag) compiles keep the keys worked out last (`held`), and only the problems of unreadable files are refreshed, with no hashing and no file checks; closing the gesture compiles again with fresh keys. A Media file whose key has no result is checked without a run (`check_media_files`): the same `check_media_file` the run uses (`crates/media/src/executors.rs`) reads its kind, length, picture size, byte size and frame rate, and the result is saved under the key, so the next run reuses it and the card shows what it read; a file that isn't a video, image or sound is a warning on the node until the file changes, one that can't be opened (a folder, no permission) is a warning checked again every 10 s (`FileCheckError`), and a missing one is "Not in the project folder" (`missing_files`). Results and checks land only in the project they were made for (`adopt`), and a change in the engine's status compiles again. The Media file node uses its result only while its path names that file.

**Run state.** Rust keeps the whole run view (`RunView` and the capped log, `RunHost` in `crates/desktop/src/run.rs`) and applies every run event with one reducer, `apply_to_view` over `apply_run_event` (`crates/runner/src/progress.rs`); windows mirror it (`useRunMirror`, `apps/frontend/src/store/run.ts`) from `run_state` when they mount and `RunViewChanged`, `RunLogged` and `RunStateReset` after, dropping a view older than the one they show (`seq`). Opening a project seeds the view from its last run (`seeded_view`: each node's newest trace, failed or not, and failures newer than the node's last result), unless that project is the one running, which keeps its live view; clearing the cache seeds it empty, and an edit forgets the errors of the nodes it touched. A run clears status, progress, errors and traces only for the nodes it includes (`run:start` `nodeIds`), so a **Run this** never hides an earlier failure; `run:done` names `failedNodeIds` and `skippedNodeIds` apart, and the panel shows each failed node as a link. A run that ends while the main window isn't focused says so in a system notification, sent from Rust (`notify_finished`, `crates/desktop/src/run.rs`); the plugin's page script asks whether notifications are allowed in every window that loads, so the default capability allows `notification:allow-is-permission-granted` and nothing else of it. The panel's exports list comes from the results of every `output.*` node, newest first (`exported_artifacts`, sent as `exports`), not from the last run's `outputs`.

**Chapters in exports.** `film_chapters` (`crates/compile/src/timeline/chapters.rs`) reads the Chapter action marks from `flatten_spec`, starts the first at 0:00 (or adds an "Intro" chapter when the first starts 10 s or more in) and merges chapters under 10 s into the one before, YouTube's rules. Export video writes them as FFmpeg chapter metadata in the finishing copy (`finish_args`, with the web-ready move), so a chapter change never renders the picture again; GIFs get none. The optional `.youtube-chapters.txt` needs at least three chapters.

**Click action.** Click presses the left or the right button (`ClickButton`; the input layer presses any `MouseButton`, the type the streamed views use too) and, for the left one, can double-click: two presses at the same point, the second with click count 2, so the page fires `dblclick`. The action logs `button` (right only) and `tSecondDown`, and the cursor squashes and rings at each press, a right click's ring hollow (`cursorAt`, `packages/video/src/camera/lib/cursor.ts`).

**Drag action.** `browser.drag` drags onto an element (measured again after the press, failing when it isn't on screen), by an offset, or along a path; the smooth method presses, waits `holdMs`, nudges 6 px (pages start drags past a threshold) and walks the points with the same 8 ms sampler as glides (pure curves in `crates/capture/src/drag_path.rs`; glides must keep their exact samples). The action logs `tDown`, `t` (the release), `path` (at most 64 points) and `drop`; `toClickLog` (`packages/video/src/camera/action-log.ts`) makes one camera event covering both ends when they fit in half the window, else a pick-up and a drop event, and `cursorAt` keeps the arrow pressed until `tUpMs`. The baked cursor follows `dragover` too. The picker's Shift-click returns a spot as `x, y`, in a window sized to the take's browser.

**One engine.** Capture, the streamed views and film renders launch the same Chrome Headless Shell: the version pinned in `crates/engine/src/downloads.generated.json` for the platform (Google's Chrome for Testing build on every platform), by sha256 and size (`bun run engine:downloads`). The app ships no browser. Settings store it as a path (`settings.engine.browser`, with its version, sha256, size and modified time), and nothing else locates it: Settings → Engine either downloads it into `<data folder>/engine` (`crates/engine/src/install.rs`) and saves that path, or saves a browser the user chooses. Either way the same full check runs before the path is saved (`crates/desktop/src/engine.rs`): the browser answers `--version` and opens a page over CDP when started headless (`check_browser`, `crates/capture/src/browser.rs`). A failed choice leaves the saved browser as it was. At start the saved browser's size and modified time are compared (`verify_on_start`); a changed one is hashed, and only a different hash runs the full check again, so a moved or replaced file shows as a problem in Settings. A browser of another version than the pinned one is allowed with a warning. Engine status is complete when the browser is ready. `settings.engine` is written only by Rust (`RUST_ONLY_SECTIONS`, refused by `patch_settings`), and runs and views take the browser that passed (`engine_files`, `EngineFiles`). Never fall back to Playwright's browsers, the system Chrome or the webview for capture or render. Capture keeps Playwright's launch switches, injected page script, clock and keyboard (`crates/capture/src/playwright/*.generated.*`) but talks CDP itself; `playwright-core` is only a dev dependency, for `bun run playwright:scripts` and reading the Chromium credits. FFmpeg is not part of the engine: the app ships it as the `opsis-ffmpeg` sidecar (see Packaging), the ffmpeg-static b6.1.1 program pinned per target in `scripts/lib/ffmpeg.generated.json`, and users can't choose their own. `EngineFiles.ffmpeg` is `bundled_ffmpeg()`, so analysis and mixing need no setup. Nothing checks it at run time: `check_ffmpeg` (`crates/media/src/capabilities.rs`) is the contract a replacement program must meet, run as a test on the staged program (`bun run test:rust`) and on every CI build runner: every encoder, decoder, format and filter Opsis uses (`REQUIRED_*`; a test fails when a golden filter graph uses one the list lacks), and a configuration line with `--enable-gpl --enable-version3` and without `--enable-nonfree`. Nothing reads media through ffprobe: `opsis-probe` reads it in Rust.

**Capture timing comes from frames, not markers.** Screencast JPEGs go into `FrameEncoder` (`crates/capture/src/encoder.rs`) through `offer`, which never waits: Chrome sends the next frame only after the last one is acknowledged, so waiting on the encoder loses any page change painted during an encoder stall. Encoder errors surface at `finish`. The encoder writes a constant-rate stream from the first frame after the setup steps; action timestamps share that origin. Live frames for the editor PiP are the same frames, throttled to the live fps setting, sent as raw bytes over a `Channel` to each window that watches them.

**Smooth takes.** Record take's **Timing** (`timing`: `real`, `smooth`) picks how a take keeps time, and every wait and time source in a take goes through the tab's take clock (`TakeClock`, `crates/capture/src/take_clock.rs`, `tab.clock()`): `now`, `wait`, `sleep_until` and `until` for polls, never `tokio::time::sleep` or `Instant` in take code (the cursor, input, selectors, page lifecycle, overlays, the trace and the take itself all use it). The clock keeps whole time: `now` is a `Duration` since the Unix epoch, a stepped clock counts whole frames at its integer frame rate (`frame_time`, `frames_in`), timeouts are deadlines compared with `now`, and a time becomes milliseconds as `f64` (`as_ms`) only where it leaves Rust: the page clock, the encoder, the trace and the action log. On the real clock they sleep and poll. At Start recording a smooth take switches the clock to steps (`Smooth`, `crates/capture/src/smooth.rs`): the screencast stops, the page clock is held paused in the top frame (`Clock::hold_for_frames`) and every CSS and web animation gets rate 0 (`Animation.setPlaybackRate`). Each step moves the page clock and every running animation of the page, its same-origin frames and the take's own overlays (chapter cards, action labels, in the closed shadow root of the injected script: `STEP_OVERLAYS`) on by one frame (`STEP_FRAME`, in whole milliseconds that add up to the frame times, `page_ms`), keeps the page time for the next document (`page_time_for_new_pages`, one init script replaced each step), takes the frame's picture and offers it to the encoder and the live view at the step's time, so every frame is its own picture and action times, trace calls and page addresses fall on frames. A wait is whole frames and at least one, `sleep_until` takes none for a time already passed, and waits that overlap share their frames. **Frame pictures** (`pictures`, shown for smooth takes only): Every picture is the window's region of the page (`clip`, placed by the scroll position the step reports) at an explicit scale, because a plain screenshot comes back at the page's pixel ratio: Standard is a JPEG at the window's size (scale 1 ÷ pixel ratio), like the screencast; Lossless is a PNG at that size (the encoder reads `FrameImage::Png`); Full detail is a JPEG at the page's pixel ratio (scale 1). A 30 s take of a busy 1920×1080 page at 2× took 36 s with Standard, 62 s with Lossless and 149 s with Full detail. The browser runs a smooth scroll on its own frame clock, which neither the page clock nor the animation rate reaches, so a smooth Scroll to element in a smooth take works out where each scrolling box ends (`PLAN_ELEMENT_SCROLL`, an instant `scrollIntoView` undone at once) and moves them there a frame at a time with the camera easing (`STEP_ELEMENT_SCROLL`); wheel scrolls are instant in the headless shell, so Scroll by already moves a step per frame. On a held clock, nothing the page itself waits for happens between steps: a page script that awaits a timer never ends, and server replies, videos, canvases driven by real time, workers and other-origin frames keep real time.

**Interactive browsing is streamed.** The element picker and Sign in are pages in the headless shell (`crates/stream`: `pick`, `sign_in`), streamed to a window of their own at route `#/view/<id>` (`StreamView`, `apps/frontend/src/app/stream-view.tsx`): frames arrive as raw JPEG bytes over a `Channel`, mouse, wheel, keys and text go back as `view_input`, the page keeps its own size and the input is mapped through the letterboxing, and dialogs, file choosers and popups are answered from the window. Sign-in state is kept as storage-state JSON and sealed (see App state). Sign in (`browser.signIn`) is an ordinary executing node in the action chain: its executor opens the view, the size of the session's browser, only when the sign-in named in Save as isn't saved yet or the node is run on its own (`forced`), and its step in the take adds the saved cookies and, per origin, the page storage (an init script, plus the current page when it is that origin). Its executor is stamped (`sign_in_stamp`, `crates/capture/src/executors.rs`): the saved sign-in's file stamp goes into the node's cache key, so a new sign-in runs every take after it again; the runner works the keys out again as soon as a stamped node has run (`rekey`), so a take recorded right after a new sign-in is saved under its new key and the next run doesn't record it again. A take that lands on the Sign in step's address fails with "Signed out during the take. Run “<name>” again."; nothing retries across nodes. The sign-in finishes on an address change or a selector, in single-page apps too.

**Traces** are recorded per capture unless retention is `off`, in our own format (`crates/traces`): per take a zstd JSON manifest (header, viewport, actions with their node ids, console, page errors, requests) and its frames as content-addressed JPEG blobs in `.opsis/traces`, shared across runs and pruned by the retention setting. Blob files keep their extension (`<sha>.jpeg`) so screenshots load straight through the file server. The Trace tab in Replay (`TracePanel`) is our own shadcn UI over `read_trace`; never embed Playwright's Trace Viewer.

**Nothing uses the internet unless the user asks.** The app works offline. Anything that needs the network (setting up the engine, getting fonts online) sits behind a button and asks first, and what it downloads is saved locally (`<data folder>/engine`, `<data folder>/fonts`). Never load fonts, images, scripts or sounds from a remote URL at render time. User-facing copy never names the services behind it.

**Fonts.** 16 families (Latin, all weights, italics where they exist, about 1 MB) are bundled from Fontsource into `public/fonts/bundled`. The user's library lives in `<data folder>/fonts` (the files, `library:` refs to the file server) and the app database's `fonts` table (one row per family; a row that no longer parses is kept as it is) and is filled from font files or ZIPs (`crates/fonts`: `skrifa` reads names, weights and italics, one file per style, variable and woff2 first), fonts installed on the computer (`fontdb`, `installed_font_families`), or Fontsource online. A project copies the library fonts it uses into `assets/fonts/<id>/` and lists them in `settings.fonts.families`, so it works anywhere. `settings.fonts` also holds the roles `main`, `heading` (empty = main) and `code`. Rust works out which family every font name means (`family_for`, `crates/compile/src/fonts/mod.rs`): `df-main`, `df-heading` and `df-code` point at the role fonts, `Inter` follows `main` and `JetBrains Mono` follows `code`, so every element follows the project fonts, and per-node fonts (the `font` widget, stored as a family name, turned into a CSS stack by `font_stack`) are found by name. Each spec carries that table (`FilmFonts`, built by `film_fonts`: every name a film can use, lowercased, and the names to load first, the roles and every font its items name); the page's `FontProvider` and `fonts/registry.ts` only look names up in it and register the faces. 3D text picks its face from the same `family_for`. The editor's font picker gets its groups, previews and stacks from `font_choices`, the library from `list_fonts` (each a `FontChoice`), and the online list says which fonts are already there (`added`). An element whose component draws with a family its settings don't name declares it on its definition (`.fonts(&["Caveat"])`), and a film that uses the element loads it first (`used_font_names`); a test fails on a declared family that isn't bundled. Elements never load fonts themselves: no font loader packages, no `@fontsource` stylesheets, no `@font-face` of their own, because with every element loaded on every page such a rule would apply to all of them. Export cache keys include the project settings, so changing fonts re-exports.

**Element time and size.** Elements whose entry has `.authored_clock` count time on a clock of 30 frames a second: their code reads `useAuthoredFrame()`/`useAuthoredConfig()` (`packages/video/src/core/authored-clock.ts`) instead of the runtime's `useFrame()`/`useFilm()`, and a `<Sequence from>` inside them takes `useRealFrames()`, so a 60 fps project plays them at their own speed. Their timing settings counted in frames are stored as seconds with `x-frames-at: 30`, and compile turns them back into frames (`frames_from_seconds`, also inside rows and comma lists). An element's Length defaults to 0, "Fit the animation", when `crates/compile/src/elements/lengths.rs` knows how its animation ends (`element_timing`, checked against the elements' own length helpers by `packages/video/src/registry/lengths.test.ts` through `length-cases.generated.json`) or when it runs on the 30 fps clock; `animation_length` keeps the designer's hold after the last animation. Elements laid out in fixed pixels carry a `design` size (1920×1080 in their entry) and draw in a box of that size scaled to fit the frame (`DesignBox`), so other shapes and 4K keep them whole and in proportion.

**3D elements** (in `elements/` like every other; their stage, loaders and motion are in `packages/video/src/three`) draw on `@react-three/fiber`'s `Canvas` through `Stage3D`, which never runs fiber's frame loop: after each commit of the scene it draws once, at the film's size, and holds the render until that frame is drawn (`useDrawnScene`). Every pose is a pure function of the frame: oxlint bans `useFrame` and `opsis/no-three-clock` bans three's clocks and animation loops. Model animations call `mixer.setTime`, never `update`. Assets load through `useHeldLoad`, which releases its hold only after the loaded value has rendered, so a still is never captured between a load and the canvas it mounts. 3D text, models, SVG logos and textures load prepared files (see Prepared files): the element only fetches an address. Model import copies a model's side files into `assets/models/<name>/` and refuses paths outside its folder or on the internet (`crates/project/src/model.rs`). The 3D screen shows its clip as a page layer placed with `matrix3d` from `project.ts`; with **End facing the camera** its last pose fills the frame exactly, so it cuts pixel for pixel to the same clip. Camera keys are the `camera` param, active when the element's motion or move is Keyframes; compile puts them on `TimelineItem.camera`, `flatten_spec` turns them into `cameraKeys` marks, and the Timeline moves them with the `cameraKey` timeline edit.

**Footage comes from Rust.** Every video the film shows (recordings in every style, the Video and Video loop elements, and the file settings whose kind is video, through each element's `kind_prop`) and every graded image is a footage use (`footage_uses`, `crates/compile/src/footage.rs`: the file, its `FootageChain` and, for Video and Video loop, the trim and loop), named by a hash of all of it. `hosted` gives each use its address under `.opsis/footage/<id>/` (a recording's `screen.footageUrl`, an element's `footageUrls` keyed by the file setting), and the render executor registers the same uses with `opsis-footage` beside the prepared files (`film_footage`, `crates/render/src/footage.rs`). The page shows each frame with `FootageFrame` (`packages/video/src/core/footage.tsx`): the time in microseconds after the address, the render held until the picture has decoded, a frame that fails ending the render with the server's message. Footage has no sound; a clip's sound comes from the mix. A footage chain is a grade and redactions: Grade footage (`effect.gradeFootage`, `clip + grade → clip`) appends a grade's steps to the footage of every recording, video and image in a clip, and Redact take (`effect.redactTake`, `recording → recording`, Redact's settings with From and Until, areas drawn on any frame of the take) appends a redaction that stays on the page as the camera moves. The window, backdrop and every other layer keep their colours; Apply grade on an exported file grades everything. The Mac cursor (`pointer.look.shape === "mac"`) reads the page's own cursor keyword while recording a synthetic cursor: once when a glide settles and after each click, stored as `c` on the cursor sample, keywords only (a `url()` cursor is never loaded); the film draws each keyword with apple_cursor's macOS set (`mac-cursors.generated.ts`), an unknown keyword as the arrow and `none` as nothing.

**Prepared files.** Work the video would repeat in every render tab is done once in Rust (`crates/prepare`) and kept: 3D text typefaces (the face is picked in compile like the page picks it, then `wuff` and `skrifa` draw its outlines at the weight into three.js typeface JSON, checked against `fixtures/prepare/typefaces.json`), 3D models (`draco-gltf` decodes Draco and meshopt meshes into a plain GLB with every image packed in, so the page uses a plain `GLTFLoader`), SVG logos (flattened by `usvg`) and textures (images over 4096 px on the long side are made smaller; others are served as they are). Compile turns those settings into `prepared:<kind>/[weight/]<project|app>/<path>` refs (`PreparedRef`, `crates/compile/src/asset_ref.rs`; `prepare_props`), `hosted` turns them into `.opsis/prepared/<path>` on the spec's project base, and the render file server answers that path (`prepared_routes`), preparing the file on first request into `.opsis/cache/prepared/<sha256 of the path, the source's size and time and PREPARED_VERSION>`. Bump `PREPARED_VERSION` (`crates/engine/src/versions.rs`) whenever a preparer's output changes: it keys the prepared files, the saved pictures and every render-phase node. `crates/render/tests/three_stills.rs` (ignored; needs the engine and the bundle) renders the 3D elements and compares them with `fixtures/prepare/stills`.

**Image nodes** (`crates/compile/src/nodes/image.rs`, executors in `crates/image`, category Image): Resize image, Crop image, Rotate and flip, Adjust image, Blur and sharpen, Place image, Image format, Redact (large pixels, a blur or a solid colour over areas drawn on the picture) and Spotlight (everything outside the drawn areas darkened or blurred, through a soft mask with rounded corners, `lit_mask`) Trim empty edges (cuts the margins that match the top-left pixel within a tolerance, `content_rect`) and Make a colour transparent (a picked or the corner colour faded out by distance with a soft edge, only where it touches the edges unless asked, `clear_colour`) and Outline (a ring the chosen width around every visible pixel, from a distance transform of the alpha, with a soft edge and a drop shadow on a canvas grown to fit, `outline_padding`; it warns when the image has nothing see-through) and Tilt (the corners turned, tilted and leant in 3D and seen from twice the long side away, `tilt_corners` and `tilted_size`, then a projective warp with a soft shadow) and Auto levels (each channel mapped by its own histogram or one shared by all three: stretched between the levels past a clipped share, or evened out along the cumulative histogram, mixed back by strength) and Grid (any number of images through the numbered `in` family, laid out by `grid_plan` in one row, one column or a grid, at the same height, the same width or in equal cells, never enlarged) and Before and after (a second file port, `after`; split by a divider at a position and angle, both pictures at the before's size, or side by side at one height or stacked at one width with the divider between, `before_after_plan`; labels in rounded boxes in the project's main font or a chosen one, drawn by `crates/image/src/text.rs`: the face picked like 3D text's, `family_for` and `face_for`, WOFF and WOFF2 unwrapped with `wuff`, the weight set on a variable font, and `ab_glyph` for the outlines) and Magnify (an area shown enlarged in a circle or rounded box with a border and a line to the outlined spot; **Size from** picks which two of the area, where it shows and the zoom are set, and `magnify_plan` works out the third, grows two boxes of different shapes to the view's proportions, makes a circle cover the whole area drawn but stay inside the box drawn for the view, grows a view drawn smaller than its area so it never shrinks, and keeps the result inside the picture) and Compare screenshots (two captures of the same size; pixels whose channels differ past the sensitivity's threshold, `compare_threshold`, are dilated by the padding so nearby changes join, labelled into areas and boxed on the after when the change itself is at least the smallest size, `changed_boxes`; a second output, `differences`, holds only the changed pixels, and the count is the result's `Measured::Changes`, shown on the card and in the run log) and Annotate (arrows, boxes, ovals, numbered steps and text in a list of marks edited with the `marks` widget; each mark is drawn in Rust from its own coverage over its bounding box, `crates/image/src/marks.rs`, steps count up in list order, and text and step numbers use the mark's font at its weight like Before and after's labels) and Frame screenshot (the Backdrop node's background choices, flattened in as `BackdropStyle`, with gradients painted by `paint_gradient`, padding, anti-aliased rounded corners, a soft shadow and a shape the background grows to, `framed_placement`). Their inputs are file ports, so imported pictures, screenshots and grabbed frames all connect, and they output an image. Every image is loaded upright (its EXIF orientation applied) and in sRGB (an embedded ICC profile converted with `moxcms`), keeping 16 bits and transparency; between nodes it is a PNG, and Image format makes PNG, JPEG (see-through parts filled with a background), lossless WebP or AVIF. Areas drawn on a picture become pixels through one function (`area_rect`, kept inside the picture), and operations that change pixels keep a 16-bit picture 16-bit (`on_each_depth`). The sizes a node makes are pure functions (`resized_size`, `crop_rect`, `rotated_size`) shared by the executors and the cards, which warn when an image is enlarged more than 2× or a crop leaves under 64 px. Their Inspector picture is the connected input.

**Elements load eagerly.** `ELEMENTS` imports every implementation, and `DemoTimeline` looks each one up synchronously (`resolveElement`, `packages/video/src/registry/index.ts`); a page that opens loads them all once.

**Asset refs are host-independent.** Specs hold `project:<relative path>`, `prepared:` or `app:<public path>` refs, and only Rust reads them (`crates/compile/src/asset_ref.rs`). Before a spec goes to a page, `hosted` (`crates/compile/src/hosted.rs`) gives every `project:` and `prepared:` ref, and every font face, its address on that host from `assets.projectBase`: the render asset server (`render_target`). The page only turns `app:` into `staticFile()` (`assetUrl`, `withAppFiles` in `packages/video/src/assets.tsx`). The editor loads every file through the desktop file server (`crates/desktop/src/file_server.rs`), which takes the ref itself (`fileUrl` in `apps/frontend/src/editor/file-url.ts` only encodes it): plain HTTP on 127.0.0.1 under a token made at each launch, with ranges, never a custom URL scheme, because WebKitGTK can't play video or audio from one (tauri-apps/tauri#3725). `reveal_in_folder` takes a ref too. Exports must stay readable like any file the user makes: atomic writes keep the umask's mode (`partial_file`, `crates/engine/src/files.rs`).

**Cache keys.** A node hash is `sha256(ENGINE_VERSION, type, interpolated params, upstream hashes)`, plus the size and modified time of every project file its settings name (`file_stamps`, so a file replaced in place runs again) and, for render-phase nodes, the project settings, the variables (a node such as Choose by variable reads their values directly), the mix, `PICTURE_VERSION` and `PREPARED_VERSION` (`crates/runner/src/keys.rs`). An executing node that reads the project's width, height or frame rate sets `uses_project_size` so those are in its key too, and one that draws text in the project's fonts sets `uses_project_fonts` so `settings.fonts` is. An executor whose output depends on something outside its settings and inputs adds it with a stamp (`Executor::stamped`, `crates/runner/src/context.rs`), read when the keys are worked out; executors are an `Executor` (the run and an optional stamp), registered by node type. Node keys and picture keys also hold the app's version, and node keys the recording browser's hash (`Release` in `crates/runner/src/keys.rs`), so a new release or another browser runs everything again (the bundled FFmpeg changes only with a release); between releases, bump `ENGINE_VERSION` (`crates/runner/src/keys.rs`) whenever an executor's output format changes. Every key that picks a file on disk is a sha256 (`versioned_hash`, `crates/engine/src/hash.rs`); the 64-bit `lookup_key` (`crates/compile/src/mix/plan.rs`) only matches values in memory, such as a mix plan to its result. Cached JSON is read into typed structs (`read_json`, `crates/engine/src/files.rs`), never trusted as-is.

**No old formats.** Nothing has been released, so there is no migration or fallback code for older project files, settings, engine folders or caches: when a format changes, change it everywhere, write `examples/` again (`bun run examples`, `crates/project/src/bin/write-examples.rs`, from `examples()` in `crates/project/src/templates.rs`) and delete local test projects. A test opens every example and fails when one isn't what the templates write today; the formatter leaves `examples/` alone, so they stay exactly as the app saves a project.

**Packaging.** `bun run make` (extra arguments go to `tauri build`, for example `-- --bundles deb`) runs `bun run stage` and then `tauri build --config tauri.release.conf.json` in `crates/desktop`. There is one build: it ships FFmpeg as a sidecar and never the recording browser (see One engine). Locally, build the deb only, cap cargo with `CARGO_BUILD_JOBS` and put the output in the cache (`CARGO_TARGET_DIR=~/.cache/opsis-build`); CI builds every format.

- `scripts/stage.ts` builds the film page without source maps (`bun run film:bundle --mode release`), fills the gitignored `resources/` with the browser's Chromium credits (`resources/engine-licences/LICENSES.chromium.html`, read from `chrome://credits` by `writeChromiumCredits` in `scripts/lib/engine.ts` through `playwright-core`, in Chrome for Testing of the version `install-engine` downloads into `~/.cache/opsis-stage-engine`, unpacked with `@zip.js/zip.js` into `~/.cache/opsis-chromium-credits` keeping the macOS app's symlinks and executable bits, `scripts/lib/unzip.ts`) and stages FFmpeg again (`stageFfmpeg`, `scripts/lib/ffmpeg.ts`, checked against the pins' sha256 and size): the pinned ffmpeg-static program for the host target (`rustc -vV`) as `crates/desktop/binaries/opsis-ffmpeg-<target triple>[.exe]` and its licence as `resources/LICENSE.ffmpeg.txt`.
- FFmpeg is a Tauri sidecar: `"externalBin": ["binaries/opsis-ffmpeg"]` in `tauri.release.conf.json` only, so `tauri dev` and the e2e build compile without the file. The bundles put it beside the main program with the triple removed (the deb in `/usr/bin`, the macOS app in `Contents/MacOS`, Windows in the install folder). It is named `opsis-ffmpeg`, never `ffmpeg`, because the deb would otherwise clash with the distribution's `ffmpeg` package. The app starts it with its own process code (no shell plugin): `bundled_ffmpeg` (`crates/engine/src/ffmpeg.rs`) returns `OPSIS_FFMPEG` in debug builds when it is set and otherwise `opsis-ffmpeg` beside `current_exe()`, and `FfmpegMissing` ("Opsis's video tools are missing. Install Opsis again.") when neither is there; `EngineFiles.ffmpeg` and `FootageTools.ffmpeg` take that path.
- The bundle settings (targets, resources, the deb's `gstreamer1.0-libav` dependency, NSIS per-user install, macOS hardened runtime) live only in `tauri.release.conf.json` (deb, rpm, AppImage, NSIS, MSI, the macOS app and DMG); the base `tauri.conf.json` stays bundle-free so `tauri dev` and the e2e build need no staged files. Tauri packs every binary target of `opsis-desktop`, so dev-only binaries sit behind a feature (`export-bindings`). Release builds use `opt-level = 3`, full LTO and one codegen unit, and are stripped (`[profile.release]` in `Cargo.toml`); expect a slow, memory-heavy link. Development film pages keep their source maps so render errors point at source lines.
- A packaged app reads its resources from Tauri's resource folder (`AppPaths`, `crates/desktop/src/paths.rs`: the film page, whose `public/` files are the app's only copy of the `app:` files, `engine-licences`, `LICENSE.ffmpeg.txt`, `LICENSE`, `THIRD_PARTY_NOTICES.md`); in development everything comes from the repository.
- Linux ships deb, rpm and AppImage (CI only for the last two); Windows NSIS; macOS the app, zipped, signed and notarized in CI with the `APPLE_*` secrets, where every Mach-O inside is checked with `codesign`. Check the workflow with `actionlint`.
- Icons: `brand/logo.svg` is the source; `bun run brand:icons` renders `brand/icons/` with the recording browser, and `bun run app:icons` makes `crates/desktop/icons` from the 1024 px PNG with `tauri icon`.
- Not yet: the updater, signing and the Windows and macOS checks. The notices of the crates and npm packages compiled into the app are deliberately not shipped.

**Other shapes.** Exports size the spec with `variant_size` (`crates/compile/src/nodes/output.rs`), and the project Inspector's canvas picker takes its shapes and canvas sizes from the catalog (`shapes`, `variant_canvas`). A recording in a shape narrower than itself keeps its own shape inside the frame (`containBox`) and the camera zooms harder (`zoomBoost`, `narrowPose`): it never rests fully zoomed out and aims at the cursor between actions. In a narrower shape the camera plans for that frame (`tuning.narrow`): `frameFor` fits each target to the frame's width, centred, up to the boosted maximum, and moves only as far as it must to keep the click in shot, as it does in wide shapes. The full-page styles (Proof, Ledger) show the whole page in any other shape (`NarrowBleedClip`) over a blurred copy of the footage, with that same camera only when narrower. Window styles in wider shapes, and the `center`/`fit` choices, keep the old crop or bars. Overlays size by the long side (`overlayScale`) and keep clear of `shapeInsets`; outside landscape, lower thirds move to the top so captions own the bottom. A Layers node with **Keep this layout in other shapes** wraps its layers in a group with `design` (the project's size), drawn scaled to fit, for marks placed over a picture. Everything is in `packages/video/src/core/frame.ts`, except `containBox`, which lives in `packages/video/src/core/still-layout.ts` and also sizes screenshot windows (the capture's own copy is `crates/capture/src/still_layout.rs`).

**Transitions.** A transition overlaps the clips by its length unless **Keep every clip whole** is on (`TransitionRef.hold`): then `sequence_clips` holds the outgoing clip's last frame and the incoming clip's first frame for the transition (group `remap`) and delays the incoming clip's sound, so no clip loses screen time. Cards warn when a transition covers more than 40% of a clip (`cover_row`, fed `inputFrames`), when it is squeezed below 40% of its designed length, when Fit length cuts or speeds a lot, and when an element is shorter than 60% of its usual length; the Timeline outlines heavy transitions (`TransitionMark.covers`). A Sequence's `cuts` give the cut before a port (`before`, a port name from the `cut` widget, which offers the connected clips after the first, so connecting other clips never moves it) its own transition, length and hold (`cuts_for`, last entry for a port wins, entries for empty ports are kept and ignored); `splitBar` splits inside any Sequence, however many clips it holds, shifting later ports and cuts by one and joining the halves with a plain cut. Transition marks carry the `slot` that owns them, and clicking a mark's label on the Timeline selects that node.

**Inputs that grow.** Sequence, Layers, the registry's scene sequencers (Spring settle) and Join files take as many inputs as are connected: a node definition declares a numbered family (`PortFamily`, `.family(…)` in `crates/compile/src/node.rs`: `in1`, `in2`, …, how many are required, a label for each that knows the last connected one, and `refs`, the list settings that name its ports), `NodeDef::input` accepts any member and `input_ports` lists what a node shows, one empty input after the last connected one. The catalogue describes the family (`family`, so the editor's `portOf` and the Local API know any member) and each compile sends every family node's inputs (`EditorCompile.inputs`), which the canvas draws; until the first compile arrives it draws the connected members and one empty one from the edges (`inputsBeforeCompile`, `apps/frontend/src/workflow/graph.ts`), so an edge into `in3` never hangs loose. Settings that pick one of a node's ports use the `cut` or `port` widget over `InspectorContext.ports`. Removing clips on the Timeline closes the gaps (`apply_removal`, `close_gaps`) and splitting shifts ports up, both through `renumber_family`, which moves the edges and the settings in `refs` together.

**Ports that take several connections.** A `many()` input port (Add sound's Sounds) accepts any number of edges; `gather_inputs` merges every value on it (their sounds, concatenated). Sounds take only `audio`: a file becomes a sound through Music or Sound effect, which own its volume and timing. A Sound effect with **On an action** stores the action's node id; Add sound places it at that action's mark in the clip (`anchor_sounds`, via `flatten_spec`), plus an offset that may be negative.

**Window frames.** The Window frame style (window style, frame colour, title bar, title bar text, address mode, title bar font) and Device frame's browser `windowStyle` draw the title bar in `WindowFrame`; without a Window frame a take has no frame. The title bar shows the take's first page address unless the frame has **Title bar text** (`window.text`, `window.mode` on `RecordingProps`): "This address" keeps the typed text for the whole take, "This host with the page's path" puts the typed host in front of the path of the page on screen at each frame (`frameAddress`, `packages/video/src/camera/frame-address.ts`); the address mode only shows for browser takes (`x-show-if-take`). The take logs every main-frame address change, loads and in-page route changes alike, with its time (`ActionLog.addresses`, kept by `Lifecycle` in `crates/capture/src/page.rs`). New Device frames take the computer's OS style (the definition's `host_defaults`, applied when a node is added, `new_node_params`).

**Child temp folders.** Every child program gets a temp folder under `<data folder>/tmp`, named `<app pid>-<kind>-<id>` (`crates/engine/src/temp.rs`) and passed as `TMPDIR`, `TEMP` and `TMP`, so whatever the browser or FFmpeg puts in the system temp folder lands there: each run its own (`run`, which film renders use too) and the streamed views and their browsers one per app launch (`shell-views`, `AppPaths::views_temp`). They are made when the app starts or the run begins, deleted when it ends, and at start `clear_stale_child_temps` deletes folders whose app process is gone. Never write intermediates to the system temp folder from the app. A child started in a folder nobody made fails, so `e2e/src/specs/views.spec.ts` opens the picker on a fresh data folder. Browsers don't end with the app on their own: every browser `launch` starts is remembered by pid (`remember_child`, `crates/engine/src/children.rs`) until it closes, the app ends every one still open when it exits (`RunEvent::Exit`), SIGTERM, SIGINT and SIGHUP save and close it like a quit (`close_on_signals`, `crates/desktop/src/exit.rs`, Unix only) instead of killing it where it stands, and at start `end_children_of_gone_apps` ends any process whose command line names a profile in a temp folder of an app that is gone, before those folders are cleared. Chrome rewrites its process title into one string, so that search reads the whole command line, never one argument.

**Canvas transitions.** The canvas transitions and filters (`makeCanvasPresentation`/`makeCanvasFilter`) draw their shaders only where Chromium's Canvas Draw Element is on, and fall back to CSS elsewhere; the film's launch switches turn it on (`film_switches`, `crates/capture/src/film.rs`). Feature switches are merged, not replaced (`effective_switches`, `crates/capture/src/browser.rs`), because Chromium keeps only the last `--enable-features`. On that path a transition hands each side's captured frame to `onElementImage`; `TransitionWrap` pairs the outgoing and incoming sides of a cut by the frame the cut starts on (`CutBoardProvider`, `packages/video/src/core/transition-cuts.tsx`, one board per set of tracks) and draws both through the incoming side; `SceneSeries` (`packages/video/src/lib/transitions/scene-series.tsx`, the scenes inside one element, such as Data story's) reports to a board of its own the same way. A no-op there leaves the scene blank for the whole transition.

**Renders use one tab.** The frame driver draws a film in one tab, in frame order, which the footage decoders rely on (each frame is decoded once). Measure before adding tabs: shader backgrounds lose their WebGL context when several tabs draw them at once.

**Screenshots.** The Screenshot node captures through `Page.captureScreenshot` with a clip `scale` from `capture_scale` (`crates/capture/src/still_layout.rs`): enough pixels to draw the shot at the largest export (twice the project size), never below the page's pixel ratio, capped by a surface budget for very large regions. Its image carries the region's size, that scale and, for one element, the element's box inside the padded region; `StillElement` lays it out with `windowLayout` (the shot's own shape; a page more than 1.5 times taller than the frame's shape takes the frame's shape and is cut only at the bottom), `cutoutLayout` (the element fitted to the share of the frame in the node's Fit setting, at most 1.5× the captured pixels) and `bleedLayout` (covers the frame, keeping the top), through `stillLayout`; the capture sizes its shot with the same Fit.

**Audio.** Built-in sounds are CC0 files in `public/sfx`, listed in `crates/compile/src/data/sounds.json` (label, `app:` ref, length; Rust sends the list to the editor in the catalog as `sounds`) with credits in `THIRD_PARTY_NOTICES.md`. Built-in music works the same way: CC0 tracks in `public/music` as 128 kbps AAC, listed in `crates/compile/src/data/music.json` (label, mood, length) and sent in the catalog as `music`, offered by Music's Song field (the `music` widget, the same picker as `sound`) and giving Music its length when no file is connected; never add a sound or a song without a checked free licence, and never link to a remote sound at render time. Ducking is a bus setting in the Mixer: rendered stems use `sidechaincompress`; channels shorter than the bus's `ignoreShorterMs` never key it (`duck_keys_for`, `crates/compile/src/mix/plan.rs`); each ducked sound carries its merged spans (`duck_spans`, `Duck.spans`), and the Timeline draws the ducked level from them (`apps/frontend/src/timeline/duck.ts` only draws the curve). Sound effects carry `role: "effect"` and their natural `lengthFrames`. A `keepMusic` sound effect never keys the ducking. Sound file nodes (Even out volume, Fix clicks and clipping, Remove hum) are one filter chain each through `filter_sound` (`crates/media/src/executors.rs`): a sound file keeps its format and sample rate, a video keeps its picture (copied when it can be), and a file with no sound fails with the node's own message; their filter builders are pure (`crates/media/src/filters.rs`, tested by string) and checked against real FFmpeg by ignored tests (`crates/media/tests/sound_fixes.rs`). Remove hum notches the mains pitch and its harmonics; with Find it, two listening passes read the level at 50 and 60 Hz from FFmpeg's log (`hum_listen_filter`, `rms_level`) and the louder wins. Sound picture draws a sound's waveform or spectrum (with a named colour scale, no axes) over a background colour in one graph (`sound_picture_graph`) and outputs an `image`, so the image nodes take it. Shorten pauses works on sound files only (a video would lose its sync): a listening pass reads the pauses from FFmpeg's log (`silence_listen_filter`, `silences`), `kept_parts` keeps the middle of each long pause at the chosen length, and the parts are joined with 10 ms crossfades (`joined_parts_graph`); the time saved goes to the run log. Clean speech (`media.cleanSpeech`) measures the noise first (astats reports every 20 ms window, `noise_level_listen_filter`, and the quietest tenth gives the level, `noise_level`), then takes it out the learned way (the voice decoded to 48 kHz mono, `nnnoiseless` frame by frame with its one-frame delay taken back, mixed with the original in even decibel steps by strength, `denoised` in `crates/media/src/denoise.rs`, and passed back to `filter_sound` as the sound under the file's picture, its channels restored) or the spectral way (`afftdn` told a floor 3 dB above the measured level, `spectral_floor`), then cuts rumble, softens "s" sounds and evens the level in the same pass (`speech_filter`; the evening skips half-waves below 1% so it never lifts the noise in the gaps), and measures again: the levels before and after go on the node's result as `Measured::NoiseLevel` (`NodeResult.measured`, from `ExecutorOutput.measured`), which the card shows. Change pitch (`media.pitch`) moves a sound by semitones with `rubberband`, a required filter (`pitch_filter`): `transients=mixed`, because the default resets the phase at a sudden start and plays the first 0.4 s about 7 dB quieter; a second of silence before it and a trim back to the file's length after it, because the filter drops its last block (69 ms); "Keep the voice's character" preserves formants, which suits voices but nearly silences a pure tone moved far. Voice effects (`media.voiceEffect`, `voice_filter`) makes a telephone (4th-order band of 300 to 3400 Hz), a radio, an echo (`aecho`) or a room, each blended with the original by Mix through `asplit` and `amix` (afir's own `dry` and `wet` are input and output gains, not a mix). Rooms are generated, never recordings (`room_response`, `crates/media/src/generate.rs`): seeded early reflections and a noise tail that falls 60 dB over the room's reverb time while its highs fade faster, at unit energy and different on each side, written beside the result and read by `amovie` into `afir` with `gtype=none:irnorm=-1`, because afir otherwise normalises the response and a room comes out about 26 dB quiet. Fit music to the film (`media.fitMusic`) takes the film's clip for its length (so it keys on the project size and frame rate) and a song, connected or chosen like Music's; `fit_plan` stretches within the largest stretch (`rubberband` tempo, padded and trimmed like Change pitch), loops the chosen section with equal-power crossfades when that is too far, or cuts a longer song, and `fit_graph` ends it on the film's length with a fade; each loop piece is its own input of the same file (`fit_inputs`), because `acrossfade` drops the second of two branches split from one input. The card reads `Measured::Fitted`. Generated sound (`audio.generate`) makes a whoosh, riser, pop, ding, tap, swell or click from settings when it runs, placed like Tones: `sound_shape` (`crates/compile/src/nodes/audio.rs`) turns the preset and its variation into a length, pitch, brightness and take, where Default is the variation chosen by ear for each preset and Custom shows the four sliders, and `crates/media/src/sound_maker.rs` draws it with `fundsp` graphs, peak-normalised to −3 dB, as a 16-bit WAV. `fundsp`'s `envelope` is sampled every 2 ms and every sound fades in over 5 ms, which turns anything shorter into a soft tap, so the click shapes its press and release per sample and fades in over 0.5 ms. Change a preset only after listening to it. Transition sounds (`audio.transitionSounds`, `clip → sound`) puts a sound at every transition of its clip, centred on its middle (`transition_cues` over `flatten_spec`, so through trims, loops and speed), as hits on the node's own Effects channel that never key the ducking, with Action sounds' small seeded changes of pitch and level; a generated sound is made when the node runs, one file for each transition length when Fit is on (`transition_sound_file`), and compile finds each in the node's artifacts; plain cuts have no transition mark, so **Also at plain cuts** adds one at each of them (`FlatTimeline.cuts`, every clip start after the first that has no entering transition, never sent to the editor), with the variation's own length; the card counts them from `Hits.transitions`. Riser to a mark (`audio.riser`) makes a riser or swell of the chosen length that ends on an action, a marker or the end of its clip, with an optional short hit on that point: an action or the clip's end is an `Anchor` (`node_id`, or `clip_end`) that Add sound resolves (`anchor_sounds`), and `keep_end` makes a start before the clip trim the head instead of shifting the sound, so it still ends on time; a marker's time counts from the start of the clip the sound is added to. Room tone (`audio.roomTone`) makes its noise in Rust (`crates/media/src/generate.rs`: white, pink or brown from a seeded generator, so a node always makes the same file): a 10 s WAV whose ends crossfade so it loops without a seam, normalised to the level asked, played looped under the whole film on its own Music channel that never keys the ducking. Tones and countdown beeps (`audio.tones`) makes a sine tone, beep or countdown (short beeps a set time apart, then one three times longer) the same way, with 5 ms edges so it never clicks, and places it like a Sound effect: at a time or on an action, for its own length. **Action sounds** (`audio.actionSounds`, `clip → sound`) puts its click sound at every press of a Click or Type and its key sound at every Press keys chord and typed key in the takes of its clip: `flatten_spec` lists them as `hits`, mapped through trims, loops, remaps and speed like the action marks, and the take logs each typed key's time (`keyTimes`). They are one item per hit on the node's own Effects channel that never keys the ducking, each with a seeded small change of pitch (`AudioItem.pitch`, `asetrate` in the mix) and level so the Timeline and the export sound the same; an action's **No sound** (`silent`, logged with it) leaves it out, the card counts the hits from the node's own output (`AudioValue.hits`), and the Timeline shows a node's hits as one bar with a tick per hit (`AudioItem.hit`, `AudioBar.hits`) whose only edit is its volume. A channel with more than 16 one-shot sounds plays them on a few lanes, each sound padded to the next one's start and joined with `concat`, instead of one `adelay` and `amix` input each (`pack_lanes`, `crates/media/src/mix/graph.rs`): 500 key sounds render in about 2.5 s instead of 24 s.

**Editor look and motion.** Panels, menus and the top bar sit on `bg-sidebar`; the canvas and page backgrounds on `bg-background`; colours are dark zinc greys (hue 286, slight colour, never pure black or white; panels about `#17171B` like Tailwind zinc-900, canvas `#101013`) and only change through the tokens in `apps/frontend/src/index.css` (the window background, `BACKGROUND` in `crates/desktop/src/windows.rs`, matches the canvas token, which `apps/frontend/src/app/window-background.test.ts` checks). Editor animation uses `motion` through the small components in `apps/frontend/src/app/motion.tsx` (`MotionProvider` respects reduced motion). Motion Primitives registry components are installed only when they pass the type check as-is (today: `text-shimmer`); otherwise write a small equivalent in `motion.tsx`. `motion` stays banned in `packages/video`. Pressed toggles and toggle-group items use `--toggle-on` (and `--toggle-on-border` for outline groups), with unpressed ones in the muted text colour, set once in `index.css` because the installed toggle's own pressed colour barely shows on panels; a toggle with its own pressed colour (Mixer mute and solo) sets `data-custom-pressed`. Run success is the `--success` token: the Run panel's checks and the node card's Done border, which `flow-node.tsx` draws itself because the installed status indicator's success border is a plain Tailwind colour. Vertical separators in a centred row need `data-vertical:self-center`, since the separator stretches by default.

**Animation names are global.** React Flow UI's `node-status-indicator.tsx` injects `@keyframes spin` (with a −50% translate) while a node runs, so Tailwind's `animate-spin` is remapped to `icon-spin` in `apps/frontend/src/index.css`. Never name a keyframe `spin`.

**One title bar.** The window has no system title bar. macOS uses `titleBarStyle: Overlay` with a hidden title (traffic lights inside our bar at 16, 16) and the native menu in the system menu bar (`crates/desktop/src/native_menu.rs`); Windows and Linux use undecorated windows with no native menu; the window buttons are ours (`WindowControls`: minimize, maximize/restore, close through the `window_role` command, icon following `WindowStateChanged`), and `WindowBorder` draws a 1 px edge while the window is neither maximized nor full screen. Every screen renders `AppBar` (`apps/frontend/src/app/app-bar.tsx`): `windowDragHandlers` (`apps/frontend/src/app/window-drag.ts`) makes it the window's drag handle: a press on anything that isn't a control starts `startDragging()` only once the pointer has moved `DRAG_START_PX`, and `dblclick` toggles maximize through `window_role`, so a double-click never starts a drag (Tauri's own drag region starts the move on the first press, and under Wayland the compositor then takes the pointer, so its double-click never arrives; mark an element `data-no-drag` to keep it from dragging); never Electron's `-webkit-app-region`, which WebKitGTK ignores; on Windows/Linux it shows the in-app menu (full Menubar from 1280 px, one Menu button below). Menus come from one list, `app_menu` (`crates/desktop/src/menu.rs`), built natively on macOS and sent to the editor for the in-app menu (`app_menu_sections`); `useMenuShortcuts` handles its accelerators in the page on Windows/Linux (leaving cut/copy/paste/select-all/undo/redo to text fields while one is focused), roles run through `run_role` in Rust, and navigation commands are handled once in the main window's layout route.

**Editor hosting.** Hash history only. Tauri serves `apps/frontend/dist` (in development the Vite server on `localhost:5173`); the CSP is `app.security.csp` in `crates/desktop/tauri.conf.json`, which allows the file server's `http://127.0.0.1:*` for pictures, media, fonts and fetches. `index.html` loads `apps/frontend/public/page-errors.js` (the editor's only public file) and `src/app/boot.ts` before the app: uncaught errors, rejections, `console.error` and `console.warn` from every window go to the app's log (`page_log`, target `page`), and the platform comes from the user agent (`apps/frontend/src/lib/platform.ts`), never from a call made while a module loads: a chunk that ran before boot once left the window black.
